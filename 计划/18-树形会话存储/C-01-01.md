## C系列-接口（C-01-01）· 树的库：表、写入、读取

- 功能
  - **一个文件**：`~/.dsh/plan-tree/trees/<根会话 id>.db`（sqlite，一棵树一个）。原版的 `session.v<N>.jsonl.zst` 在会话目录里，两边互不认识。
  - **两张表**，各管一件事：
    ```
    sessions(id TEXT PRIMARY KEY, parent TEXT, at_seq INTEGER, plan_id TEXT, created_at INTEGER)
    records(session_id TEXT, seq INTEGER, line TEXT, PRIMARY KEY(session_id, seq))
    ```
  - `sessions` 一行 = 树上一个节点：它叫什么、从谁分出来、继承了多少条。`parent` 为空表示"接根会话"。
  - `records` 一行 = 一条**提案记录**（`plan` / `adopt` / `reject` / `shelve` / `status` / `dispatch` / `file`），`line` 是那条记录的 JSON，不分拆字段。`seq` 与该会话日志里的位置一致。
  - **树管提案，不管消息**：会话消息（`user/message`、`assistant/message`、`tool/*`…）一条都不进库，它们留在原版日志里。理由是两边职责不同——消息是会话能继续跑的前提，提案是树的全部内容；混在一起会逼着树去管 5 MB 的拷贝。
  - **`at_seq` = 从父那里继承了多少条**（不是"第几条之后"）。叶子也有这个数，含义一致：`A-1` 从 `A` 继承 2 条，`A` 从根继承 4821 条。它是**关系上的一个数字**，不是消息副本。
- 暴露
  - **两个视图，同一棵树**：
    - 关系视图：`chain(leafId)` 沿 `parent` 往上给出有序链条（根在前），加上 `sessions` 里的 `plan_id` / `at_seq`；界面的树形图就是它的渲染，**不另存一份模型**。
    - 内容视图：`records(ids)` 取这些会话的提案记录，按写入顺序。传哪些 id 由调用方决定，于是"往下继承、往上不聚合"这条边界由**传参**决定，而不是由库里存了什么决定：一个会话的视图传它自己的祖先链，就看得见祖先的提案，看不见任何后代或兄弟的。
  - **不打开就不加载**：没有任何预加载、常驻缓存。
- 表结构与身份
  - `PRAGMA application_id = 0x54524545`（"TREE"）：任意 sqlite 工具打开就知道这是谁的库。
  - `PRAGMA user_version = 2`：格式版本，迁移时先看它。**1 → 2 是把 `events` 改名成 `records`**（旧名字读起来像在管消息）：旧库就地搬行、删旧表、把 `about` 与版本一起换新。
  - `meta(key, value)`：`about`（一句人话，说明这是什么、怎么读）、`format_version`。
- 写入路径
  - **建节点**：`INSERT INTO sessions(id, parent, at_seq, plan_id, created_at)`，一条。派发时写，先于子会话的第一个事件。
  - **追加记录**：`INSERT INTO records(session_id, seq, line)`，一条。用 WAL，读不阻塞写。**镜像失败只 warn，不影响日志**——日志才是会话能继续跑的前提。
  - **写入幂等**：同一 `(session_id, seq)` 重复插入用 `INSERT OR IGNORE`，重放不会翻倍。
  - **归属**：派发时 `note(childId, rootId)` 记下子属于哪棵树；进程重启后内存表为空，靠扫 `trees/*.db` 的 `sessions` 表把根找回来，扫不到就自己独立成树。
- 约束/许可/缺点
  - **约束**：不碰原版任何文件。会话日志只由原版写；我们只写自己的库。
  - **约束**：文件名不能长得像 `session.jsonl` / `session.v<N>.jsonl`（含 `.zstd` 变体），否则会被原版当成本会话的一代日志。我们的库在 `~/.dsh/plan-tree/` 下，不沾这些模式。
  - **许可**：`node:sqlite` 是 Node 内建的（24.18.1 实测可用，无需 flag、无需装包），所以不引第三方依赖。
  - **缺点**：库是自造格式，读它必须经本 mod；关掉 mod，这些提案就看不见了（会话本身不受影响）。
  - **缺点**：同一份提案现在存在于两处——会话日志（原版）与树库（本 mod）。日志是权威，库是索引与留存；两者不一致时以日志为准。
- 待议
  - 节点 id 用人给的名字（`02-04-06`）还是 GUID？前者让树在磁盘上可读，后者与宿主一致、改名免费。
  - `line` 要不要按批做 zstd blob（省空间，但打开就不直接可读）。第一版明文。
  - 同一棵树被两个会话同时写（理论上不该发生）时，是用 `busy_timeout` 排队还是直接报错。
  - 界面读库要过哪条通道：现在库只在 host 侧（sqlite），客户端拿不到；要么开一个投影把树摊给客户端，要么开一条只读的 remote 调用。
