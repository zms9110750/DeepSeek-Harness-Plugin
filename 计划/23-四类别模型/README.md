# 四类别事项模型

> **状态**：模板已写完，等审查。代码已实现 kind 字段与推断。
> **替代**：之前的「计划 + 全局九态」模型。

---

## 一、为什么换掉「计划」这个词

原来的库里跑着这些互不相干的东西，全被叫成「计划」：

| 实际是 | 现在的类别 |
| --- | --- |
| 用户甩过来的一堆要求 | 目标 |
| AI 的设计 / 决策 / 提问 | 设计 |
| 汇报 / 复盘 / 阻碍 | 记录 |
| 调研 / 实现 / 修复 | 工作 |

它们**生命周期、谁能动、占不占会话**完全不同，却共用一套九态和一条
「处理中只能有一个」。结果规则要么太松（草稿能提权），要么太紧（用户提的问题被当成
"任务"卡住）。

最典型的症状就是那个死锁：**父计划一被领取，它的子计划就全领不了。**

---

## 二、四个大类

分类轴是「**什么时候算做完**」——四个定义互斥且穷尽：

| 大类 | 做完的定义 | 谁动手 | 占位 | 可领取 |
| --- | --- | --- | --- | --- |
| **目标** goal | 子事项全部终结 | 无人（推导） | 否 | 否 |
| **设计** design | 用户采纳 / 驳回 | **用户** | 否 | 否 |
| **记录** record | 写出来即完 | 无人 | 否 | 否 |
| **工作** work | 真做出来了 | AI | **是** | **是** |

### 只有「工作」能领取

这是整个模型的关键。另外三类的行为：

- **目标**：它的「进行中」是**推导出来的**（有没有未终结的子事项），
  不是存下来的字段。所以它不占位，也不需要领取。
- **设计**：等用户回答 / 选择 / 过目。AI 领它没有意义。
- **记录**：没人动手，写出来就完。

### 死锁在这个模型下不存在

旧模型：领子计划 → 要求父计划「处理中」→ 父占住会话位 → 子领不了 → 死锁。

新模型：能当容器的父节点是**目标**，而目标**不可领取**。
父子争位这个前提从根上消失了，不需要任何"交接"的特殊逻辑。

---

## 三、模板决定行为

大类只给最底层的性质，其余全部下沉到模板。

| 模板 | 大类 | behavior | 形态 |
| --- | --- | --- | --- |
| `G · 用户提出` | 目标 | answer | 空表单 + 派发按钮 |
| `Q · 决策` | 设计 | decide | **选项卡**（可选项/可填/可拒/可要求调研） |
| `P · 方案` | 设计 | propose | 长文 + 采纳 / 打回 |
| `K · 提问` | 设计 | answer | 一问一答 |
| `C · 接口` | 设计 | propose | 契约 + 错误行为 |
| `A · 问题` | 设计 | propose | 痛点 + 验收 |
| `B · 阻碍` | 记录 | block | 阻碍卡片 + 影响 |
| `W · 汇报` | 记录 | write | 只读长文 |
| `F · 复盘` | 记录 | write | 只读长文 |
| `R · 调研` | 工作 | execute | 正文 + 结论 + 证据 |
| `D · 实现` | 工作 | execute | 正文 + 改动清单 |
| `I · 实现项` | 工作 | execute | 单个可交付块 |

### 决策和设计是一回事

用户原话：

> 设计，和决策，是一回事。决策是封闭问题，但不是真的封闭。用户还是可以要求调研。
> 设计，是天然开放问题。ai 做的难道能信吗？用户还是要过目的。

所以两者都是 `design` 大类，区别只在模板的 `behavior`：

- `decide`：封闭问题，给 2-4 个互斥选项
- `propose`：开放问题，给方案 + 代价 + 替代方案

「不是真的封闭」体现在：决策模板里有「我还不知道什么」小节——
如果某个未知项会直接改变答案，先派一个调研，不要硬问。

## 四、阻碍是记录类的一个模板

用户纠正过我三次，最后一次才说清：

> 阻碍不是关系。是记录里面的一种模板。是这个模板产生的行为。
> 是工作和"阻碍"之间的交互。

所以阻碍是**节点**，由工作**派生**出来：

```
工作 A（处理中，占会话位）
 └──派生──> 记录：阻碍（behavior=block）
```

它一出现，触发这个行为：**A 从「处理中」踢成「需要补充」**。

不是链接，是父子关系。

### 阻碍解除后不自动改状态

用户明确：

> 阻碍消除以后，不需要自动化的动别的状态。
> 只要能查出来，并且阻碍已经完成了，就可以继续下去。
> 能点继续就是可以继续。

所以「能否继续」是**实时查询**，不是存的状态：

```
能点「继续」 ⟺ 这个节点当前没有未终结的阻碍子节点
```

这和「目标的状态由子事项推导」是同一个思路：**不落状态，靠派生判断。**

### 为什么不用自动流转

九态是拟合 A2A 协议用的，不是我们内部自发的。
往里塞新语义 = 污染协议对齐层。

## 五、派发规则

| 从 \ 派发到 | 目标 | 设计 | 记录 | 工作 |
| --- | --- | --- | --- | --- |
| **目标** | — | ✅ | — | ✅ |
| **设计** | — | ✅ | — | ✅ |
| **记录** | — | ✅ | ✅ | ✅ |
| **工作** | — | ✅ | ✅ | **—** |

**工作不能派工作。** 理由：

> 一个需要再拆的东西，本身就不是"可动手"的——它是容器。容器就是目标。

如果真遇到「做的过程中发现得拆成几份」，就把这条工作**升级为目标**。

这个限制还顺带堵死了死锁：工作只能派设计/记录/调研，
这三样都不参与领取竞争，所以永远不会出现"父工作占着会话、子工作领不了"。

## 六、不做什么

- **不做 tag**。用户原话：「能不能先不做 tag。因为目前只需要具体枚举的语义。」
  我找不到需要 tag 的反例：组合靠**加节点**，不靠加标签（树本身就是组合器）。
- **不改九态**。它是 A2A 协议对齐层。
- **不自动流转**。阻碍解除后停在原状态，靠查询判断能否继续。
- **不重写存储**。还是单 JSONL、append-only。
- **H1–H8 不再是模板**。它们是"为什么停"的理由，已降级为阻碍模板里的词表。

## 七、兼容

老数据没有 `kind` 字段，读的时候按 `type` 推：

```
A/B/C → design    D/R → work    F/H1-H8 → record    G → goal    空 → work
```

**注意**：新 `B` 是「阻碍」（记录类），老 `B` 是「设计」（设计类）——同一个字母含义变了。
兼容靠 `kind` 字段：老数据没存 kind 才按 type 推，且老数据不会出现新 B。
