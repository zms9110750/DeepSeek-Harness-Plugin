# 22-事项模型（Type-Driven）

- **状态**：蓝图草案，未实现
- **来源**：T-045（用户任务3）
- **一句话**：把「计划」这个词拆掉，换成**事项（Item）**；一切行为由 `kind` 决定，
  状态是 `kind` 的子集，标记（已读/待处理）与状态正交。

---

## 一、为什么不能叫「计划」了

现在库里跑着这些互不相干的东西：

| 实际是 | 现在被塞进 |
| --- | --- |
| 用户甩过来的一堆问题 | 计划 |
| 要 AI 做的一件事 | 计划 |
| AI 的分析 / 设计 | 计划 |
| 必须用户拍板的决策点 | 计划 |
| 一次调研 | 计划 |
| 一份只读的汇报 | 计划 |
| 一次失败的原因说明 | 计划（备注里） |

它们的**生命周期、谁能动、要不要占住会话、能不能派发**全都不一样，却共用一套九态和一个
「处理中只能有一个」的规则。结果就是要么规则太松（草稿能提权），要么太紧（用户提的问题
被当成"任务"卡住）。

**「计划」只是其中一种。** 需要一个上位词。

---

## 二、命名

### 上位词：**事项**（Item）

理由：

- 「事项」天然涵盖"待办 / 待议 / 待答 / 待看"，不预设它一定要被"执行"。
- 与「条目」区分：条目偏**存储单位**（一行记录），事项偏**流转单位**（有生命周期）。
- 与「工单」区分：工单预设了客服式的流程，太重。

`计划` 保留为**一个 kind**（真正需要执行的那类），不废除，只降级。

### 二级词：**种类**（kind）

避免与「类型（type = 模板）」混淆：

| 词 | 字段 | 含义 |
| --- | --- | --- |
| **种类** | `kind` | 决定行为：有哪些状态、能否派发、谁处理、占不占位 |
| **模板** | `type` | 决定正文骨架与交互形式（A/B/C/D/R/F、H1..H8、U…） |

一个 kind 下面可以有很多模板；模板不能跨 kind 乱用（见第六节）。

## 三、种类表（第一步只要这些）

| kind | 中文 | 谁创建 | 有状态？ | 占位？ | 能派发 | 默认模板 |
| --- | --- | --- | --- | --- | --- | --- |
| `question` | 用户问题 | 用户 | **无** | 否 | 是 | U |
| `task` | 用户任务 | 用户 | **无** | 否 | 是 | U |
| `analysis` | 分析 / 设计 | AI | 有 | 是 | 是 | B / C |
| `decision` | 需要决策 | AI | 有 | **否** | 是 | Q |
| `research` | 研究 | AI | 有 | 是 | 是 | R |
| `report` | 汇报 | AI | 有（只读） | 否 | 否 | W |
| `review` | 复盘 | AI | 有 | 是 | 否 | F |
| `impl` | 实现 | AI | 有 | 是 | 否 | D |

### 关键：`question` / `task` 没有状态

这是你第 1 条的原话：

> 只要他们派发了子任务，只要采纳了，那他们实际上就是进行中。
> 而因为他们没有实际的状态。所以他们是进行中，也不阻止领取任务。

落地方式：

```
草稿(未采纳)  →  已采纳(派发)  →  子事项全部终结  →  自动算「完成」
```

- 它们的「进行中」是**推导出来的**（有没有未终结的子事项），不是存下来的字段。
- 因为是推导的，**它不占位**——一个会话做 `question` 的方式不是"领它"，而是"领它的子事项"。
- 「未采纳 → 已采纳」这一步仍然只有用户能做（与现在的采纳规则一致）。

### 关键：`decision` 也不是占位型

```
AI 提问  →  等用户选  →  用户选了  →  AI 接着做
```

它等着的时候**不占会话**（会话可以去干别的），所以 `decision` 是"非占位"的。
这解决了现在「搁置就卡住」的问题。

## 四、状态：从全局九态变成「kind 的状态子集」

现在九态是全局的，所有东西共用。改成：

```js
STATES = {
  analysis: ['草稿','提交','处理中','需要补充','需要授权','完成','失败','取消','拒绝'],
  decision: ['待选','已选','已拒','需要更多信息'],
  research: ['草稿','提交','处理中','需要补充','完成','失败','取消','拒绝'],
  report:   ['草稿','已发布'],
  review:   ['草稿','提交','处理中','完成'],
  impl:     ['草稿','提交','处理中','需要补充','完成','失败','取消','拒绝'],
}
```

### 但「分组」必须通用

你之前定的三组（进行 / 搁置 / 完成）要保留，作为**跨 kind 的统一投影**：

| 组 | 含义 | 各 kind 怎么映射 |
| --- | --- | --- |
| 进行 | 还活着 | 含"处理中/待选/提交"等 |
| 搁置 | 停下来等人 | 含"需要补充/需要授权/待选" |
| 完成 | 终结 | 含"完成/失败/取消/拒绝" |

**面板只看组，不看具体状态名。** 这样加新 kind 不用改面板。

### 占位 vs 非占位

| 概念 | 含义 |
| --- | --- |
| **占位状态** | 会占住一个会话（`处理中`） |
| **非占位状态** | 不占（`提交`、`需要补充`、`需要授权`、`待选`） |

「一次一个会话只能做一件事」这条规则**只对占位状态生效**。
现在的问题是把「处理中」以外的状态也当成了"在做"，导致搁置就卡死。

## 五、标记：与状态正交（围棋落子的比喻）

你第 2 条要的「像围棋落子一样高亮」「需要处理 / 需要审核 / 已读 / 未读」「像邮箱那样」。

### 这是第二套维度，不是状态

| 标记 | 谁设 | 含义 |
| --- | --- | --- |
| `unread` | 系统（新建/被改动时自动） | 我没看过 |
| `read` | 我（打开详情即置） | 看过了 |
| `needs-me` | 事项自己声明 | 卡在我这里，等我动手 |
| `needs-review` | 派发方 | 我做的，等你审 |

### 为什么必须与状态分开

- 「已读」不是生命周期的一部分——一张"处理中"的事项可以已读也可以未读。
- 「需要处理」可能对应多个状态（`需要授权` + `待选` + `需要补充`），但它是**同一个语义**：等我。
- 如果塞进状态，状态数会爆炸（3 组 × 2 读 × 2 待 = 12 种，还要按 kind 再乘）。

### 高亮规则（界面）

| 条件 | 表现 |
| --- | --- |
| `unread` | 强高亮（像刚落的子） |
| `read` | 正常 |
| `needs-me` | 左侧色条 + 计数徽章 |
| `needs-review` | 虚线边框 |
| 超过 N 天没动 | 淡出 |

面板顶栏给三个计数：**待我处理 / 待我审 / 未读**。这就是邮箱的心智模型。

### 标记什么时候自动置

- 新建 → `unread`（对创建者以外的人）
- 被改写（备注、状态、正文）→ 对**不是改它的那个人**置 `unread`
- 状态变成"等我"类（`需要授权` / `待选` / `需要补充`）→ 自动 `needs-me`
- 派发方把自己的子事项标 `needs-review`（可选）

## 六、模板与 kind 的关系

你第 3 条：模板自己也需要类型，且**只对部分 kind 可见**。

### 模板声明自己属于哪些 kind

```yaml
# templates/W.yml（汇报）
name: W · 汇报
kinds: [report]
```

```yaml
# templates/Q.yml（决策）
name: Q · 需要决策
kinds: [decision]
```

```yaml
# templates/U.yml（用户问题 / 用户任务共用）
name: U · 用户提出
kinds: [question, task]
```

### 可见性规则

- 新建某 kind 的事项时，**模板下拉只列 `kinds` 含它的**。
- 现在的问题是「汇报里可能有研究、复盘」——那不是模板嵌套，是**汇报可以派生出研究和复盘**：

```
report(W) ──派发──> research(R) ──派发──> review(F)
                    └──派发──> review(F)
```

所以「模板对哪些 kind 可见」解决的是"建的时候能选什么"，
"派发能派什么"是另一张表（见第七节）。

### 现有的 A–F / H1–H8 怎么归

| 模板 | 归属 kind |
| --- | --- |
| A（问题） | `question` |
| B（设计）、C（接口） | `analysis` |
| D（实现） | `impl` |
| R（研究） | `research` |
| F（复盘） | `review` |
| H1–H8（搁置原因） | **不归属任何 kind**——它们不是"做什么"，是"为什么停"。改为状态变更时的**原因标签**，不再是一等模板 |

最后这条是重要简化：H1–H8 现在混在模板列表里，语义上和 A–F 不是一个维度。

## 七、派发：从「新建 + 选派生自」变成「在事项上直接派」

你第 4 条：

> 应该不需要点击新建计划，选择派生自。而是从用户决策上面，直接创建一个子任务。

### 现状

新建表单里有一个「父计划」下拉，要手动选。这是把树结构暴露给用户去拼。

### 改成

详情层底部一排**派发按钮**，按当前 kind 的「可派发」表生成：

```
[ 派发：研究 ]  [ 派发：决策 ]  [ 派发：实现 ]
```

点一下 → 表单打开，`parent` 已填好、`kind` 已选定、模板已选好 → 用户只填标题和正文。

### 可派发表

| 从 \ 到 | question | task | analysis | decision | research | report | review | impl |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| question | — | ✅ | ✅ | ✅ | ✅ | — | — | ✅ |
| task | — | ✅ | ✅ | ✅ | ✅ | — | — | ✅ |
| analysis | — | — | ✅ | ✅ | ✅ | ✅ | — | ✅ |
| decision | — | — | ✅ | ✅ | ✅ | — | — | ✅ |
| research | — | — | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| report | — | — | — | — | ✅ | — | ✅ | — |

规则简述：

- 用户类的（question / task）什么都能派。
- report 只能派"补充材料"类（research / review）。
- impl 做完只能派 review。
- review 什么都不派（终结）。

## 八、存储：向后兼容的最小改动

现有 JSONL 事件不变，新事件多两个字段：

```json
{"op":"upsert","task":{"kind":"decision","flags":["unread","needs-me"], ...}}
```

- 老记录没有 `kind` → 按 `type` 推断（A→question，B/C/D/R/F → 对应 kind，H*→analysis）。
- 老记录没有 `flags` → 视为 `[]`。
- **状态字段不变**（还是那个字符串），只是每个 kind 允许的取值集合不同。

---

## 九、不做什么（边界）

- **不重写存储层**。还是单 JSONL、append-only。
- **不引入 kind 插件化**。第一步 kind 是代码里的一张表，不是可注册的东西。
- **不改「一次一个」的本质**。只是把适用范围收窄到"占位状态"。
- **不做模板嵌套**。汇报派生研究是**树**，不是模板里套模板。
- **不改 group 的三分类**。进行 / 搁置 / 完成 是跨 kind 的统一投影，保留。

## 十、落地顺序（建议）

| 步骤 | 内容 | 为什么先做 |
| --- | --- | --- |
| 1 | `kind` 字段 + 推断函数 + 三分类仍按 kind 映射 | 不改行为，先把概念落进数据 |
| 2 | `flags`（unread / read / needs-me / needs-review） | 纯展示层，风险最低，体验提升最直接 |
| 3 | 状态改为「kind 的子集」+ 占位/非占位区分 | 解决"搁置卡死"和"用户任务不占位" |
| 4 | 模板声明 `kinds` + 下拉过滤 | 依赖 1 |
| 5 | 详情层派发按钮 + 可派发表 | 依赖 3、4 |
| 6 | 面板按 flags 高亮 + 三个计数 | 依赖 2 |
| 7 | 改称「事项」（文案、README、工具描述） | 最后做，纯改名最便宜 |
