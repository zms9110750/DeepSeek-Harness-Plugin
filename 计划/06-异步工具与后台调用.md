# 06 异步工具与后台调用

对应需求：`todo/异步的工具.TXT`
关联：`05-带注释的工具调用.md`（编号）、`02-能力接入.md` 2.2（拦截）

```yaml
A 问题:
  痛点: ask、命令行授权请求这一类调用，用户不选就卡死整个循环；
        而有些任务本来可以先做别的。另外调用之间没有统一编号，
        想"待会儿再看"根本指认不了。
  验收: 任何调用都有编号；调用可以被放到后台；有按编号的 wait 和 kill；
        用户回来能补答；循环不被无关调用阻塞。
  适用性: 只对能安全脱离当前步骤的调用有效。写文件不能后台 —— 会破坏顺序语义。
  先例: Reasonix 的体验（用户描述）；DSH 自己的 jobs（已经有了大半）。
```

---

## 关键发现：DSH 已经有后台作业系统

不是没有，是**只给了一部分工具用**。

`ctx.jobs`（`@deepseek-ai/dsh-jobs-local`）是进程内的通用作业注册表，
设计上明确写着 **kind-independent**（"bash, PTY"都走同一套）。

三个模型可见的工具（`@deepseek-ai/dsh-tool-jobs`）：

| 工具 | 签名 | 说明 |
|---|---|---|
| `job_output` | `(job_id, wait?, timeout_ms?)` | 默认不阻塞；`wait:true` 才等，默认 30s，上限 600s |
| `job_list` | `()` | `<id> [<kind>] <status> — <label>` |
| `job_kill` | `(job_id, reason?)` | 请求取消，**真的停了**才算 settled |

**完成通知**是这套系统最聪明的地方：

- 代理正忙 → 通知注入它的**下一步**（"the turn cannot close while the inbox holds it"）；
- 代理空闲 → **唤醒一个新一轮**；
- 模型已经自己取过结果 → 不再通知（`awaited`）；
- 唤醒次数可以用 `maxConsecutiveWakes` 封顶，或用 `completionDelivery: quiet` 完全关掉。

几个已有数字（可以直接抄）：

```yaml
maxConcurrentJobsPerOwner: 10     # 每个 owner 同时跑的上限，满了直接报错不排队
retainBytes: 262144               # 实时输出环
settledRetainBytes: 16384         # 结束后保留
pumpPollMs: 150                   # 拉取轮询
waitTimeoutMs: 30000              # 默认等待
maxWaitTimeoutMs: 600000          # 模型能要的最长等待
```

## 现在缺的三块

### ① 编号不是统一的

只有**成了 job 的调用**有 id（`pwsh run_in_background`、subagent）。
同步调用没有 id，所以"指认"和"wait/kill"只对后台调用成立。

→ 这就回到 `计划/05` 的 `#n`：**一套编号覆盖所有调用**，后台的 job id 就是 `#n`。

### ② 任何工具还不能后台

现在只有产 job 的"生产者"能后台。要让 `read`、`web_fetch`、甚至 `ask` 也能后台，
得在 `tools/execute` 外面包一层，把这些工具的同步 execute 变成 job producer。

难点不在调度，在**返回值语义**：工具结果是 `render` 出来的内容块，
变成 job 之后要重新定义"何时、以什么形状回到上下文"。

### ③ 缺一个按编号的 wait

现在"等"是 `job_output(wait:true)`，不是独立工具。
用户描述里的 wait/kill 两件套更清楚：`wait(#n)` / `kill(#n)`。

→ 建议：保留 `job_*` 不动（向后兼容），新增 `wait(#n)` / `kill(#n)` 作为统一入口，
内部转调 `ctx.jobs`。

## 设计

```yaml
B 主要目标:
  - 统一编号: 每个调用拿到 #n（见 05）
  - 可选后台: 调用时带 background: true，立刻返回 #n
  - 按编号操作: wait(#n) / kill(#n)

B 次要目标:
  - 完成后自动把结果注入（复用现有通知机制）
  - 被后台的 ask / 授权请求，用户回来补答后自动回填结果
  - 队列可见（和 03 的并发节流共用一块面板）

B 约束:
  - 写操作禁止后台（顺序语义会被破坏）
  - 后台结果必须最终回到上下文，不能"悄悄丢了"
  - owner 被销毁时，它的 job 全取消（现成行为，别改）

B 工具:
  - ctx.jobs（start / snapshot / cancel）
  - tools/execute（包装同步 execute 成 job）
  - tools/post-execute（回写 #n）
```

## C 接口

```
同步调用:  #12  read  …            → 结果 + "#12"
后台调用:  #13  pwsh  …  [running] → 立刻返回编号，结果稍后到
指定:      wait(13) / kill(13)
```

待议：

1. **同步调用要不要也建一条 job 记录？** 建了就能统一 wait/kill，代价是每个调用都多一条生命周期记录（内存 + 事件体积）。
2. **后台的 ask 怎么补答？** 现有 `userQuestions` 服务有 `askTimed`，超时会失败 —— 要改成"挂起不超时，等用户回来"。
3. **通知策略**：默认唤醒（wakeup）还是注入（quiet）？前者会自激（被唤醒的回合又开新后台任务），后者可能卡住没人看的会话。

## D 实现

```yaml
复用:
  - ctx.jobs 已经能跑，先不重写
  - 三个 job_* 工具保留

新增:
  - 编号器: 会话内自增，通过 tools/post-execute 回写
  - wait(#n) / kill(#n): 薄封装，转调 ctx.jobs
  - background 参数: 先只加在"我们自己的工具"上，不碰内建

风险:
  - 包一层 tools/execute 会影响所有工具的行为，必须能一键关掉
  - 后台化一个工具后，它的 render 逻辑要走"最终结果"路径，不能沿用中间态

魔数:
  - 沿用现有: 30s / 600s / 10 并发 / 256KB
  - 新增: 单个会话最多保留 200 条编号记录（超出丢弃最老的元数据，正文仍可从日志取）
```

## 和"用户不选就卡死"的关系

这是本需求最原始的那句话。拆开是两件事：

1. **ask 不再阻塞循环** —— 变成后台作业，用户回来补答；
2. **授权请求同理** —— 审批（approval）也要能挂起，而不是让整个回合停在对话框上。

第 2 条和 `02-能力接入.md` 2.2 的拦截是同一个闸门：**拦截/放行/挂起**三种结局，
现在只有前两种。

## Reasonix 的做法（已从源码确认）

它的后台调用是**三件套，全部按 job id**：

| 工具 | 行为 |
|---|---|
| `bash(run_in_background)` / `task(run_in_background)` | 起后台，立刻返回 |
| `bash_output(job_id?)` | **增量**读上次之后的新输出 + 状态；省略 id 就列出在跑的作业 |
| `wait(job_ids?)` | **阻塞**到结束，返回状态与最终输出；省略就等全部 |
| `kill_shell(job_id)` | 终止；已结束或 id 未知是 no-op |

比我们现在的 `job_output(wait:true)` 好在两点：

1. **读和等是两个工具**，语义清楚 —— "看一眼"和"等它完"是不同意图；
2. **省略 id 就列全部**，不用先 `list` 再 `output`。

对应到我们的设计：

- 保留 `job_output` / `job_list` / `job_kill`（向后兼容）；
- 新增 `wait(ids?)`，做成 `job_output(wait:)` 的显式版本；
- `#n` 编号与 job id 合并成一个东西，避免两套 id。

另外证实了一条：**它的用户交互也是工具**（`ask` / `await_user`），
不是弹窗阻塞 —— 和需求 8 的方向一致。
