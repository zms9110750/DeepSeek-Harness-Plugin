## B系列-设计（B-05）· 子工作区是唯一可写范围

- 主要目标
  - 一个会话有一个根（它开始时的那个工作区）。它派出去的每一支，可以各自认领一块**子工作区**。
  - **写只落在被认领的范围内**；一块都没有认领，就只能读。
  - 认领由父在派发那一刻写下，后代不能改（A-1 的工作区那一条）。
- 次要目标
  - 锁的判据是**"有没有认领"**，不是"有没有计划"。只读的目的从头到尾是逼出第一块写得清的地方，计划只是通往它的路。
  - 完全权限（`danger-full-access`）整套跳过——用户已经明说放开，不要再替他管。
  - 逃生口一条命令：`/plan off`，会话级，随时收回。
  - 认领是记录，不是目录操作：不创建目录、不检查存在、不动 ACL。
- 约束/许可/缺点
  - **约束**：认领事件必须写在**分叉边界之前**。写在之后，子会话说看不见自己的写范围，会在自己的目录里被锁成只读。
  - **约束**：权限投影读不到时**不拦**。读不到就不设限——把正常会话锁死比放过一次更糟。
  - **缺点**：读范围（A-5 的后半段：以用户工作区为基准、可读别的项目、范围外逐个授权）**还没做**。现在只锁写，没管读。
  - **缺点**：`workspace-write` 档也会被收窄到认领目录，可能出乎意料。所以 `/plan off` 必须一直可用，且拒绝文案要把这条路写出来。
  - **许可**：一块目录可以被不同计划先后认领；记录按路径归一化后作键，不做去重也不做继承。
  - **许可**：会话根永远可读，可写与否只看认领。
- 被否决的替代
  1. **用"有没有第一个计划"当只读判据**（早期实现）
     - 计划和目录不是一回事：画图的计划根本没有目录，却会解锁整个工作区；
     - 反过来，一份还没派发的计划不该等于"这里可以随便写"。
  2. **交给文件沙箱自己判断**
     - 沙箱只认"根"，不认"这一支的范围"，也分不清同一棵树里两个子会话各自的目录。
  3. **按"目录属于谁"建一张全局表**
     - 那就成了另一个工作区管理器，和 DSH 的 workspaces 打架；而这里只需要"这一次派发划了哪块"。
- 工具
  - 投影 `subWorkspaces`：`{ claims: { [归一化路径]: { path, planId, by, at } } }`。
  - 服务 `subWorkspaces`：`claim / release / owns / claimFor / claimsOf / rootOf / stateOf`。
  - 命令 `/sub-workspace list | add <路径> | remove <路径>`。
  - 守卫 `tools.guard`：写工具 + 不在认领内 + 不是完全权限 → 拒绝，并给出逃生口。
  - `plan_dispatch` 带 `workspace` 时自动认领。
- 先例
  - 产品的权限预设是"沙箱边界"，不是"任务边界"：它管得住越界，管不了"这一支该在哪干活"。子工作区补的正是后者。
- 结论：**采纳**（0.17.0 起实现；读范围与范围外授权仍未做）。
