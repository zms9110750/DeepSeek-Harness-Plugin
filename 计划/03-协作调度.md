# 03 协作调度

## 3.1 并发 agent 节流

```yaml
A 问题:
  痛点: subagent 一次能扇出很多，20 个同时跑既烧钱又压机器，用户也来不及看
  验收: 有池子；当前 x 个在跑时，下一个要等 3x 秒；用户随时能停，排队的也跟着取消
  适用性: 只对"通过工具创建的"子 agent 有效；用户手动开的不受管
  先例: 无直接先例（gitagent 只管文件锁，不管 agent 数量）

B 设计:
  主要: 一个带队列的 spawn 门
  次要: 全局上限、按模型分池、队列可见
  约束: 待启动的项必须能被一次性取消；不能占用会话上下文
  工具: ctx.subagents（startActivation / listChildren / interrupt）

C 接口:
  功能: 发起后立刻返回"已排队 + 位置"，而不是阻塞到启动
  暴露: 模型能看到"排队中"，用户能看到队列
  待议: 队列满了怎么办（拒绝？默认上限多少？）

D 实现:
  三种可能路线:
    ① 自写一个 subagent_pool 工具，内部调 ctx.subagents —— 最干净，但模型要愿意用新名字
    ② 包一层同名工具覆盖原 subagent —— 取决于注册顺序能否覆盖
    ③ 在 tools/pre-execute 里拦截并延迟 —— 该阶段是同步的，不能拖时间，**不可行**
  魔数: 退避 3x 秒（用户指定）；建议全局上限 8；队列上限 32
```

**难点**：`3x` 里的 x 是"正在执行的个数"，所以要能实时拿到运行中数量 —— `ctx.subagents.listChildren` 可以，但它是 async，且要按 parent 过滤。

## 3.2 子工作区（读写锁）

```yaml
A 问题:
  痛点: 多个子 ai 同时改同一个目录，互相覆盖；也没有"我要占这块地"的声明方式
  验收: 写操作前声明占用路径；被占用时**异步阻塞**而不是报错；没声明就默认占当前工作区
  适用性: 只在同一进程内有效；跨进程要靠文件锁
  先例: gitagent 的 per-file locks + 冲突时明确拒绝

B 设计:
  主要: 占用声明 + 等待队列 + 释放
  次要: 读写区分（共享读 / 独占写）、超时、死锁检测
  约束: 必须能取消；不能让一个死掉的 agent 永久占着锁
  工具: ctx.workingDirectory（已有 per-agent cwd）、ctx.subagents

C 接口:
  功能: 工具增加可选参数 "占用"（路径数组）；不填 = 当前工作区
        另加两个工具：转移工作区、查看谁占了什么
  暴露: 模型能看见"等待中，前面还有 2 个"
  待议: 锁的粒度（目录？文件？路径前缀？）

D 实现:
  好消息: **DSH 已经有 per-agent 工作目录**（ctx.workingDirectory.get(session)），
          所以"子工作区"的一半已经存在 —— 缺的是互斥和声明
  细节: 进程内 Map<pathPrefix, {owner, mode}>；等待用 Promise 队列
  魔数: 默认超时 10 分钟；超过则放弃并报告
```

**和 3.1 的关系**：两者共用一个"调度器"，一个是 agent 数量，一个是路径占用。建议同一个插件里实现。

## 3.3 ai 对话（多消息系统 / 狼人杀）

```yaml
A 问题:
  痛点: ai 没有记忆；多 ai 对话本质是"不同记忆系统分别请求"。现在看不见子 ai 的中间消息，也没法让它们互相看见
  验收: ① 一个工作区里能管理多条消息流；② 能看见子 ai 的消息（并发地看）；③ 至少能跑通最小狼人杀
  适用性: 强依赖 3.4（树/分支）；token 成本随人数线性涨
  先例: 讨论 #11894 里提过；维护者明确说"没有先例、不能证明必要性"

B 设计:
  主要: 每个 ai = 一条独立消息流 + 一个共享的公开频道
  次要: 发言顺序、私聊、旁观者视角
  约束: **不做真实验**，最小样例验证即可；并发查看不能拖慢对话流
  工具: ctx.subagents（已有）、ctx.agents、session 日志

C 接口:
  功能: 创建 N 个角色，每个有不同的系统提示/记忆；一个回合内按顺序发言
  暴露: UI 上能同时看到几条流（这和 4.1 侧边栏是同一个问题）
  待议: "看见"是实时流式还是回合结束刷新

D 实现:
  最小验证: 4 个角色 × 3 轮，用本地模型（若接上）或最短提示词
  度量: token 消耗、回合耗时、消息串扰情况
  魔数: 默认 4 角色；单轮发言上限 200 字
```

**为什么放最后**：它是 3.4 的下游，而且最贵。先把 3.4 的"分支 + 摘要"做出来，狼人杀才有地方跑。

## 3.4 树上下文工程

```yaml
A 问题:
  痛点: 线性消息记录会被无关细节淹没；切话题、开子目标时无法"回到分叉点继续"
  验收: 消息记录能分支；当前计划结束时产出摘要，回到分叉点接上，细节被隐藏
  适用性: 需要"能改消息记录组织方式"的前提，而维护者**已明确不打算重构 transcript**
  先例: 无。讨论 #11894 被回复"没有先例，需要证据"；#10473 是相关但不同的东西

B 设计:
  关键结论: **不要跟 transcript 死磕**。维护者反对重构，那就用现成机制拼:
    · 分支 = 会话 fork（DSH 已有 fork 语义）
    · 摘要 = 投影 + 注入（sessionProjections 服务已验证存在）
    · 回落 = 新会话以"摘要 + 引用"开头
  主要: 树结构存在 projection 里，不进消息记录本体
  次要: 连续失败检测、中断上报、Barrier 工具
  约束: 不修改既有 transcript；不引入不可回滚的状态
  工具: ctx.sessionProjections（树上下文插件的原方案就是这个）、fork

C 接口:
  功能: spawn（建子节点）/ settle（结算并回到父）/ report（看树）
  暴露: 模型只看见三个工具，看不见树本身
  待议: 节点结算后，父节点保留哪些内容（摘要？引用？都不留？）

D 实现:
  状态: projection（事件溯源，append-only），已有一版可用代码在
        C:\Users\16229\.dsh\profiles\node_modules\@tree-context（未启用）
  教训: 那份代码依赖 zod + schemastery + dsh-tools，放在 profile 外会 import 失败；
        要么给它自己的 node_modules，要么放回 profile
  魔数: 最大继承层数、每节点最大子节点数（原项目里都是 0 = 不限）
```

**要说服维护者的东西**（如果他们要看）：任务成功率、token 成本、父节点有多常需要被摘要丢掉的细节。这三项要能被测量，所以 3.4 的第一版就得埋点。
