# 05 带注释的工具调用

```yaml
A 问题:
  痛点: 用户说"你去调用一下，看看返回什么"时，想要的是**原始返回**，
        但模型会给总结；而原始内容在界面里默认折叠，一堆一模一样的调用卡片，
        根本分不清哪一个。
  验收: ① 调用能带一句话注释，界面上看得见；② 有一个动作能把某次调用"举起来"，
        在显眼的地方展开它的原始参数和原始返回。
  适用性: 只在有渲染界面时成立 —— 和截图工具是同一条边界。
  先例: 同类产品没有做；DSH 自己的 presentCall 存在但 Web 客户端不消费（已确认）。
```

---

## B 设计

分三层，从便宜到贵：

### 第一层：参数（最便宜）

给**我们自己的**工具加一个可选参数：

```yaml
note: 一句话说明这次调用在干什么，给用户看的
```

对内建工具（`read` / `pwsh` / `grep`）**改不了**——那是应用包里的东西。但有个半成品：
`pwsh` 已经有 `description` 字段（"Clear, concise description of what this command does"），
它本来就是干这个的。

### 第二层：渲染

客户端插件给我们的工具注册 `tool.call.toolview`：

- `note` 显示在卡片标题旁，而不是埋在参数 JSON 里；
- 原始返回**默认展开**，不折叠；
- 用主题变量，明暗都能看。

### 第三层：举起

一个 `pin_call` 工具 + 一块置顶区域（`shell.overlay` 或一个面板）：

- 调一次，就把指定调用的**原始参数 + 原始返回**贴在显眼处；
- 再调一次可以取消；
- 不修改消息记录，只是显示。

```yaml
B 约束:
  - 不修改内建工具的参数 schema（做不到，也不该做）
  - 不改写消息记录本身，置顶只是视图
  - 界面文本走 Client locale，不硬编码中文

B 可用工具:
  - Client 插槽: tool.call.toolview（按工具名 keyed）、shell.overlay
  - Host: ctx.tools.register、session 事件
```

---

## C 接口

| 动作 | 模型侧 | 用户侧 |
|---|---|---|
| 注释 | 工具参数里多一个 `note` | 卡片标题旁一行小字 |
| 举起 | `pin_call(note?)` | 顶上一块区域，展开原始内容 |

**最要紧的待议：怎么指认"指定的调用"？**

模型**看不到 callId**。三个方案：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（倾向）** | `pin_call` 作用于**紧邻的前一次调用** | 简单，语义清楚："把刚才那个举起来" |
| B | 按序号，"上数第 3 个" | 模型要数，容易错 |
| C | 模型把内容抄进参数 | 那就不是"原始"了，自相矛盾 |

选 A 还有一个好处：它天然对应人的说法——"你刚才那个，给我看看"。

**第二个待议**：`present` 要不要改造？

倾向**不改**。`present` 现在是"交付文件"，语义干净；把"展示调用"塞进去会让它变成两个东西。
新开一个 `pin_call` 更清楚。但如果你希望只有一个"交付"入口，那就合并，代价是 `present` 的参数要分叉。

## D 实现

```yaml
客户端:
  - 注册 tool.call.toolview 到我们自己的工具名，渲染 note + 展开结果
  - 置顶区用 shell.overlay（全窗口浮层，可点穿，加法式插入）
  - 数据来源: 客户端监听 session 事件里的 pin 记录

宿主侧:
  - pin_call 工具写一条 session 事件（append），内容 = 目标调用的定位信息 + note
  - "紧邻的前一次调用"怎么取: 需要在 execute 里拿到本次会话最近的工具调用记录

关键未知（要查）:
  1. 客户端插件能不能遍历 chat flow 里的其它节点？
     如果不能，"举起别人"就只能靠宿主把内容一起写进事件里
  2. 内建工具能不能被同名覆盖？（决定 note 能不能统一加在所有工具上）
```

### 如果第 1 条不成立，退路是什么

宿主侧在 `pin_call` 执行时，把**上一次调用的原始参数和结果**读出来（从 session 日志里），
连同 note 一起写进事件；客户端只负责渲染这条事件，不需要遍历 chat flow。

这条退路更笨，但**确定能成**——因为它不依赖客户端的可见性。
