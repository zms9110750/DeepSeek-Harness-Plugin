# 计划总览

一项需求一个目录。每项里按 A / B / C / D 分文件。

## 分层不是分类，是择备

**每一层都是上一层的一种择备。** 同一个父亲下的几个文件是兄弟，彼此并列：
采纳一份，其余的留着并写明"为什么不采用"。

    A-问题.md                        需求本身
      ├── B-01.md                    对 A 的一种设计理解（采纳）
      │     ├── C-01-01.md           对 B-01 的一种接口选择（采纳）
      │     │     ├── D-01-01-01.md  对 C-01-01 的一种实现（采纳）
      │     │     └── D-01-01-02.md  另一种实现（留档）
      │     └── C-01-02.md           另一种接口选择（留档）
      └── B-02.md                    对 A 的另一种设计理解（留档）

拆文件就是为了这个：兄弟必须能并肩存在。写在同一份里，"采纳的"会把"否决的"挤掉，
下一个人（或下一轮的我）就再也看不到那条路为什么走不通。

## 四层各写什么

**A —— 需求。** 用户想要什么。用用户的话说，不解释、不设计、不预判实现。

**B —— 设计。** 问题背后真正是什么；牵连着哪些东西；要不要顺带一起做；落在架构哪一层。

**C —— 接口。** 给使用者的感知层：UI 或 API。底层是黑箱，这里不管。
先谈体验：用户看到什么、点哪里、为什么这样最自然、能不能望文生义。

**D —— 实现。** 黑箱部分：怎么做到 C 说的那个效果。关键决定、踩过的坑、验证方式。

每一份文件都要交代**取舍**：为什么是它，不是别的。

## 贯穿所有项的约束

1. 不做烧 token 的真实验，一律最小样例。
2. 不用子 agent 做调研，自己读。
3. 先解源码再动手：`探针\asar\out\` 是全量解包，可随时重新生成。
4. 客户端插件改代码要换包名重装；宿主侧换名或重启。
5. 能离线验证的先离线验证：解析、计算类逻辑在 Node 里跑通，再搬进界面。
