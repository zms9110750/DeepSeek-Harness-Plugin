## A系列-问题

- 痛点/验收
  - **痛点**：`plan_dispatch` 名义上有两条执行路——`via: "self"`（默认，直接建子会话）和 `via: "team"`（交给 agent-team 插件，由它管名册、收件箱、收工通知）。self 路是文档里的默认，team 路要多一个插件在场。**两条路的差别没被实测过**：派出去不算通，收得回来才算。
  - 具体的失血点已经见过了：本分支（team 路派出来的子会话）继承的历史里，`plan_dispatch` 那次调用**只留下"开始调用"一条，结果字段是空的**——分支说明原文是「records this tool call starting but does not include its result」。也就是说，子会话**没法从自己的上下文里确认自己是被哪条路、用什么参数派出来的**。team 路的回传多经过插件一层（`spawn_teammate` 造人 → 插件收工通知），最容易坏的就是这一层：派得出去、收不回来，结算丢在插件里，树上看不到节点。
  - 验收：
    1. **两条路都能把一份计划派成子会话**，且派发十五项参数（plan / reason / workspace）在子会话侧可核。
    2. **两条路的子都按 `结算格式.md` 的六行收口**：verdict / conclusion / evidence / artifacts / pitfalls / where，缺一行就不算结算完成，节点留 open。
    3. **六行都进树**：`plan_tree` 能看到节点与 pitfalls，父用 `plan_file` 落五项；两条路的判定与计数规则一致（reject +1、shelved 不计）。
    4. **team 路额外一条**：本节点必须在工作区留下归档文件（就是本文件），使插件不在场时这段活仍可回查——不能只活在插件的收工通知里。
    5. **两条路的失败态可分辨**：self 路失败直接把错误回给派发方；team 路先在 `spawn_teammate` 处失败（provisioning / failed），再谈通知，两者不能混报成同一种失败。
- 适用性
  - 前提是 **agent-team 插件在场**（`spawn_teammate` 可用、名册里有 `lead` 与具名 teammate）。插件不在场时 `via: "team"` 无路可走，只剩 self 路。
  - 前提之二是 **宿主把"回传"当作独立一环**：子只放弃进程，父不重读过程（`结算格式.md` 第 60-63 行），所以回传必须落成一条能被父读到的东西。若哪天宿主把结算直连进父的上下文，team 路就没有独立价值了——两条路退化成同一个开关名，只剩标签不同。
  - **失去价值的情况**：若"归档"被理解为插件自己的持久化而非工作区里的文件，那么插件一卸载，team 路的全部痕迹消失，这条验收就作废。所以判据钉在文件上，不钉在插件状态上。
- 先例
  - **13-树上下文工程 B-02**：节点 = 一个真会话，计划提交那一刻 fork 出子会话，结算时把摘要作为一条消息追加回父，父只持有摘要。双路的 s/t 两岔共用这套 fork；差别只在"谁负责把子收回来"。
  - **19-A2A 调研**：A2A 的 `Task` 从 `message/send` 才开始存在，回传是 `TaskStatusUpdateEvent` 事件流；我们没有那层事件流，回传靠父**等一次**（本节点就是 `wait: true` 的那一次）。可抄的是它把"任务存在"与"结果可查"分开（`tasks/get`）：team 路也该有一个插件坏了也能查的落点，那个落点就是工作区里的归档文件。
