## 2.1 配备 MCP

```yaml
A 问题:
  痛点: 我的自定义工具一般是 MCP 服务，但 DSH 接不进来。已查证：只有 @deepseek-ai/dsh-mcp-resources（资源登记 + 三个共享工具），没有连接器，也没有官方 MCP bundle
  验收: 设置里能加一个 MCP 服务（JSON / 一行命令 / https 地址），列出工具数与 transport，能连能断
  适用性: stdio 要起子进程（沙箱问题！）；http 要出网（VPN 问题）
  先例: 参考图里的 Reasonix Studio「扩展 → 外部工具」；官方 TS SDK

B 设计:
  主要: 客户端插件（连 server、拉 tools/list、映射成 DSH 工具）
  次要: resources、prompts、sampling；连接失败的可读诊断
  约束: 不静默启动外部进程；工具数要有上限；连不上不能拖慢启动
  工具: @modelcontextprotocol/sdk

C 接口:
  功能: 设置项「扩展 / 外部工具」：粘贴 JSON 或命令 → 预览工具列表 → 保存并连接
  暴露: 工具命名建议 mcp__<server>__<tool>，避免撞名
  待议: 工具是否默认进 agent 工具表（还是像参考图那样"首次调用时启动"）

D 实现:
  骨架: 一个 host 插件 + 一个 client 插件（设置页）
  transport: stdio（spawn）与 http（streamable）
  难点: **spawn 受沙箱限制** —— 参考图那个产品的 stdio 服务能直接起子进程，我们这边要先解决沙箱
  魔数: 单 server 工具上限 128；启动超时 15s
```

**已确认的事实**：`@deepseek-ai/schemastery`、`@deepseek-ai/dsh-tools` 在 npm 上是公开的（都是 0.2.1-rc.2 这一代）。MCP SDK 是 Tier 1 官方维护。

## 2.2 按权限禁止工具（四描述符）

```yaml
A 问题:
  痛点: 现在工具权限是"全部放行 / 不放行"两态。MCP 协议里每个工具本来就有四个注解，却完全没用起来
  验收: UI 上每个工具四个开关（写 / 破坏 / 幂等 / 外部）；关了就在调用前拦截
         另有一个总闸：一开，连 read/list 都不许，用来质询 ai
  适用性: 只对声明了注解的工具有效；没声明注解的要有保守默认
  先例: MCP 规范的工具注解；参考图的「工具与权限：全部放行」总闸

B 设计:
  主要: 读注解 → 落到 DSH 的工具 guard → UI 四开关
  次要: 按 server 批量设置；审计记录；"为什么被拦"的可读理由
  约束: 拦截必须在 **tools/pre-execute** 阶段，不能等到执行后
        总闸打开时要能拦住"只读"工具，这是和普通 deny 列表不同的东西
  工具: ctx.tools.guard() / tools/pre-execute

C 接口:
  功能: 设置页每个工具四个开关 + 一个总闸
  暴露: 被拦时模型收到明确原因（"该工具被用户禁止：破坏性"），而不是通用错误
  待议: 注解缺失时默认值（建议：readOnly=false, destructive=true，即保守拒绝）

D 实现:
  数据: 每个工具的注解缓存到配置里，UI 可改
  细节: 总闸 = 在 pre-execute 里对所有调用返回 deny
  魔数: 无
```

**依赖**：没有 MCP 就没有注解可读，所以先做 2.1。但**也可以先做**——把内建工具也标上四个描述符，先用起来。

## 2.3 开 VPN（按调用走代理）

```yaml
A 问题:
  痛点: github、pixiv 需要梯子；但全局开会烧钱、会污染所有流量；关掉又影响我自己上网
  验收: 指定某些工具调用走代理，其余直连；不能是全局开关，不能碰用户的梯子状态
  适用性: 只对"我们发起的连接"有效；用户自己开不开全局是用户的事
  先例: clash-verge-mcp

B 设计:
  主要: 给需要出网的工具加一个代理参数，或按工具名配置路由表
  次要: 规则组选择、失败回退、连接诊断
  约束: 不得"开全局"；不得"关闭用户梯子"；拿不准就不走代理
  工具: Clash Verge 的 REST API

C 接口:
  功能: 工具参数 proxy: 'auto' | 'off' | 'group:<name>'
  暴露: 默认值来自配置；模型可以显式要求
  待议: "按域名分流"还是"按工具分流"（前者更接近 clash 的原生能力）

D 实现:
  关键事实: **新版 Clash Verge Rev 默认不在 TCP 上暴露控制器**，
           REST API 走命名管道 \\.\pipe\verge-mihomo，且必须手动开 External Controller
  两条实现路径:
    ① 进程级: 给子进程注入 HTTP_PROXY/HTTPS_PROXY（简单，但只对子进程有效）
    ② 请求级: 给 fetch 配 dispatcher/agent（精确，但要求所有出网都走我们的 fetch）
  难点: DSH 的 web_fetch 走的是内建服务，能不能按调用注入代理要验证
  魔数: 连接超时 10s；失败重试 1 次
```

**待查**：mihomo 的 `select` / `rule` API 能否做到"只让某条连接走某组"，而不是切整个模式。

## 修正：MCP 不要逐个映射成工具（读 Reasonix 源码后）

原方案（每个 MCP tool → 一个 DSH 工具）**是错的**。Reasonix 的做法正好相反：

```yaml
一个常驻代理工具: use_capability
  action: list    → 列出配置的 server（不启动进程）
  action: inspect → 列出已连接 server 的实时工具 / 没连上的给缓存 schema
  action: call    → 对某个 server 或它的某个工具发起调用
  action: decline → 拒绝
```

它明确写：**provider 可见的名字、描述、schema、顺序，在 MCP 清单变化时都不变。**

原因只有一个：**provider 前缀一变，KV 缓存全废**。装一个 server 就改一次工具表，
每次都要重新prefill，钱全烧在这。

我们如果按原方案做，会有同样的代价 —— 而且 DSH 的工具表还参与
`tools.restrict`（preset 的工具白名单），改表等于改限制。

### 改成这样

1. 注册**一个** `use_capability` 工具，参数是 `action` + `server` + `tool` + `args`；
2. MCP 的连接、schema 缓存、工具清单全部在宿主侧，不进模型可见的工具表；
3. **进程在批准之后才起**（Reasonix 也是这么做的），不是启动就连；
4. 每个 server 一个独立的授权身份（如 `mcp_connect__github`），可以精确禁止某一个。

### 一个额外的坑

`action: call` 的参数是"任意 JSON"，而 DSH 的工具参数 schema 是**强类型 DSL**。
要么用 `json` 类型（DSH 的 schema DSL 里有 author-only 的 `json`），要么把 args 编码成字符串。
这条要试一下哪种能被校验器接受。
