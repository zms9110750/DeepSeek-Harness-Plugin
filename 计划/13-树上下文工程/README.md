# 13-树上下文工程

- **状态**：设计中（方案已定：真分叉，逐字继承；未动代码）
- **一句话**：每个计划都是一次分叉，子节点带着逐字复制的前缀走自己的路，父只收摘要

## 折叠的两种做法

同一个动作：把一段消息换成一条摘要。区别只在谁决定边界、谁写摘要。

| 项 | 主动设锚 | 被动压缩 |
|---|---|---|
| 触发 | 节点结算（这段话题结束） | 上下文接近上限 |
| 边界 | 节点自己划，落在完整消息上 | 压缩器按位置切，不知道话题在哪结束 |
| 摘要作者 | 干这段活的那个会话 | 压缩后端 |
| 频率 | 每个节点一次 | 接近上限时一次 |
| 原文下落 | 该分支会话日志，按节点可查 | 会话日志，摘要后模型看不到 |
| 可回溯 | 按节点回查，能问到具体某一句 | 只能整段重放 |

### 结算摘要的必填项

格式的权威是 **`计划/结算格式.md`**（出口锚那份文件，和 `提案格式.md` 同级）：六行、五项必填、合格与不合格对照、谁来写谁去读，都在那里。这里只留一句判据——

> 后来的人拿着这五句能直接接着干，不需要再问一句"你当时到底怎么定的"。


## 定下来的三条

1. **每个计划都是一个分叉。** 分叉不是清空，是把此前记录逐字复制，子节点看得见分叉点之前的全部消息，如 git 分支。
2. **逐字复制是为了缓存。** 前缀只要有一字之差，从第一个 token 起就命中不了；兄弟分支前缀相同，才共享同一段缓存。
3. **分支冻结。** fork 只复制到那一刻（含端点）；父后改的主意不会自动传下去，变更只能靠发消息。
4. **树上只有派发过的。** 计划被写出来但用户没过、没有派发调用，就不存在节点；起草不占树（见 15）。

## 与 15 是同一个东西

- 13 的"树"就是 15 的"计划树"：同一批事件、同一棵树，不是两棵树。（0.17 起落成两个投影：`plans` 计划记录 + `nodes` 派发节点；读的是同一份日志。）
- 13 出机制：逐字分叉、结算摘要、树简报。
- 15 出语义：节点类型、层序、计数、闸门、锚点字段。
- 所以两者一起落地。不存在"先 13 后 15"的分界，也不存在只做一半能跑的状态。

## 已核实的产品机制

| 机制 | 能做到什么 | 出处 |
|---|---|---|
| 会话分叉 | 按事件序号逐字复制前缀成新会话，端点含在内 | `@deepseek-ai/dsh-api-session-controller` 的 `fork` / `atSeq` |
| Agent 句柄 | `followup` 派任务、`inject` 注入、`cancel` 中断、`whenIdle` 等停稳 | `@deepseek-ai/dsh-agent` |
| 子 agent | spawn 空白起步、fork 继承父级已完成轮次；父只收答复 | `@deepseek-ai/dsh-subagent-*` |
| 表层替换 | 整段区间换成摘要，模型看不到原文，日志仍保留 | `@deepseek-ai/dsh-session` 的 surface replace |
| 会话投影 | 插件记录并回放簿记状态，不进模型上下文 | `@deepseek-ai/dsh-session-projection` |

分叉用 `session.fork(atSeq)`，不用子 agent 的 fork 后端：后者只能切在已完成轮次的边界上，切点不精确，而且是"委派"语义，不适合"回头追问、重启同一节点"。
