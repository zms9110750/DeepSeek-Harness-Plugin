## B系列-设计（B-02）· 会话 fork，真分叉（采纳）

- 关键决定
  - **每一个计划都是一个分叉**。分叉不是清空，而是把此前记录**逐字复制**：子节点看得见分叉点之前的全部消息，正如 git 分支。
  - 这么做不只是为了"忠实"，也是为了缓存：前缀逐字相同，兄弟分支就共享同一段已缓存前缀，只有分叉点之后的部分才按新 token 计价。反过来，若拿"父写的一段摘要"当子节点的起点，等于把起点换成一段新文本，从第 0 个 token 起就无法命中——越省越贵。
  - 分支是冻结的：fork 只复制到分叉那一刻（端点含在内）。父后来改的主意不会自动出现在子分支里，要传达变更只能发消息。这既是 git 的规矩，也顺带杜绝了"分叉点漂移"。
- 主要目标
  - 节点 = 一个真会话。计划提交的那一刻 fork 出子会话，父停在原地继续和用户对话。
  - 结算时把摘要作为一条消息追加到父会话，父只持有摘要，看不见子的细节。
- 次要目标
  - 同一处分叉出的兄弟备选方案（B-01、B-02）前缀完全相同，缓存命中最大化。
  - 子会话可再入：结算后还能继续跑，还能被追问实现细节、被重启任务。
- 约束/许可/缺点
  - 成本：请求仍然要携带整段前缀，省下的是计价，不是长度。上下文窗口照旧被占用。
  - 会话数量随计划数增长，界面必须收拢成树，否则会话列表本身就被淹没。
  - 分叉粒度是事件序号，只能切在完整消息边界，不能切在一次工具调用的中间。
- 工具
  - `session.fork({ sessionId, atSeq })`：逐字复制前缀，子会话记录自己的继承来源。
  - `agent.followup / inject`：向子会话派任务、把摘要贴回父、追问、再入。
  - `agent.cancel`：中断、搁置。
  - 会话投影：记录树的形状、派发理由、结算理由。
- 结论：采纳。B-03 的"投影记形状"作为它的簿记层一并采纳，两者不是竞争关系。
