## A系列-问题

- 痛点/验收
  - **痛点**：会话是一条只追加的直线，没有“节点”。于是七件事都做不了——换话题后旧内容还在参与推理；找不到“上一件事到此为止”的界限；没有计划可供并发的几方对齐；派活只有“全给”和“什么都不给”，派一次磁盘就多一份完整前缀；上下文之间没有通道、没有公共板，用户只能当传声筒；失败只剩“失败”两个字，学不到东西；子 ai 干了什么看不到，也换不了。
  - 验收：
    1. **无关的段落不再参与推理**，但原文仍查得到。（换话题）
    2. **有锚点**：能指出“上一件事到此为止”那一行；入口说做什么，出口说结果。
    3. **有计划**：并发各方读到同一份计划与同一批写范围。
    4. **有分支点**：子会话带着当前前缀，磁盘不按人数翻倍。
    5. **有通道与公共板**：用户不必当传声筒，ai 能派出 ai。
    6. **有状态**：失败带着坑落库；同层连败到阈值转研究。
    7. **有可见性**：面板上点一个节点，回到那条会话。
- 适用性
  - 只要模型上下文有上限、会话会变长、一次任务会并发，这个需求就成立。三条现在都成立，所以不是锦上添花。
  - 失效条件：宿主自己长出话题折叠、树形派发、任务板和面板——那时这套只剩树库那一层还有意义。这也是所有机制都用宿主插件 API 接、不自建平行系统的原因。
- 先例
  - 宿主已经给了一半，不用重造：`agentTeams`（花名册、一对一投递、公共任务板）、`agents.create` + `buildForkSeed`（分叉与种子）、`sessionProjections`（给客户端的投影）、`plan-debug`（计划的纸面形状：`plan_write` / `plan_tree` / `plan_file`）。
  - 状态词汇有现成的：A2A 的 `TaskState` 九值，含终结态与中断态，语义不必自己发明。
  - 文档格式本身有先例：`计划/提案格式.md`、`计划/结算格式.md` 来自 ZMS.MCP 的 plan 目录。
  - 未查：外部产品（编辑器里的上下文压缩、子 agent 的上下文传递）没有单独调研，需要时另开 R 系列。
