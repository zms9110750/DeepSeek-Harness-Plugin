# 提案格式

<br/>以下介绍了一种提案的格式模板。
<br/>在实际写的时候，需要
<br/>
<br/>每一个层都是上面一层的具体实现。需要单独写一个文件。
<br/>在文件头需要描述提案状态：采用，搁置，否决，失败，完成，被取代。
<br/>描述来自于哪一个提案的具体提案。
<br/>提案可能是一个具体实现的"待议"，所以最上层提案也可能需要链接到某个提案。
<br/>一个提案可能需要多个方面组合，所以他们并行写出来的提案是配合性的。那么他们需要互相连接可用性。
<br/>一个提案下面可能有多个并发提案一起采纳和实现与进行。
<br/>每一个提案下面还可以有任意的研究提案，复盘提案。




## 通用的文件头

>- id: A-01
>- 标题: 转移话题时，无关上下文占用
>- 状态: 草案                    # 草案|评审中|采用|实现中|完成|搁置|否决|失败|被取代
>- 父提案:                       # 空 = 顶层；C 填 B-xx，D 填 C-xx-xx
>- 依赖: []                    # 我先要它完成
>- 被取代: []                    # 我取代了谁
>- 对接: []                    # 并行提案的接缝，双向声明
>- 交付物: []                    # 状态=完成 时必填


## A系列-用户问题

- 痛点/需求/验收
  - 用户需要这个，是出于一个什么问题，什么原因，什么使用场景。
  - > 房子想要大一点。蜡烛倒下的时候，烧的很快。
  - > 需要一个api解析jsonl
- 适用性
  - 如果长期搁置，出现了什么事情，这个提案将失去意义？即用户的使用场景如何产生必要性的。
  - >使用可燃物进行照明。
  - >jsonl被广泛使用
- 先例
  - 已有的同类产品长啥样，是否能抄。
  - >xx地区的富人区着火了以后，燃烧扩散的很慢，灭火很快
  - >xx库，其他语言的实现

## B系列-开发者设计

- 实际问题
  - 用户的这个问题，他表达的背后，实际痛点是什么。 
  - >生命财产安全。
  - >数据交互，有具体的格式要求。或者便于追加，和中间错的可以忽略。
- 需要考虑的问题
  - 用户不懂技术，但我们懂。我们要考虑。
  - >占地面积。承重能力。上楼费腿。
  - >根据接收方判断是否发送敏感数据。
  - >频繁的请求会导致网络流量，但他是幂等的，考虑使用缓存。
  - >这个东西需要持久化，并且需要完整性，需要循环缓冲池的写入或者具有事务性
- 非目标
  -  哪些问题完全由外部负责，或者由其他提案负责。这里不考虑。
  - >使用哪个缓存库。具体的持久化方式。
  - >服务器稳定性，传入错误，缺少内容的json
  - >本次是一期工程，只考虑属性，方法，静态公开的扩展。不考虑索引器。
  - >出于语义，仅序列化属性。不考虑字段。对字段的序列化后续讨论，可能使用明确特性，或是一个配置。
- 次要目标
  - 基于整个问题体系和实现框架，我们还可以附带交付什么。
  - >一个完整的mod接口
  - >查询引用和改名是同构的，所以根据符号改名也可以一起交付。
- 约束
  - 我们不得在什么情况下实现用户的问题。
  - >土地证需要钱。材料学不支持大房子。
  - >这是一个后台服务，不得占用太多性能
  - >部署对象是不可写的，必须在内存里做到一切事情。具体持久化公开一个接口给用户下载。并支持导入

- 工具
  - 有什么东西可以用
  - >合作的施工队。xx建筑学院可以咨询。
  - >我们自己有平台可以部署。
    
## C系列-接口/界面
- 目标
  - 基于实际目标和阶段性目标，和当前选择的次要目标，我们想做什么
  - >创建一个新的api，一个名字和几个重载，解析jsonl。
  - >创建一个导出和导入，可以把内存序列化为文本，通过下载接口给用户。并且可以导入回来。
- 暴露
  - 后来人没经过这个设计时，如何让他们理解这个东西怎么用的。在当前社会环境下，如何让用户望文生义。
  - >WASD移动，左键开火。
  - >在右键菜单加一个删除选项。
- 功能
  - 我们具体需要什么功能。这些功能在什么情况下产生什么行为。
  - >开火以后射出子弹。等待一个周期以后射出第二发。如果打到人就根据攻击力扣血
  - >如果是文件就移动到回收站。如果是文件夹就递归移动到回收站。如果太大了就问用户要不要永久删除。
  - >如果格式不正确或者参数为0，报错。如果没有更多数据，终止。
- 待议
  - 尚未决定的事项
  - >持久化放在用户文件夹还是程序文件夹。
  - >使用管道风格，还是把参数做成对象，还是把主要使用用可选参数一字排开
  - >请求以后本地筛选，还是把条件直接作为请求条件？后者需要考虑什么时候发送请求以规避429。

## D系列-实现
- 工具
  - 选择用什么包，什么技术进行实现。
  - >使用r3和消息总线配合，在开发期间在没有另一个模块时，不需要对方模块来进行测试。
- 细节
  - 封装的细节的要点。
  - >使用stringbuild拼接字符串，这里有大量循环。
- 魔数
  - 一拍脑袋决定的，可以推翻的实现细节。
  - >缓存上限128M，7天后过期。在程序启动后10秒进行缓存清理。

## F系列-复盘
- 为什么失败。我如何确信下一次可能不一样
- 我进行穷举，其根源是因为我不知道什么。如何正向找这个知识。
- 我现在不知道，我有什么猜测去作为已知事实去写研究
- 如果研究也无法得出结论，我应该去哪里知道我怎么知道
  - >论坛，官网的扩展内容页，mod发布平台可能有教怎么做这个。
  - >有一个别人做的可以工作的，进行改改，看改什么会改坏
  - >有人发布了这个成品。看看他的足迹，关注，历史记录。既然他会做，肯定看过教怎么做的。
