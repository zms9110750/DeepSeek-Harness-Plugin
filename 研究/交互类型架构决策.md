# 交互类型（union 槽位）架构决策

七条已由用户拍板。这里是**结论 + 理由**，实现时照此执行。

原文语境（用户原话）：

> 我说的不是模板。我说的是传参和解析可以允许 type 表示交互形态。所以一定允许 object
> ```
> {type=tab
> "选择"={ type=ask  }
> "排序"={type = sort}
> "调研" = { type = creat_link }
> }
> ```
> 这样就会制造一个选项卡。
> 所以，这里一定是传 object。自己带一个 type 的。

---

## 一、数据形状：独立文件

**决策**：交互数据**不内嵌正文**，存成独立文件。

**用户的理由**（原话）：

> 我希望他是独立的文件。因为他可以在这方面自己添加，组合。被扩展，被引入。

也就是说：这份数据要能被外部**添加**（加新块）、**组合**（拼装多处）、**扩展**（加字段）、**引入**（被别的数据引用）。
Markdown 正文里的 fenced JSON 做不到这些 —— 正文是给人读的交付物，不是可加工的结构。

**落地形态**：

```
~/.dsh/taskboard/
  plans.jsonl          事项本体（正文 + 元数据）
  interacts.jsonl      交互数据（每行：{taskId, node, ...}）
```

独立文件而不是塞进 plans.jsonl，因为：
- 交互数据体积大（可能有嵌套 items），不该拖累事项本体
- 外部包可以只读写自己那部分
- 事件溯源时，改交互不重写整条事项

---

## 二、未注册的 type：显示为灰色

**决策**：数据照存，UI 渲染成灰色只读卡片。

```
┌─────────────────────────────────┐
│ ⚠ 未注册的交互类型「sort」        │
│ {"items":["x","y"]}    [复制]    │
└─────────────────────────────────┘
```

用户原话：

> 显示为灰色的。合理。

**不丢弃**：外部包可能先装宿主半身、后装浏览器半身，窗口期里用户输入会丢。
**不报错**：别用部署状态否决内容。

---

## 三、校验：只校验「能不能看懂」

**决策**：不做字段 schema 校验，只判断**结构能不能读**。

用户原话：

> 为什么要校验？数据总是数据，总是一个 object。他只决定渲染。
> 他只需要能不能成功。只需要知道能不能看懂。

这是最反直觉但最重要的一条。想清楚了：

- 数据就是 object，没有“对不对”这回事
- `type` 只决定**渲染成什么**
- 所以只需要两个判断：
  1. **能不能解析** —— 是不是合法 JSON / 合法 object
  2. **能不能看懂** —— type 认不认识（不认识 → 灰色卡片，见第二条）

**不做的事**：
- ❌ 不校验 `sort` 的 items 是不是数组
- ❌ 不校验 `ask` 的 options 是不是字符串数组
- ❌ 不报“字段缺失”的错

**要做的**（最小防线，防的是坏数据不是坏字段）：

| 检查 | 目的 |
| --- | --- |
| 是合法 JSON | 否则读不出来 |
| 是 object（非 null / 非数组 / 非标量） | 否则没有 type |
| `type` 是字符串且非空 | 否则没法选渲染器 |
| 无 `__proto__` / `constructor` | 防原型污染注入 |
| 体积上限 | 防止一条数据撑爆文件 |

**渲染器自己负责健壮性**：拿到数据解析不了就渲染成“这条坏了”的卡片，不能让整个面板白屏。

---

## 四、选项卡：不允许递归

**决策**：容器**不能嵌套同类容器**。

用户原话：

> 不能。如果要套选项卡，就要写一个二级选项卡的 type。绝对不允许递归。

也就是说：

```
✓ tab → ask / sort / creat_link      （叶子）
✗ tab → tab                          （同类递归，禁止）
✓ tab2 → tab → ask                    （要套？另写一个 tab2 类型）
```

**这是个很聪明的约束**：递归会带来深度计算、渲染保护、schema 自引用一堆麻烦。
而“另写一个 tab2”把复杂度推给了**需要多级的那个人**，他自己承担，核心不用管。

---

## 五、值回传：走命令通道，必须保存全部选项

**决策**：用户交互的值走 `remote.commands`，不走文件写入。

用户原话：

> 走命令通道。提交的时候选项卡各选项都要保存。
> 并且要保存，哪一个选项是被选中的。
> 因为持久化本来就不能因为切选项卡把别的置空了。
> 但数据发给 ai 的时候，这里可以处理掉未选中的内容。

拆开是三件事：

### ① 通道：命令

```js
runCommand('/task-interact {"id":"DP-05","node":"n1b","value":...}')
```

和现有「新建事项」同构（`submitCreate` 就是这么干的），`recordInput: false` 压掉聊天留痕。

### ② 持久化：选项卡**所有**选项的值都存

**不能因为切到别的选项卡就把之前的置空。**

```json
{
  "n1": {
    "选择": { "value": "先做分组",  "selected": true  },
    "排序": { "value": ["分组","模板"], "selected": false },
    "调研": { "value": null,          "selected": false }
  }
}
```

`selected` 记哪个选项卡是激活的，切回来还是那一页。

### ③ 送给 AI 时：可以裁掉未选中的

用户原话：「但数据发给 ai 的时候，这里可以处理掉未选中的内容。」

也就是说：

- **存储**：全量，一个不丢
- **喂给模型**：只给选中的那部分（省 token，也更聚焦）

这两件事分开，因为服务对象不同 —— 存储要对用户负责（不能丢他填的东西），喂模型要对上下文负责（别把三页都塞进去）。

---

## 六、不存在“破坏性更新”

我原来的第 6 条问错了。用户纠正：

> 不懂。你是说破坏性更新吗？是加载注册信息变了，还是说 llm 用参数覆盖了模板？
> 重新提交？我说过采纳了就不能变，只能填写了。
> 既然只有填写变化，就说明一直处于交互许可里，没有破坏更新。

**关键前提**：**采纳（→提交）之后，交互声明就不能改了，只能填值。**

所以状态机是这样的：

```
草稿（未指定）     → 模型可以自由改声明、改正文
   ↓ 用户采纳
提交（已采纳）      → 声明冻结，只剩「填值」
   ↓
处理中 / 需要补充 / 需要授权  → 还是只能填值
```

结论：**声明变了只有一种可能 —— 还在草稿期，那用户也没开始填。**
所以不需要“两个字段防覆盖”那一套。声明和值可以放一起，因为它们的生命周期天然不重叠。

**要改声明 → 先“重开”回草稿（这是用户专属动作，现有实现已有）。**

### 由此推出的编辑规则（不要再问一遍）

| 字段 | 草稿期 | 已采纳 |
| --- | --- | --- |
| `options`（AI 提议的候选项） | AI 能改，用户也能改 | **冻结** |
| `picked`（选中的那个） | 一般还是空 | **只有用户能填，AI 不许** |

`picked` 永远是用户的字段 —— AI 可以提议选项，但**不能替用户选**。
所以不存在“AI 改了 options、把用户已选的踢掉”这种情况：采纳后 AI 根本改不了。

## 七、打包：一个包可以含多个 type

**决策**：按**功能域**分包，不按 type 分包。

用户原话：

> 一个包可以批量包含 type。比如核心库包含通用模板，也包含多个默认 type。
> 然后那个扩展的就包含他们的模板，和模板依赖的 type。
> 所以跨包依赖就一定要把 type 摘出来做公用引用。或者把别人的模板一起注册。

意思是：

```
@local/taskboard          核心：通用模板 + 默认 type（ask/sort/creat_link/tab）
@local/taskboard-painting 绘画扩展：绘画模板 + 绘画专用 type（如调色板选择器）
```

**不这样分**（一个 type 一个包）：

```
✗ @local/interact-ask
✗ @local/interact-sort
✗ @local/interact-derive
```

理由：装三个控件变成装六个包（每个都有宿主半身 + 浏览器半身）。

### 跨包依赖的两条路

用户提了两条，都对：

1. **把 type 摘出来做公用引用**
   扩展包不自己定义 `ask`，而是引用核心的。核心的 `ask` 改了，扩展自动跟上。

2. **把别人的模板一起注册**
   扩展包连模板带 type 一起注册，自成一体，不依赖核心的版本。

**选择标准**：这个 type 是“通用的”还是“我这份模板专用的”。
- 通用（ask/sort/tab）→ 公用引用，别复制
- 专用（绘画调色板）→ 自己定义，跟着包走

### 硬限制（踩过的坑）

`dsh-client-modules` 的 `exactPackageSpecifier` 只认**两段包名**：

```js
@local/interact-kit      ✅ 两段
@local/interact/kit      ❌ 三段，不认
```

所以外部包的包名必须是 `@scope/name` 形式，不能用子路径导出多个客户端入口。

## 完整链路

```
【1】模型创建事项（草稿期）
     task_submit({
       type: 'DP',
       body: '## 选择\n…',
       interacts: {
         type: 'tab',
         '选择': { type: 'ask', options: ['A','B'] },
         '排序': { type: 'sort', items: ['x','y'] },
         '调研': { type: 'creat_link' }
       }
     })
        ↓
【2】宿主：只查「能不能看懂」
     · 合法 object ✓
     · type 是字符串 ✓
     · 无 __proto__ ✓
     · 体积 OK ✓
     没有字段校验，没有 schema
        ↓
【3】落盘到独立文件
     ~/.dsh/taskboard/interacts.jsonl
     每行：{ taskId: 'DP-05', node: {...} }
        ↓
【4】用户采纳 → 声明冻结
        ↓
【5】客户端渲染
     · 读 interacts.jsonl
     · 查本机注册表：type 认识吗？
         不认识 → 灰色卡片（数据不动）
         认识   → 渲染
     · tab 容器：渲染成选项卡，全部选项都在 DOM 里
        ↓
【6】用户交互
     切选项卡 → 立即记住 selected（存内存）
     填值/排序 → 立即记住 value（存内存）
     点确认   → 一次性提交
        ↓
【7】提交（命令通道）
     runCommand('/task-interact {
       "id": "DP-05",
       "values": {
         "选择": {value: "A",    selected: true},
         "排序": {value: ["x","y"], selected: false},
         "调研": {value: null,    selected: false}
       }
     }')
        ↓
【8】宿主持久化：全量保存
     切选项卡不置空别的
        ↓
【9】喂给模型时裁剪
     只取 selected:true 的那个
     省 token，也聚焦
```

## 八、三块分工：行动库 / 模板 / 解析器

用户原话：

> 行动是行动。模板是模板。
> 模板描述怎么用，描述有什么章节。描述这个章节支持什么行动。
> 然后传参是对于章节传入行动的 object。然后解析器就去看了。

> 行动是一群架构的 object。模板是定义模板的 object。他们是正交关系。
> 章节里面写的是行动名（架构的某种唯一确定方式）
> 传参，这是你工具调用面方面的行为……他除了能校验以外就干涉不到什么了。
> 解析器，这个参数的 object 是完整的。解析器就看这个参数内容是什么，能不能把 object 转化为 html

三块**正交**：

```
① 行动库      name + JSON Schema + render 名      ← 定义「一个 object 该有哪几个字段」
                   ↑ 被引用
② 模板        body 里 type: [textarea, choose]     ← 只写行动名，不知道字段
                   ↑ 被校验
③ 传参        工具面按章节的 type 取 schema 校验    ← 过不了就拒绝，计划不进任务板
                   ↓
④ 解析器      按 action 查 render，转成 HTML        ← 只看 object 自己
```

### 关键规则

**行动只能用 JSON Schema 描述。** 用户原话：

> 因为行动是什么。他就是描述你这个 object 要有什么字段。
> 这要描述只能是架构来描述啊。

所以不要写 `validateChoose(obj)` 这种行动专属校验函数 —— 规则会和 schema 重复，迟早不一致。
只有一个通用的 `validate(schema, value)`。

**章节的 `type` 接受 `string | string[]`。** 所以 27 个模板**不用改**：

```yaml
type: textarea              # 单个（现有全部是这种）
type: [textarea, choose]    # 多个，这一章可以用其中任意一种
```

**校验在持久化之前。** 用户原话：

> 架构校验不能过，直接拒绝这个计划提案。工具返回就是报错的。
> 校验过了，才上任务板。然后解析器工作。

两类错误要分清：

| 情况 | 时机 | 处理 |
| --- | --- | --- |
| 架构校验不过 | **持久化前** | 拒绝整个提案，工具返回错误 |
| UI 没有渲染器 | 渲染时 | 灰色卡片 + 原始 JSON |

### 正文不再是 Markdown

用户原话：

> 不存 md 了。你存 md 你还要走 md 解析器。那你解析器不是白做了？
> 要 md 就把文本框直接走 md 的解析器。

所以：

```
存 object 数组，按章节 id 索引：
body: {
  want: { action: 'textarea', value: '用户要什么' },
  how:  { action: 'choose', options: ['A','B'], picked: 'A' },
}
```

Markdown 只是**某个 action 的载荷**（`value` 的内容），不是正文的格式。
`parseSections`（按 `## ` 切字符串）整个不需要了。

**老数据不迁移**（用户明确说了）。测试期数据无所谓，正式用时手写。
