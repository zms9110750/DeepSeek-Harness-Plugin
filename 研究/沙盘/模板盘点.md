# 现有模板盘点：哪些章节适合加行为

模板库只有 **4 个**（在 `packages/core/templates/`）：

| 文件 | 名字 | 默认类别 | domain |
| --- | --- | --- | --- |
| `GU.yml` | GU · 用户任务 | goal 目标 | general |
| `DP.yml` | DP · 方案 | design 设计 | general |
| `RR.yml` | RR · 汇报 | record 记录 | general |
| `WI.yml` | WI · 实现 | work 工作 | code |

（没有小说、绘画领域的模板，domain 只有 `general` 和 `code`。）

---

## 全部 22 个章节

### GU · 用户任务（5 章）

| # | id | 标签 | 现在类型 | 内容是什么 |
| --- | --- | --- | --- | --- |
| 1 | — | （无 id） | `markdown` | 「这一份只写用户要什么、什么算做到了」 |

**22 个章节里 19 个是 `textarea`**，2 个是 `markdown`（GU 的开场白），
2 个已经用了 `derive`（GU 的 `split`、DP 的 `plan`）。

## 适合加行为的章节

按「这个章节的内容，是不是从一组有限选项里挑」来判断。

### 🟢 强烈适合（内容本身就是选择）

#### 1. `WI.change` —— 改动清单 → `rank` 或 `ask`

现在：一段自由文本，让 AI 一行一个列文件路径。

问题：**它是清单，但读的人要自己数、自己对**。「改了几个文件」
「哪些是代码、哪些是配置」全靠阅读。

适合的行为：
- `rank` —— 如果改动有先后依赖（先改 schema 再改渲染器）
- `ask` + max_picks —— 如果想让**用户勾选「先合哪几个」**

#### 2. `RR.limits` —— 不确定的地方 → `ask`

现在：一段自由文本。

问题：模板自己写着「这一节写“无”通常代表谎报」。**这是它知道内容有固定形态却没建模。**

适合的行为：`ask`，选项固定为：

```
1. 全部验证过（写这句要能说出验证方式）
2. 部分推测（说明哪部分）
3. 关键部分没验证（说明风险）
```

选 1 就必须在别处给出验证方式，选 3 就该进「需要补充」。

#### 3. `DP.risk` —— 什么情况下方案会错 → `multi`（多选）

现在：一段自由文本。

「该放弃这个方案的条件」——这是**条件清单**，天然是多个。

适合的行为：`ask` + `max_picks: 99`，选项是常见失败模式：

```
· 依赖的外部接口变了
· 数据量超出预估
· 有人不同意这个取舍
· 工期超了
```

### 🟡 值得考虑（内容部分可选）

#### 4. `GU.bounds` —— 边界 → `multi`

「明确不做什么」可能是多项。但边界往往是自由叙述，收窄成选项会丢信息。

**建议**：保留 textarea，但**加一个 `ask` 章节「硬边界」**，专门勾选几条不可逾越的（比如「不能改数据库」「不能动线上」）。

#### 5. `DP.cost` —— 代价 → `ask`

代价的形态比较固定（改什么 / 破坏什么 / 多久 / 谁维护），
但现在模板要求「必须写」这些内容，**靠提示词约束**。

可以拆成四个小 `text`，或者一个 `ask` 问「代价等级」+ textarea 写细节。

#### 6. `RR.conclusion` —— 结论 → `ask`

结论可以收窄成：

```
1. 做成了
2. 没做成（见依据）
3. 做成了但要重新考虑
```

但会丢信息——真实的结论很少这么干净。**建议不改**。

#### 7. `WI.magic` —— 拍脑袋定的东西 → `list`

现在：一段自由文本，列出阈值、超时、缓存上限这些「不是深思熟虑的结果」。

这章的价值很高——它把「哪些是我蒙的」标出来，以后可以推翻。
但用 textarea 写，读者要自己挑出每一项。

适合的行为：`list`（一行一项），或者 `ask` + 多选常见种类：

```
· 阈值（超时、重试次数、并发数）
· 容量（缓存上限、批量大小）
· 命名
· 默认值
```

### 🔴 不该加（内容本质是自由文本）

| 章节 | 为什么 |
| --- | --- |
| `GU.want` | **用户原话**，加选项就是改写用户的话，违反模板自己的规则 |
| `GU.done` | 判据可以任意多，且必须能验证，选项化会漏 |
| `DP.problem` | 复述问题，自由文本 |
| `DP.plan` | 方案细节，必须自由 |
| `DP.alternative` | 「至少一个」的论证，自由 |
| `RR.evidence` | 证据是链接和输出，自由 |
| `RR.deliver` | 产物描述，自由 |
| `WI.goal` | 验收标准，自由 |
| `WI.verify` | 命令和输出，自由 |
| 所有 `other` | **它存在的意义就是装不下** |

## 一个更根本的观察

**模板现在基本只用 `textarea`，不是因为它够用，是因为行为库里的选择太少。**

现在的行为：

```
text       一段可编辑文本
markdown   只读富文本
ask        从选项里挑
rank       排先后
derive     派生子任务
```

22 个章节里 19 个用 `textarea`，说明**缺的不是「给哪些章节加行为」，而是缺行为本身**。

### 缺的行为（从这 22 章里反推）

| 缺什么 | 哪些章节需要 |
| --- | --- |
| **列表**（一行一项，可增删） | `WI.change` 改动清单、`DP.cost` 代价项 |
| **文件路径引用**（能点开、能校验存在） | `WI.change`、`RR.evidence` |
| **勾选清单**（多选 + 每项有说明） | `DP.risk`、`GU.bounds` |
| **时间/工期** | `DP.cost` |
| **状态选择** | 每个模板的隐含字段 |

**这些都不是「换个现有行为」，是需要新行为。**

---

## 我建议的顺序

**先做这三章的行为升级**（成本低、收益明显）：

1. `RR.limits` → `ask`（三个选项，逼 AI 说清验证程度）
2. `DP.risk` → `ask` + 多选（常见失败模式清单）
3. `WI.change` → `rank`（改动有先后顺序时）

**然后考虑加新行为**：

4. `list` 行为（一行一项，可增删）—— `WI.change`、`DP.cost` 都用得上
5. `check` 行为（多选 + 每项可带说明）—— `DP.risk`、`GU.bounds`

**不要动的**：`GU.want`（用户原话）、所有 `other`（兜底）。
