# 消息持久化：内置实现、可替代性与替代方案

调查对象：`dsh 0.2.1-rc.2`（`app.asar\package.json`），profile `desktop`。
方法：只读（本会话 `pwsh` 仍不可用）。证据 = 随包 README + 随包构建产物 `lib/index.js` + 活体
`cordis_inspect_query`（Service / Event），另用解包副本 `探针\asar\out\dsh\` 做 grep 复核。

---

## 0. 一句话

**消息持久化 = 事件溯源日志 + 一个可替换的 `sessionPersistence` 服务 + 默认 JSONL 后端；
真正的落盘发生在"后端插件自己监听 `session/event`"里，不在服务方法里。**
所以：装饰器替代不了；监听只能看不能拦；"只存我要的"在 seam 层没有开关；
SQLite 能当第二个 provider 但不适合顶替默认后端；而要省分叉前缀，只有"自己当 provider 或
做 provider 门面"一条路。

---

## 1. 真实链路（从 append 到磁盘）

```
session.append(type,data)                    ← 内存：校验 + 冻结 + 分配 seq
   ├─ session/event  (emit, post-commit)     ← 后端的唯一输入
   │     └─ writers.get(session.id)?.enqueueLive(event)   ← 查表；查不到就丢弃
   │           └─ 200ms 批窗 → drain → handle.append(batch) → zstd 帧 + fsync
   ├─ session/flush  (parallel, awaited)     ← 持久化屏障：drainLive() + handle.flush()
   └─ session/disposed                       ← 最后排空 + close
```

证据：
- `dsh-session/README.md:28,100` — 日志是唯一记录，模型历史由它派生。
- `dsh-session-persistence-jsonl/lib/index.js:421-424` — 路由只认 `writers.get(session.id)`。
- 同上 `:190-193` — 批窗 = `setTimeout(..., 200)`（不是保证，只是写合并；`flush` 才是屏障）。
- 同上 `:426-433` / `:434-440` — `session/flush`、`session/disposed` 的收尾。
- `dsh-session-persistence/README.md:57` — **"A published session without an active write handle
  persists nothing."**（静默丢弃，不报错）
- 落盘形态：`~/.dsh/sessions/--<归一化 cwd>--/<sessionId>/session.v4.jsonl.zstd`，
  一批一帧、每帧 fsync、懒物化、torn-tail 只剩完整记录、跨进程单写（flock / 命名信号量）。
  `dsh-session-persistence-jsonl/README.md:57-77,168`

推论（对 plan 18 很重要）：
1. 想"让原版不写"只需让它没有写句柄 → 可行。
2. 想让"你的文件被原版读" → 不成立：原版只按自己的目录/格式找。
3. 落盘不是"每次 append 立刻写"，`append` 只保证进入后端缓冲；**唯一可依赖的 durable 点
   是 flush**（`session/flush` 或 `handle.flush()`）。plan-events 里"<500ms 落盘"测到的就是
   200ms 批窗，属实现细节，别写进契约。
4. 未知事件类型不加 `ignorable: true`，整份日志会被拒（plan-events 的两次事故即此）。

## 2. 接口（更正 `18/A-问题.md:16`）

现文写的 `create / append / list / load / remove` 不对。活体契约（`Service.listService
{service:"sessionPersistence"}`）：

```ts
create(header, { signal?, inheritedEventCount? }): Promise<SessionHandle>  // 拿写所有权
open(id, 'read' | 'write', { signal? }): Promise<SessionHandle>            // read 不夺权
stat(id, { signal? }): Promise<Snapshot | undefined>                       // 不读日志
list({ signal? }): Promise<readonly Snapshot[]>                            // 无分页无过滤
flush(): Promise<void>                                                     // 全服务屏障

interface SessionHandle {
  id; header; inheritedEventCount; access
  read(offset?, length?, { signal? }): Promise<{ eventState, events }>
  append(events, { signal? }): Promise<void>       // 只收连续批，首 seq 必须等于 next-seq
  flush({ signal? }): Promise<void>
  close(): Promise<void>                           // 幂等、不可取消
}
```

要点：
- **没有 `remove` / 没有保留策略**：`dsh-session-persistence/README.md:153`（"pruning … out-of-band"）。
- **没有按 id 的 append / load**：只能经 handle（`README.md:49`）。
- `create` 已经接受 `inheritedEventCount`，`SessionHeader.isSeeded` / `Session.inheritedEventCount`
  本来就有 → "前缀共享只需改存储"在语义层成立（`A-问题.md:17` 这条判断是对的）。
- 只有"拿到写句柄"的会话才落盘；生产环境里拿句柄的是 **agent-loop**（`README.md:28,152`）。

## 3. 五种方案逐条裁决

| 方案 | 能不能 | 代价 / 卡点 |
|---|---|---|
| ① 换 provider（composition 里把 `session-persistence-jsonl` 那行换掉） | 能，官方明说第三方可实现 | 一次性承担全部契约：连续 seq、flush 屏障、torn tail、fail-closed 校验、单写、懒物化、格式代际迁移、`shared-frozen`、reload 语义；**且现有 JSONL 历史默认读不了**，除非先导入。一个 bug = 全部会话打不开 |
| ② 运行中包实例方法（`session-fork-bridge2` 的招） | 对 `create/open` 能拦住 | 但**不足以接管落盘**：原版监听器只查自己的 `writers` 表 → 你换句柄它就不写（正好，禁写成功），可你也必须自己监听 `session/event`、自己实现 `list/stat/open('read')`，否则 UI / sessionQuery / resume 都看不见这些会话。实际是"门面 provider"，不是"create 分流点" |
| ③ 只加关系、不碰事件（`18/B-01`） | 能 | 不省磁盘（B-01:13 自己写了）。但它是唯一"卸载即回归原状"的方案 |
| ④ 装饰器 | **不能** | 见 §4 |
| ⑤ 旁路监听 / 旁路 SQLite | 能 | 只能镜像，不能省原版那份；好处是零风险 |

结论：**"改存储以省前缀"和"依赖原版"互斥**。B-02 的真名是"自写 provider 并做门面"，
不是"建会话时判一下"。若只为省磁盘，代价见 ①；B-01 判定不值——从契约看这个判定是站得住的。

另一个硬点：一旦你自写 provider，`session-query-sqlite` 会跟着换（它只认 seam），但它要求
`snapshot.revision` **必须是字符串**，且"相等 = 未变"（`dsh-session-query-sqlite/lib/index.js:1015,721`）。
你的 provider 必须自己守这两条，否则搜索索引静默陈旧或直接抛错。

## 4. 装饰器

DSH / Cordis 里的装饰器都不是"横切钩子"，是**声明期元数据**：

- `@Remote('list')`（typert）——把宿主方法登记成客户端可调用的 remote。服务目录里到处是这种签名。
- `@messageProjection` + `ctx.sessions.registerMessageProjection()` —— 声明"这类事件会改消息内容"，
  由 Session 在 append/恢复时调用（`dsh-session/README.md:54`）。**它改的是消息派生，不是落盘。**
- Cordis 的服务注册走构造函数 `super(ctx, name)`（`cordis/src/service.ts:42-58`），没有
  `@Injectable` / `@Service` 式装饰器。

所以：方法装饰器最多把某个方法包一层（= 方案 ②，还得自己管恢复顺序）；它给不了
按会话路由、批窗、fsync 屏障、单写锁、格式代际。**持久化的单位是"一批连续事件 + seq"，
不是一次方法调用**——形状不对，装饰器替代不了。

## 5. 监听：能做什么、不能做什么

用到的就四个事件（活体 Event 目录）：

| 事件 | 模式 | 语义 |
|---|---|---|
| `session/created` | emit | 会话发布 |
| `session/event` | emit | **post-commit、fire-and-forget**，每个已接受事件一次 |
| `session/flush` | parallel | **awaited**，都跑完才返回；唯一 durability 观察点 |
| `session/disposed` | emit | 会话离开 store；最后排空 |

能：镜像进自己的库、做侧索引、计数、审计、给别的会话投递消息（plan-events 已经这么干）。
不能：否决/改写已提交事件（**没有 append 的 waterfall**，只有 `agent/pre-step`、`tools/*` 那些）；
阻止原版写；看到未提交事件。
坑：listener 抛错只 warn（`README.md:57`）；构造器种子事件不发 `session/event`
（`README.md:104`）；顺序 = 提交顺序。

非会话数据（树关系、书签、索引）另有 `storageDomain`：`domain/changed` 在写 durability 之后
发一次（`dsh-storage-domain/README.md:73,90`）。**不要**把这类数据塞进会话日志。

## 6. 只持久化"我要的"

seam 的粒度是**会话**，不是事件：没有事件级过滤器，没有"只存 user/assistant、不存 tool/*"。
拿到写句柄 → 该会话所有事件都进日志。可用的杠杆只有三个：

1. **控制谁拿句柄**（agent-loop 是生产获取点；要拦就是方案 ②/①）。
2. **自己的结构化数据走 `appendPluginRecord`**：进日志、标 `ignorable`、随 resume/fork 走、
   不进模型上下文（`dsh-session/README.md:70-76`；plan-events 已在用）。
   注意：官方把它限定给 `packages/experimental/`，外部插件"不应调用"——运行时能用，版本演进
   时有风险。
3. **旁路筛**：`session/event` 里过滤后写自己的 SQLite / domain。原版那份照样全量，
   所以这是"再存一份"，不是"只存一份"。

另外：**没有删除/保留 API**，compaction 是"遮蔽"不是删除（`dsh-session/README.md:161`）。
所以"先全存、回头清理成只留我要的"这条路不存在。

## 7. SQLite

三件事分开看：

**(a) 官方已经在用 SQLite 做索引。** `dsh-session-query-sqlite`：FTS5 虚表 `persisted_docs`
（`text` + `session_id/seq/type/time/surface`）+ STRICT 表 `persisted_sessions`，`user_version=8`，
按 `persistence.list()` 的 revision 增量重建（`lib/index.js:106,117,763-786`）。
它是**派生、可丢弃**的；消息正文已经在那里。要"能用 SQL 查的消息库"，**先查它，别自建**。

**(b) 当旁路库（C-01-01 现状）：最稳。** `node:sqlite` 内置（本机实测可用，无需装包）。
注意 C-01-01:38 的自问自答是对的：库在 host 侧，客户端拿不到 → 要么走
`sessionProjections` 摊出去，要么开只读 remote。

**(c) 当 provider：契约上可行，工程上不建议顶替。**
- 容易：append-only 行、事务天然没有 torn tail、WAL+`synchronous=FULL` 满足 flush 屏障、
  rowid/`data_version` 当 revision、懒物化、单进程单写。
- 难：跨进程单写（seam 明说"provider-specific"，`README.md:150`）；**既有 JSONL 根目录的导入/
  迁移**（provider 必须把历史格式转成当前再给 handle，`README.md:67`）；`SessionLocation`
  诊断（"一个文件"失去"打开哪个文件"的定位）；reload 语义；revision 是字符串且"相等=未变"。
- 还有生态耦合：`session-log-export` 导出条目按 JSONL 文件名命名（`README.md:60`），
  换 provider 后导出会名不副实。

## 8. 顺带：「mod」如果指 Claude Code mods 桥

`claudeCodeMods`（`@deepseek-ai/dsh-experimental-claude-code-mods`）是**实验性桥**，本 profile
没有装载（193 条目里没有它）。它的能力上限，与持久化相关的只有：
- 8 个 hook 点：`session.start/end`、`prompt.submit`、`turn.start/complete`、`tool.call`、
  `command.run`、`ui.render`；`session.append` 在"注册但永不触发"名单里。
- 能看到的只有 `turn.complete`（答案 + usage）和 `tool.call`，**看不到逐条消息**（它自己也是
  靠 `session/event` 折 `turn/start|assistant/message|turn/end`）。
- **不写日志**：hook 返回的 `{text}` 只进 `logger.info`；`$.session.append/send/repo` 一律
  `no implementation`。
- 自己的耐久存储只有一个 4MB 上限的 domain KV（`$.store`）。
- 一个反证很关键：`tool.call` 改参数被显式拒绝（`RewriteRefusedError`），理由是"这次调用已经
  记账了"——**日志是权威，hooks 不许回改**。

所以：**mod 桥替代不了持久化，连拦截都做不到；它只能观察 turn 级事实 + 存自己的小 KV。**

## 9. 对 plan 18 的四条修正

1. `A-问题.md:16` 的接口写成 `create/open/stat/list/flush + handle`，`remove` 不存在。
2. `B-02` 的"分流点只在建会话那一刻"低估了：还要包 `open('read'|'write')`、`list`、`stat`，
   否则冷读、UI、搜索都看不见；本质是门面 provider。
3. "只加关系"（B-01）与"改存储"（B-02）不是同一量级的改法；B-01 的否决理由（B-01:18-19）
   与契约一致，可以保留。
4. 树关系、计划记录、索引 → 走 `storageDomain` / `node:sqlite`；要进日志就
   `appendPluginRecord`；**不要**试图从日志里"只挑一部分存"。
