# 部分替代：三种粒度、审计结论、推荐路径

问题：能不能只对我的东西做自定义持久化缓存，我的东西加载出来之后走他的消息管理？
结论：**能。但"部分替代"的正确切口是数据级（记录/投影/缓存），不是会话级（provider）。**

---

## 1. 三种"部分"

| 粒度 | 能不能 | 机制 | 代价/风险 |
|---|---|---|---|
| **事件级**（只存某几类消息） | **不能** | 无过滤器：后端按会话路由 `session/event`，拿到写句柄的会话全量落盘 | — |
| **数据级**（我的数据有自己的存储） | **能，官方现成** | `appendPluginRecord`（进日志，ignorable）/ `ctx.sessionProjections.register`（加载时重建）/ `dsh-session-projection-cache`（持久检查点，冷读零 I/O）/ `ctx.storageDomain`（独立 KV） | 低。日志仍是权威，消息管线完全不动 |
| **会话级**（我的会话不进原版） | **能，但要门面** | 包活实例的 `create/open/stat/list/flush` + 自己监听三个事件 | 中高。见 §3 审计 |

---

## 2. 数据级：官方三件套（你说的那句话正是这个模型）

**(a) 记录进日志** — `appendPluginRecord(session, 'plugin:<owner>/<name>', data)`
- 写一条 `ignorable: true` 的事件，随 resume / fork / 迁移走；不认得的构建跳过它。
- runtime 不校验包名（只在官方仓库有 lint 门），但官方口径是"只给 experimental 包用"。
- 读回：`pluginRecordOf(event)`，或投影里直接看 `event.type`。

**(b) 加载时重建** — `ctx.sessionProjections.register(definition)`
```js
{
  key, stateVersion, stateSchema,
  init(header, inheritedEventCount) -> state,     // 必须用这个 cut，不许反推
  apply(state, event) -> state,                   // 同步、纯、无关事件返回原引用
  wire?: { viewSchema, view }                     // 给客户端的视图
}
```
- 重启后第一次读时从日志折叠（`session/event` 驱动，惰性建 cell）。
- `snapshot(session)` → `{asOfSeq, values}`，一个一致切面。

**(c) 持久缓存** — `dsh-session-projection-cache`（**本 profile 已装**）
- 每个注册单元自动 checkpoint，写点：会话创建（种子 cut）、`turn/end`、会话销毁，外加
  `writeEveryEvents` / `writeIntervalMs` 节流；失败 fail-soft，下次自愈。
- 读面：`cachedSnapshot(header)` 零 I/O（按 `formatVersion/createdAt/cwd/isSeeded` 认身份）；
  `coldSnapshot(header, inheritedEventCount, events)` 从检查点前缀续折；
  `hydratePrepared(session, events)` 不额外读盘就把 cell 灌好。
- **日志领先，缓存只落后不超前**；记录按会话存，无淘汰。
- 语义：你的值被 *seed* 进投影，之后活会话的事件照常驱动它 —— 消息仍是 surface / deriveMessages 在管。

**"不走日志"的变体**：自己的 sqlite/domain 当缓存，加载时 hydrate（`agent/created` 或首次读），
日志里只留一条 pointer record。要求：缓存必须可重建、且不超前于日志。

## 3. 会话级门面：审计结论

**可行性：改活实例的方法 = 可行；换服务值 = 不可行。**
- Cordis 每次 `ctx.sessionPersistence.x` 都重新解析属性描述符；`SessionPersistence` 不是
  `createCallable` 服务，注册的就是裸实例。Typert/remote 每次派发都 `Reflect.get` 取方法。
- 全仓**没有**消费者解构方法；只有 `dsh-acp` 在装载时存了服务对象（不是方法），改实例方法仍生效。
- `ctx.set('sessionPersistence', wrapper)` 只有提供者 fiber 能做，而且**不会**让
  `ctx.inject` 的依赖者重绑（session-query / sqlite / acp / translator 会拿旧对象）→ 不要换值。
- 安全做法：从 `svc[Symbol.for('cordis.original')]` 拿裸对象，`Object.defineProperty` 覆盖方法，
  `ctx.effect` 里还原；保留 `identity` 同一个 Symbol。

**三条会静默丢东西的红线**

1. **`list()` 是唯一的"哪些会话存在"的预言机。** 藏起来的会话会从：侧边栏、会话搜索、
   @提及候选、ACP `session/list`、工作区成员/固定/归档/挂载、ZIP 导出（含 descendants）里消失，
   **不报错**；而且检索库会把这些 id 的 FTS 行**删掉**、bump `global_generation`、作废游标。
   还会踩两个硬断言：两次连续 `list()` 必须一致（否则整体搜索失败），
   header 必须与活会话一致（否则 `SESSION_QUERY_SOURCE_CONFLICT` 全局抛）。
2. **`stat()` 必须对我拥有的 id 都答**：subagent 重名守卫、message-feedback、projections 冷读、
   translator、ACP resume 都靠它。
3. **写入根本不走服务方法**：第三方 append（feedback / translator / schedule ack）只经
   `session/event` 投递。不自己监听 `session/event`/`flush`/`disposed`，这些事件**无提示丢失**，
   并且 `ctx.sessions.flush()` 返回 false → `message-feedback` 与 `schedule` 直接抛错。

**没有更细的官方缝**：`agents.setFactory` 是单槽且被 agent-loop 占着；`agentLoop.resumeWith`
只内部用；`ctx.isolate('sessionPersistence')` 只影响该 isolate 内的消费者，而 agent-loop 从
`this.runtime.ctx` 取持久化 → 拦不到。

---

## 4. 推荐（按顺序）

1. **把"我的东西"写成投影单元**，数据用 `appendPluginRecord` 进日志。
   本 profile 已有 projection-cache → 白得冷读缓存，零额外代码。
2. 若数据量/结构不适合进日志：**自己的 sqlite 当缓存**，加载时 hydrate；日志只留 pointer。
   保持"日志领先、缓存可重建"。
3. **只有**当"我的会话"必须不复制前缀（磁盘/大量 fork）时，才做会话级门面；范围限定为
   自己创建并登记的会话，且必须：`list()` 合并、`stat/open` 答全、自己接三个事件、
   保留 identity、revision 用稳定字符串。
4. 不做全量 provider 替换（上一轮结论）。

---

## 5. 一句话

**"加载出来就走他的消息管理"是官方支持的形状 —— 你的状态是投影，你的缓存是投影检查点；
消息从头到尾都归他。会话级门面不是"更彻底的部分替代"，而是"把写路径从我这儿挪走"，
它换来的是磁盘，付出的是全局可见性与事件路由。**
