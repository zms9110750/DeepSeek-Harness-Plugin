## 1. 九态够不够

**判断：待议（不改九态，但要补两个「派生标签」+ 一个 `waiting_on` 字段）。**

九态本身是 A2A 的标准集，够表达「生命周期」。真正缺的不是**状态**，是**状态里的信息**，现在有三处表达不了：

1. **「被前置阻塞」被塞进了「提交」**。`claimBlocker()` 会在领取时检查依赖/父/派生源，但计划本身**在库里始终显示「提交」**。也就是说「已采纳、可以马上领」和「等着 T-003 完成才能领」在列表、科技树、`task_list` 输出里长得一模一样。这是实打实的信息丢失——人看不出这张为什么没人做。同理，父计划不是「处理中」时子计划也显示「提交」，但根本领不了。
2. **「等待外部事件（不是等人）」**。H6（资源被占用）只是**模板**，不是状态：`type=H6` 不会让任何代码分支变化（README 明说 H 系列不参与逻辑）。所以「等 CI 跑完」「等另一个 agent 释放文件锁」只能落在「需要授权」里，而它其实不需要用户授权。用户看到「需要授权」会以为自己被要求做事，实际不是。
3. **「部分完成」**没有表达。一张计划做了 3/5 个交付点，只能靠正文自己写，状态仍是「处理中」；停下来就「需要补充」，可它不缺信息。

不建议加第十态（会破坏「九态来自 A2A」这个已经写进 README 和系统提示的约定，而且所有级联/分组/面板都按 `GROUP_OF` 推导，加状态要改三处）。建议**用派生字段**解决，不动状态机。

### 计划草稿（要）

**标题**：给「提交」加阻塞派生标签 + `waiting_on` 字段，区分「可领」与「等前置」

- **目标**：现在「提交」同时表示「可以马上做」和「在等别人」，人和模型都分不出来。真实库里 15 张有 1 张长期「处理中」、13 张完成，剩下一张草稿——一旦并行会话多起来，这个歧义会立刻变成误判（模型反复 `task_claim` 同一张不该领的）。
- **功能**：
  1. 新增只读派生字段 `blocked`（由 `claimBlocker()` 的检查结果出来，不落盘）：`{blocked: true, reasons:['依赖 T-003 未完成（当前「处理中」）']}`。
  2. `/tasks` 与 `task_list` 输出里带 `blocked` / `blockedBy`；面板卡片上画一个小锁图标，详情层显示具体原因。
  3. 新增可选字段 `waiting_on`（自由文本，≤200 字，`task_note` 同级可改，进 `HEAD_FIELDS`）：写「等 CI #123」「等 subai-beta 释放 X 锁」。配 H6 模板的「被谁占着」一节。
  4. `task_state` 进「需要授权」时如果 `type` 是 H6 且 `waiting_on` 为空，给一句警告（不拒绝）。
- **待议**：`blocked` 是实时算（要扫全库，10 万张会慢）还是落盘缓存？建议先实时算，`task_list` 已扫全库，边际成本为 0。`waiting_on` 与 `note` 是否重复——倾向不合并，`note` 是给人看的理由，`waiting_on` 是给脚本/调度器判断的机器字段。

## 2. 缺什么工具

**判断：要。**

模型侧 8 个工具、面板 10 条命令，覆盖面是「读一张 / 写一张 / 改状态 / 改备注」。缺口按痛感排序：

| 缺口 | 现状 | 后果 |
| --- | --- | --- |
| **按条件查** | `task_list` 无参数，永远返回全库 | 33 张时输出 1152 字符还好；几百张时模型每一步都要为「找那 3 张能领的」付全量 token |
| **删除 / 清理** | 没有任何删除路径 | 草稿（未指定）永久堆积，`T-00x` 编号只增不减；真实库 15 张里 13 张已完成，随历史只增 |
| **给已采纳计划补链接** | `task_update` 硬性只允许「未指定」 | 做完一张才发现还要依赖另一张，只能 `fork` 一份新的，产生重复计划 |
| **批量改状态** | 一次一张 | 父计划失败后想手工收 5 张子计划，要 5 次调用 + 5 次级联扫描 |
| **历史 / 时间线** | 无 | 见第 5 条 |
| **导出 / 导入** | 无 | README 说「备份只搬一个文件」，但没有工具能做，也没有校验 |

### 计划草稿（要 · 第一优先）

**标题**：`task_query`：按状态 / 父 / 依赖 / 领取者过滤，并支持分页

- **目标**：`task_list` 全量输出在计划数上三位数时会让每一步都变贵；同时模型缺一个「只看能领的」入口（现在只能自己从全量里筛，容易漏掉 `blocked` 的）。
- **功能**：
  1. `task_query({ status?, group?, parent?, claimedBy?, type?, blocked?, limit?, offset? })`，全可空；`group` 取 `进行/搁置/完成/草稿`（复用 `hasGroup`，注意「需要补充/需要授权」同时在两组的语义要保留）。
  2. 返回 `{ total, rows:[summarize 行], nextOffset }`；默认 `limit=50`。
  3. 面板顶栏加一个状态筛选条（多选 chip），复用同一份过滤逻辑在客户端做（`/tasks` 已经给了全量头，客户端筛不花往返）。
  4. `task_list` 保留，但正文加一句「计划 > 50 张时请用 task_query」。
- **待议**：过滤应该在宿主做还是客户端做？头数据不大，客户端做能省往返，但模型的 `task_query` 必须在宿主做。两处实现要共用一份判据（可以只让宿主做，面板也走 `task_query`）。

**标题**：`task_delete`（只删草稿与终态，硬删需二次确认）

- **目标**：现在计划只增不减，草稿和「取消/拒绝」的历史会永久占位并污染科技树。
- **功能**：
  1. `task_delete({ id, confirm? })`：`未指定` 可直接删；`完成/失败/取消/拒绝` 要求 `confirm:true` 且**没有存活的子计划/依赖方**（否则拒绝并列出阻碍）。
  2. 落盘为 `{"op":"delete","id":...}` 事件（JSONL 折叠时删 key），**不物理删行**——保留审计痕迹。
  3. 面板详情层加「删除」按钮，仅对草稿显示；终态的「删除」藏在编辑菜单里。
- **待议**：删除后 id 是否复用？建议**不复用**（`createNewInner` 取 max+1，删了也不回填），否则历史事件里的 `依赖:T-005` 会指向另一张计划。

**标题**：`task_link`：给已采纳计划增删「依赖 / 来源」链接（受审计）

- **目标**：已采纳计划完全不可改（`updateTaskInner` 只放行「未指定」），连补一个漏写的依赖都要 fork，制造重复。
- **功能**：
  1. `task_link({ id, add?, remove? })`，只允许 `依赖:` / `来源:` / `对接:` 三类；`派生:` / `取代:` 仍禁止（它们会触发级联，必须走新计划）。
  2. 只允许在 `提交` / `处理中` / 搁置态改；终态拒绝。改动写进事件并带 `actor`（见第 5 条）。
  3. 加链接时校验目标存在、不成环（见第 9 条的 cycle 漏洞）。
- **待议**：这等于给「已采纳不可改」开了一个有人看守的口子，和 README 现有承诺冲突，需要你拍板：是开这个口子，还是把「补依赖」也当成必须 fork 的操作。

## 3. 缺什么视图

**判断：要（过滤 + 只看我的 + 依赖反查）；时间线放第 5 条一起做；「按状态分区」用线性列表就够，不要另做一套泳道。**

面板现在只有两个视图：科技树（dagre LR）与详情层。`DetailPane` 里已经有「父 / 子 / 指向 / 被指向」四行，**依赖反查其实已有雏形**（`inLinks`），缺的是能点进去之前的**全局**反查。

具体缺：

1. **状态过滤**：`/tasks` 返回的 `groups` 字段面板拿到了但**只用来给圆点上色**，没有当过滤用。真实库里 15 张有 13 张完成——科技树上 87% 的节点是噪音。
2. **只看我的**：`/tasks` **已经返回了 `claimed_by`**（已确认字段存在），面板**完全没用**。而「我现在在做哪张」是「按计划」档下最常问的问题。
3. **时间线**：见第 5 条，不做重复设计。
4. **已完成计划的收纳**：`DEFAULT_COLLAPSED` 是拿**样例数据** `SAMPLE_TASKS` 算出来的常量，接上真实数据后根本没用上——现在没有任何折叠逻辑，也没有 `展开全部/收起全部` 的按钮（文案 `board.expandAll` / `board.collapseAll` / `board.list` / `board.off` 都注册了，**一条都没被引用**）。

### 计划草稿（要）

**标题**：面板加「状态筛选条 + 只看我的 + 已完成折叠」

- **目标**：100 张计划时科技树有 9.5 屏高（实测，见第 8 条），其中绝大多数是已完成的历史；没有过滤等于面板不可用。而「只看我的」所需的数据（`claimed_by`）已经在传输里了，纯前端就能做。
- **功能**：
  1. 顶栏加筛选区：状态多选 chip（默认全选，视觉上「完成」半灰）、「只看我的」开关（按 `claimed_by === sessionId` 过滤）、关键词输入（标题/正文首行）。
  2. 过滤只作用在**渲染层**，不动 `data.tasks`，所以科技树布局用完整数据集算、过滤后用透明度/隐藏表达——否则每次过滤 dagre 都要重排，布局会跳。
  3. 「已完成折叠」：`完成/失败/取消/拒绝` 且**无存活子计划**的节点默认收进一个「已完成 N 张」的折叠块，点开才进图。
  4. 把 `board.expandAll` / `board.collapseAll` 接到新逻辑上（或删掉文案，别再挂着不用）。
- **待议**：过滤后是隐藏节点还是变灰？隐藏更干净但会断掉依赖链的视觉连续性；建议**变灰 + 连线保留**，点击灰节点仍能看详情。

**标题**：依赖反查视图（`task_query reverse=依赖:我`）

- **目标**：`DetailPane` 的「被指向」只对当前这张计划有效；「谁在等我」要逐个点开看，没法回答「我一旦失败会带走谁」——而这正是 `cascadeClose` 的破坏半径。
- **功能**：
  1. `task_query({ reverseOf: 'T-003', label: '依赖' })` 返回所有 `links` 里写 `依赖:T-003` 的计划（复用 `linkPairs`）。
  2. 详情层在「关系」里加一行「威胁半径」：直接/间接会被我级联取消的计划数，点开跳到新视图。
  3. 面板在选中节点时高亮整片下游（沿 `cascadeClose` 的 BFS 路径染色）。
- **待议**：这个视图和科技树的高亮是否算重复？如果科技树的 hover 已经能高亮上下游（现在只高亮**相邻**一条边），也可以不做独立视图，只做高亮范围扩展。

## 4. 并发与锁

**判断：要（有真实可复现的竞态）。**

`withWrite` 是**进程内**的 Promise 链，只包住了 `setState` / `updateTask` / `setNote` / `createNew`。**`task_claim` 的读改写不在锁里**（`task_claim` 里先 `readTask`、后 `saveTask`，中间没有 `withWrite`）。`task_claim` 的 `activeClaimOf` 也在锁外。

已复现（临时库，两个并发 Promise）：

| 场景 | 结果 |
| --- | --- |
| 同一张「提交」计划，两个会话并发 `task_claim` | **两个都成功**；`claimed_by` 最后是第二个；**两个会话的守卫都放行**（同一份权限，不是并集，但两个会话在做同一张活，会互相覆盖产物） |
| **同一个会话**并发领两张不同的计划 | **两个都成功** → 库里出现两张 `claimed_by` 相同、状态都「处理中」的计划，**「一次只做一个」的不变式被打破** |
| 同一张计划两个会话并发 `task_state` | 一次「失败」、一次「完成」，最终落「完成」（后写覆盖，前写无痕） |
| 同一张计划并发 30 次 `task_submit`（新建） | 30/30 唯一，**这条没坏**（`createNew` 在 `withWrite` 里） |

另外还有三处结构性风险：

- **没有跨进程锁**。DSH 重启后 `refreshClaims` 会重建 `CLAIM_CACHE`，但两个 DSH 实例（GUI + headless）同时开着时，两边各自 `appendFile` 同一个 JSONL。Windows 上单次 `appendFile` 一行（<4 KB）通常是原子的，但 `task_claim` 的读-改-写会互相覆盖（都是 `upsert` 整条）。
- **`upsert` 整条覆盖 = 丢失更新**。A 读到 `{status:提交}`，B 读到 `{status:提交}`，A 写「处理中」，B 写「完成」——A 的领取消失，且 `claimed_by` 是 B 的空值。没有版本号/`if` 条件。
- **`applySupersede` 在 `withWrite` 内又调 `cascadeClose`**（其内部 `saveTask` 不再进锁），这类「重入不锁」的写法目前靠注释说明（「再进一次会自锁」），容易在后续改动里被踩。

### 计划草稿（要 · 第一优先）

**标题**：领取与改状态走同一把锁 + 乐观版本号（消除双领 / 会话双开 / 丢更新）

- **目标**：已复现「两个会话同时领到同一张」「同一会话同时领到两张」；在「按计划」档下这意味着两个会话同时按同一份权限写同一片工作区，产物互相覆盖。跨进程多实例还会丢更新。
- **功能**：
  1. `task_claim` / `planClaims.claim` / `task_state` 的**读-改-写整体**塞进 `withWrite`（与 `setState` 共用同一条链，或抽一个 `mutate(id, fn)`）。
  2. 计划记录加内部字段 `rev`（整数，每次 `saveTask` +1）；`saveTask` 接受 `expectRev`，不等则抛「已被改动，重读再试」。
  3. 「一次只做一个」的检查改为**在锁内**执行 `activeClaimOf` + 写入，成为 CAS。
  4. 单实例之外：`~/.dsh/taskboard/plans.jsonl.lock`（`open(..., 'wx')` 带 pid/时间戳 + 超时回收），所有写路径先拿锁；或退一步——`plans.jsonl` 改名 `plans-<pid>.jsonl` 分实例写、读时合并，**明确不支持**跨实例的领取互斥（写进 README）。
- **待议**：锁文件在 Windows 上进程崩溃会留残锁，需要 stale 超时（建议 30 s + pid 存活检查）。`rev` 是否暴露给面板？建议不暴露，只在工具内部用。

## 5. 可观测性

**判断：要。**

JSONL **结构上**是 append-only 事件流，但每个事件只有 `{"op":"upsert","task":{…}}`——**没有时间戳、没有 actor、没有 from→to**。也就是说：

- 历史**被覆盖在整条 task 快照里**：想知道「T-007 什么时候从提交变处理中」，只能把相邻两条 `upsert` 的 `status` 字段做 diff，**而且没有时间**。
- 谁改的完全不知道：`task_state` 不记 `agent.id`（只有 `claimed_by`，而且离开「处理中」就清空）。
- 现在真实库 64 行事件 / 15 张计划，其中 49 行是同一批计划的整条重写，**没有任何一行能回答「谁在什么时候做了什么」**。
- 面板不展示历史；`task_get` 也不返回历史。

### 计划草稿（要）

**标题**：事件补 `ts / actor / from / op`，并提供 `task_history` + 面板时间线

- **目标**：状态变化无历史 = 无法复盘「为什么这张停在需要授权三天」、无法回答「谁把它拒了」、也无法做第 6 条的压缩（压缩要先能识别「哪些是历史、哪些是当前」）。这是所有可观测性功能的地基。
- **功能**：
  1. 事件形状扩展（**只加不删**，旧事件仍能读）：`{"op":"upsert","ts":<ISO 或 epoch ms>,"actor":"<sessionId|user>","from":"<旧状态>","to":"<新状态>","task":{…}}`；`task_note` / `task_update` 落 `fields:['note']` 这类变更清单。
  2. `task_history({ id, limit? })` → `[{ts, actor, from, to, fields}]`；`/task-history <id>` 命令给面板。
  3. 面板详情层加「时间线」一节：状态流转按时间列出（谁、什么时候、从什么到什么），折叠在底部。
  4. 时间戳在**宿主侧**写（`Date.now()`），不要在客户端补——客户端补的时钟不可信。
- **待议**：`actor` 在 `task_state` 里现在是拿得到的（`exec.agent`），但 `setState` 的签名只传了 `agent` 用于「一次一个」检查；要不要区分「模型改」和「面板命令改」（`byUser` 已有）？建议 `actor` 写 `session:<id>` 或 `user`，别混。历史里存不存被改掉的正文？建议不存（体积），只存字段名 + 值 hash，需要正文靠「同 id 相邻 upsert 的 body diff」现算。

## 6. 体积

**判断：要（但现在还不急，先做第 5 条的时间戳，压缩才有依据）。**

实测数据：

- 真实库：**163 KB / 64 行 / 15 张计划**，正文总 15 124 字符，平均 1 008 字符/张，最长 1 647。
- 一次状态变化 = **整条计划重写**（含 body）。在临时库上对一张 1.5 KB 正文的计划做 50 次状态往复：**91 438 字节**。也就是 **约 1.8 KB / 次转状态**。
- 推算：50 张计划 × 平均 100 次状态变化 ≈ **9 MB**；500 次 ≈ **45 MB**。`task_list` 每次要把整个文件读进来折叠——**读放大 = 文件大小 × 调用次数**，模型每一步都在付。
- 现在几十行没问题；三个月后是几十 MB，`task_list` 每次几十 ms→几百 ms，面板每次 `files.read(limit:5000)` 也是全文件。

### 计划草稿（要）

**标题**：JSONL 滚动压缩：超过阈值写一行 baseline 快照，保留最近 N 条

- **目标**：`upsert` 整条重写导致体积 = 正文 × 转状态次数，线性膨胀且无上界；`readStore` 每次全文件折叠，随体积线性变慢。
- **功能**：
  1. 新增 `{"op":"snapshot","ts":…,"tasks":[…]}`：一行装下**全部当前状态**。
  2. 触发条件（任一）：文件 > 2 MB、行数 > 2 000、或距上次压缩 > 7 天；压缩在**写路径里顺手做**（`withWrite` 内，压缩后 `rename` 原子替换，写 `.bak` 一份）。
  3. 压缩规则：`snapshot` + 最近 200 条事件（保留最近历史，供第 5 条的时间线）；更早的历史**归档**到 `plans.history.<yyyy-mm>.jsonl`，不删。
  4. `readStore` 支持 `snapshot`（遇到就重置 map）。
- **待议**：压缩时要不要按 id 去重 body（相同 body 只存一次 + 引用）？收益在「同一张计划转 50 次状态」的极端情况下很大，但会让格式变复杂，建议**先不做**。是否要在 `task_list` 里做「按 mtime 缓存折叠结果」？这是另一个正交优化，见第 9 条。

## 7. 权限漏洞

**判断：要（本报告最严重的部分，5 条已复现）。**

先给复现摘要（全部在临时库 + 桩 ctx 上跑，`sessionProjections.stateOf()` 返回 `{preset:'plan'}`）：

| # | 场景 | 结果 | 代码位置 |
| --- | --- | --- | --- |
| 1 | **模型自建 `permission=完全权限`、`workspace=C:\` 的计划，再 `task_state` 直接置「处理中」** | 守卫放行写 `C:\Windows\System32\x.dll`；`planClaims.effective` 返回 `完全权限` | `task_state` 不校验「未指定 → 处理中」是否经过采纳（`setStateInner` 只拦 `→提交`，不拦 `→处理中`） |
| 2 | **陈旧 claim 快取**：会话先领「完全权限」计划，再用 `task_state` 换成「工具全关」计划 | 守卫**仍按旧 claim 放行**（写任意路径成功） | `task_state` 工具路径**不更新 `CLAIMS`**，只有 `/task-state` 命令路径更新（index.js:1121–1129 vs 976） |
| 3 | 计划完成/被取代后，原会话的 `CLAIMS` 条目仍在 | 守卫继续放行（实测 `完成` 之后同会话写仍 ALLOWED） | `cascadeClose` / `applySupersede` / `setState` 都不 `CLAIMS.delete`；`refreshClaims` 只重建 `CLAIM_CACHE`，`resolveClaim` 先查 `CLAIMS` |
| 4 | 「仅可查看」计划下调用 **不在 `WRITE_TOOLS` 里但会写盘**的工具：`plugin_manager` / `apply_patch` / `subagent` / `mcp__fs__write_file` | **全部放行** | 守卫是**黑名单**（`WRITE_TOOLS`），只认 5 个名字；未知工具一律当只读 |
| 5 | 「工作区内修改」下 `pwsh` 命令里**只要出现允许目录字符串**就放行 | `Remove-Item C:\Windows\...; echo X:\temp\dsh\probeE` → **ALLOWED** | index.js:322–325 用 `lowered.includes(entry)` |
| 6 | 任意会话可以改**别人正在做**的计划状态（含完成、改「处理中」抢走） | `/task-state T-001 完成` 由入侵者会话执行 → success | `setState` 没有「只有 `claimed_by` 的会话能改」校验 |

另外两处没到「绕过」但同属权限面：

- `planClaims.release(sessionId)` 只按 `claimed_by` 找，谁都能替别人 release（需要知道对方 sessionId，风险较低）。
- `resolveClaim` 的回落已删（README 明确说删了、测试也覆盖了），**这点是好的**，不用回退。
- `_无主处理中_`（`claimed_by` 空）现在被拒，正确。

**这 6 条里 #1 和 #4 是「权限档形同虚设」级别**：#1 让模型能给自己发完全权限（只需 `task_submit` + `task_state`，都不受计划权限约束）；#4 让「仅可查看/工具全关」挡不住任何非内置工具，而 MCP（文件系统类）恰恰是现在最常用的一类。

### 计划草稿（要 · 第一优先）

**标题**：按计划档的守卫改为白名单 + claim 只能由「用户采纳」路径产生

- **目标**：当前守卫用黑名单 `WRITE_TOOLS`（5 个名字），任何新工具（MCP、plugin_manager、apply_patch、subagent）默认放行；同时模型可以用 `task_submit` + `task_state` 给自己造一份「完全权限」计划，绕过「采纳只能由用户做」这条硬规则。两条合起来等于「按计划」档可以被自助提权。
- **功能**：
  1. **`task_state` 禁止 `未指定 → 处理中`、禁止 `未指定 → 完成/失败/取消/拒绝`**：`处理中` 只能由 `task_claim` / `planClaims.claim` 产生（这两条都要求状态是「提交」），`未指定` 只能由 `/task-approve`、`/task-reject` 离开。这样「未采纳的计划」永远进不了 `CLAIMS`，也就拿不到权限。
  2. **`task_submit` / `task_update` 不接受 `permission=完全权限` 时来自模型的写入**（或者：模型提交的计划 `permission` 最高只能到「工作区内修改」，`完全权限` 必须用户面板改）。`task_submit` 的 `description` 里写明这一点。
  3. **守卫改成白名单**：定义 `READ_ONLY_TOOLS`（read/grep/glob/read_image/…）+ `WRITE_TOOLS`，**不在任何清单里的工具在「按计划」档下一律拒绝**（报错文案给「这是未登记工具，按失败即关处理」）。MCP 工具按前缀 `mcp__*` 归入「需显式登记」。
  4. **`pwsh` / `bash` 的命令子串判据删掉**：改为要求命令里出现允许目录且**不含** `;`、`&`、`|`、`>`、`$(…)` 等串接符号（宁可误拒），或直接要求 `cwd` 参数落在允许目录内、命令本身不解析路径。
  5. `CLAIMS` 的更新收到 `setStateInner` / `task_claim` / `applySupersede` / `cascadeClose` 的**唯一出口**：任何状态离开「处理中」都 `CLAIMS.delete(sessionId)`；并在 `resolveClaim` 里做一次**存储校验**（内存命中的 claim 必须仍能在库里找到 `status=处理中 && claimed_by=自己`，否则视为无 claim，失败即关）。
  6. 归属校验：`setState` 对「非用户路径」要求 `task.claimed_by === agent.id`，否则拒（管理类工具 `byUser=true` 的 `/task-state` 例外，那是用户操作）。
- **待议**：第 2 条会和「子 AI 自己提交计划再自己做」这种用法冲突（现在的 `planClaims` 就是给自管 AI 的）。需要你定：**模型提交的计划要不要能写「完全权限」**？我的倾向是**不能**，需要完全权限就由用户在面板里改。第 5 条的「每次守卫都读一次库」会慢，可以缓存 500 ms。

**标题**：`CLAIMS` 与存储的单一事实来源（消除陈旧快取）

- **目标**：已复现「用工具切任务后守卫仍在用旧 claim」，根因是 `task_state` 工具路径不写 `CLAIMS`、离开「处理中」不清 `CLAIMS`。
- **功能**：删掉 `CLAIMS` 这份进程内快取（或改成只做 250 ms 的读缓存，key 为 sessionId，值为 `{id, rev, checkedAt}`），`resolveClaim` 一律走 `readStore()` + `claimed_by` 匹配；`refreshClaims` / `CLAIM_CACHE` 一并删除（它们本来就是 `resolveClaim` 的第二数据源，而两数据源必然漂移）。
- **待议**：每次工具调用都读一次 JSONL 会不会太慢？当前文件 163 KB，读+折叠 < 5 ms，可以接受；文件长大以后由第 6 条的 snapshot 把体积压住。

## 8. 面板可用性

**判断：要。**

实测 dagre LR 布局尺寸（`NODE_W=168, NODE_H=52, nodesep=14, ranksep=46`，视口 336 px 高、面板宽约 1 274 px）：

| 计划数 | 布局 | 视口倍数（高） | 备注 |
| --- | --- | --- | --- |
| 10（二叉） | 818 × 324 | 1.0 | 现在这样，刚好 |
| 30 | 1 032 × 984 | **2.9** | 要滚 |
| 60 | 1 246 × 1 941 | **5.8** | |
| 100 | 1 460 × 3 195 | **9.5** | 横向也开始超出 |
| 200 | 1 674 × 6 495 | **19.3** | |
| 100（全平铺、无父子） | 176 × 6 594 | **19.6** | 一条竖线，最糟 |

问题不在「10 张就满」——10 张是 1.0 屏，没问题；**真正的拐点是 30 张**（近 3 屏），100 张时已经不可用。而真实库现在 15 张、其中 13 张完成：一旦历史不折叠，**3 个月就到 60 张**。

另外几个具体缺陷：

1. **没有缩放/平移**：`TechTree` 是固定 `height: 336` 的 `overflow:auto` 容器，只能滚，不能 zoom-to-fit。
2. **没有折叠**：`DEFAULT_COLLAPSED` 用样例数据算出来的常量，接上真实数据后**完全没被引用**；`board.expandAll` / `board.collapseAll` 文案也**没被引用**。
3. **`STORE_FILE` / `TEMPLATE_DIR` 是硬编码绝对路径**（`C:\Users\16229\.dsh\taskboard\plans.jsonl`、`X:\temp\dsh\开发\taskboard\templates`）。换机器、换用户、换盘符立刻坏；而且面板靠 `remote.workspaceFiles.read` 读**工作区外**的这两个路径，本来就没保证。
4. **数据只加载一次**：`load()` 在 `[load]` 上跑，`load` 依赖 `[sessionId]`——**只有首次挂载和点「刷新」会拉**。模型在后台改了状态，面板不会知道（没有轮询、没有事件订阅）。
5. **详情层不显示 `claimed_by`**：谁在做这张看不到（数据在 `/tasks` 里）。
6. **`SAMPLE_TASKS` 兜底**：读不到库时显示**样例数据**并标「样例数据」——这在演示时是优点，在真实使用里会让人误以为有 15 张不存在的计划。
7. **面板宽度 `min(600px, 100%)` 的详情层压住标题栏**（代码注释自认），窄屏时筛选区会被盖。

### 计划草稿（要）

**标题**：科技树支持 zoom-to-fit + 折叠 + 分组过滤，并在 30 张以上自动切换视图

- **目标**：实测 30 张就要滚 3 屏、100 张 9.5 屏；没有缩放和折叠时，面板在真实使用量下（3 个月 ~60 张）就退化成一张只能摸瞎滚的大图。
- **功能**：
  1. **fit-to-view**：初始 `scale = min(1, 视口宽/图宽, 视口高/图高)` 并把缩放中心放在**选中节点**（没有选中就顶层第一个）；滚轮 + 拖拽平移，右上角「适应」按钮复位。
  2. **折叠**：以 `parent` 为轴的树折叠（现在 `TechTree` 是纯图，没有层级概念）；折叠节点显示 `+N` 角标。
  3. **自动切视图**：> 30 张时默认「分组列表」（按 `groupLabel` 分三段，每段内按 id），图上只留「进行」组；科技树保留为可切换的视图。
  4. **路径参数化**：`STORE_FILE` / `TEMPLATE_DIR` 从宿主拿（加一条 `/task-paths` 命令返回两个绝对路径，或让 `/tasks` 的响应带上 `store` 字段），客户端不要硬编码。
  5. **轻量轮询**：面板打开期间每 3 s 拉一次 `/tasks`（或订阅宿主事件）；变化时**只更新数据、不重排**（用 `rev` 判断）。
  6. 详情层加「正在做」一行（`claimed_by`），以及「上次变化」时间（依赖第 5 条）。
- **待议**：dagre 每次重排是同步的，60 张时 ~10 ms，可以接受；200 张要移到 Web Worker 或做增量布局。轮询 3 s 会不会太吵？可以做「窗口聚焦时才轮询」。

## 9. 我自己想到的

### 9.1 状态机没有转移表（要）

`setStateInner` 只校验「状态名合法」，**不校验转移是否合法**。已复现：

- `完成 → 处理中`（终态复活，直接违反 A2A「终结态不可重启」）
- `完成 → 未指定`（终态退成草稿）
- `未指定 → 需要授权` / `未指定 → 失败`（跳过采纳直接进搁置/终结）
- `提交 → 完成`（跳过「处理中」，`claimed_by` 永远为空）

这和第 7 条的 #1 是同一个根因的两面（#1 是安全，这里是语义）。**要**：加一张 `ALLOWED_TRANSITIONS` 表，用户路径（`byUser=true`）可以有额外边（比如「拒绝」「采纳」），模型路径严格按表。理由：现在「终态是记录、不销毁」的承诺没有任何代码保证——一条 `task_state` 就能把它复活。

**计划草稿**
- **标题**：九态转移表 + 非法转移拒绝
- **目标**：终态复活会让「完成态是已交付记录」这条写进 README 的承诺失效；`提交 → 完成` 会让「完成」失去「真的做过」的含义。
- **功能**：`ALLOWED = { 未指定: [提交(用户), 拒绝(用户)], 提交: [处理中], 处理中: [完成,失败,取消,需要补充,需要授权], 需要补充: [处理中,取消,拒绝(用户)], 需要授权: [处理中,取消,拒绝(用户)], 完成/失败/取消/拒绝: [] }`；`task_state` 越界报错并给出合法目标；`/task-state` 在 `byUser` 下额外允许 `拒绝` 与 `未指定→提交`。
- **待议**：`需要补充 → 处理中` 是否要求先补 `note`？建议只警告不拒。`失败 → 处理中`（重试）要不要开？A2A 说不开，我倾向不开，要重试就 fork。

### 9.2 没有删除（要，已并入第 2 条）

`task_delete` 见第 2 条。补充：真实库 15 张里 13 张已完成且内容永久占着 `plans.jsonl`；没有删除 + 没有压缩（第 6 条）= 只增不减。

### 9.3 父子环 / 自指没有任何防护（要）

已复现：`task_update({id:A, parent:B})` 当 `B.parent===A` 时**创建成功**；`task_update({id:B, parent:B})` **自指成功**。`assertParent` 只校验「父存在且不是完成」，不校验环。后果：

- `cascadeClose` / `shelveChildren` 有 `seen` 防环，**不会死循环**（好消息）；
- 但面板的 `taskDepth()` 是 `while (current.parent)` 的**无界循环**（`client.src.js:369`）→ **环会让面板直接卡死**（`DEFAULT_COLLAPSED` 初始化时就调用它，不过那是样例数据；真实数据不走这条路，但 `TechTree` 的父子边 + dagre 对环的行为未定义）。
- `cascadeClose` 的语义在环上不成立（A 失败会取消 B，B 已被取消又轮到 A…… 靠 `seen` 停住，结果是「谁先被访问谁就是根」）。

**计划草稿**
- **标题**：父子与链接成环校验（提交、更新、加链接三个入口）
- **目标**：已复现自指与环；级联语义在环上没有定义，面板 `taskDepth` 会无界循环。
- **功能**：抽 `assertAcyclic(id, parent, links)`：沿 `parent` 向上走（带 `seen`）遇到自己就拒；对 `依赖/派生` 做一次 DFS 判环。`task_submit` / `task_update` / `task_link` 三处调用。报错文案给出环路径。
- **待议**：已经有环的存量数据怎么办？建议只在新写入时拒绝，读时不修（存量数据现在是干净的）。

### 9.4 编号排序在 T-1000 之后错位（要，一行修复）

`listAll()` 用 `a.id < b.id` 字符串排序（index.js:537）；`T-1000 < T-999` 为 `true`（已确认）。到 1 000 张后顺序会乱。**要**：按 `T-` 后的数字比较。顺带 `createNewInner` 的 `padStart(3)` 在 ≥1000 时自动变 4 位，没问题。

**计划草稿**
- **标题**：计划排序按数字段比较
- **目标**：`T-1000` 会排到 `T-999` 前面，列表/科技树顺序在四位数后错乱。
- **功能**：`sortKey(id)` 抽出 `^T-(\d+)$` 的数字；非标准 id 排最后按字典序。
- **待议**：是否顺手加 `T-001a` 这种子编号？不建议，现在没有需求。

### 9.5 文档与实现不一致（要，低成本）

1. README 第 5 行说「给模型 7 个工具、给面板 8 条命令」，实际是 **8 个工具 / 10 条命令**（测试 `apply 注册八个工具、十条面板命令` 断言了正确值）。README 第 132 行标题「给模型的工具（7 个）」，表格里列了 8 行。

3. 系统提示里「计划管理类工具（… task_update …）永远放行」——但 `task_update` 对已采纳计划直接抛错，这是语义错误不是权限问题，描述会误导。

**计划草稿**
- **标题**：修正 README 与工具描述里与实现不符的 4 处
- **目标**：模型会按 `task_state` 的描述去「完成父计划」（以为会级联取消子计划），实际被拒；README 的工具/命令数量与模板数量都是错的。
- **功能**：改 README 第 5、132、182 行；改 `task_state` 的 `description`（改成「有进行态子计划时拒绝完成；失败/取消/拒绝会级联取消」）；改 `task_templates` 的数量说明；在 README 加一条「工具数/命令数以测试断言为准」。
- **待议**：要不要顺手把 README 的 H1–H8 表格和 `TYPE_NAMES` 对齐？现在是一致的，不用动。

### 9.6 面板兜底显示样例数据（要，低成本）

读不到库时 `setData({tasks: SAMPLE_TASKS, …})` 会渲染 15 张**假计划**，只在角落标「样例数据：<error>」。误点「采纳/完成」会真发命令（命令带的是样例 id，宿主会报「没有这份计划」，还算安全），但视觉上非常容易误导。

**计划草稿**
- **标题**：读不到计划库时显示空态 + 明确错误，不显示样例
- **目标**：真实使用中把样例计划当真；SAMPLE_TASKS 只该在开发时用。
- **功能**：`data.live === false` 时渲染「读不到计划库：<原因>」+「重试」；样例数据挪到 URL 参数 `?demo=1` 或 dev 开关后面。
- **待议**：要不要保留「演示模式」给录屏用？可以留 `?demo=1`。

### 9.7 `note` 只有当前值，搁置理由覆盖即丢（要，依赖第 5 条）

`task_note` 直接覆盖 `task.note`，没有历史。而「为什么停在这里」恰恰是最需要历史的一条：三天后用户问「它为什么在等」，如果中途改过一次，前面的理由就没了。第 5 条的时间线如果记 `fields:['note']` + 旧值，就顺带解决了。

### 9.8 没有「结算 / 产物」字段（待议）

`计划/结算格式.md` 定了出口锚六行（verdict/conclusion/evidence/artifacts/pitfalls/where），而 taskboard 的计划**没有对应字段**——结算只能塞进 `body` 或 `note`，既不可查询也不可结构化展示。`15-计划即提案` 的实现（`plan-tree`）有这套东西。建议：**暂不做**，等「计划完成时自动生成结算」这个需求真出现再说；现在 `body` + `note` 够用，硬加字段会让 `HEAD_FIELDS` 和表单都要改。

### 9.9 面板没有「新建时选模板的预览」（小，可选）

`CreateForm` 已经解析模板并把 `markdown` 块渲染成说明文字，这块是做好的。缺的是「空模板」时没有占位示例。低优先级，可以不做。

### 9.10 一个正面发现（不要动）

`applySupersede` 的「先转移依赖、再判死刑」顺序、`cascadeClose` 的 BFS + `seen` 防环、`resolveClaim` 删掉危险回落、`PLAN_TOOLS` 永不放行造成的防死锁——这四处设计是对的，测试也覆盖了。**不要为了改权限而把它们改坏**：尤其是 `PLAN_TOOLS` 全放行，一旦收紧会让「工具全关」的计划把会话锁死。

## 我认为最该先做的三件事

### 第一件：堵住「按计划」档的提权与越权（第 7 条）

**为什么排第一**：其他所有问题都是「不好用」，这一条是「不安全」。已复现的两个洞是致命的——

- 模型可以 `task_submit(permission=完全权限, workspace=C:\)` + `task_state(处理中)`，**不需要用户采纳**就拿到完全权限，守卫实测放行写 `C:\Windows\System32`；
- 「仅可查看 / 工具全关」的守卫是**黑名单**，`plugin_manager`、`subagent`、`apply_patch`、所有 MCP 写文件工具**一律放行**，而 MCP 文件工具现在是真实使用中最常见的写盘路径。

再加上陈旧 `CLAIMS`（工具路径切任务后旧权限残留）和「任意会话可结束别人的任务」，这一档现在基本等于没有。修法明确、无设计争议、改动集中在 `installGuard` / `setStateInner` / `task_claim` 三处，**不碰级联和分组语义**，风险可控。

### 第二件：领取的并发正确性（第 4 条）

**为什么排第二**：和第一件是同一类问题（正确性 > 体验），而且互相咬合——第一件把权限收紧之后，`claim` 就是唯一的授权来源，**双领会被放大成「两个会话按同一份权限写同一片工作区」**。现在已复现「两会话同时领到同一张」「同一会话同时领到两张」；`withWrite` 只护住了 4 个写入口，`task_claim` 恰恰不在里面。修法：把读-改-写纳入锁 + `rev` 乐观校验 +（可选）跨进程锁文件。做完这条，`planClaims` 才是真的能给调度器用。

### 第三件：事件补时间戳/actor，并加 `task_history`（第 5 条）

**为什么排第三**：

- 它是**所有可观测性功能的地基**（时间线、谁干的、为什么停着），而 JSONL 现在**结构上**是历史、**内容上**不是（没有 ts / actor / from→to）。
- 它同时是**第 6 条压缩的前提**（要先能区分「当前状态」与「历史」才能抽 snapshot），做完这条再压缩才有依据。
- 改动最小、收益最广：只加字段（`ts/actor/from/to`），旧事件继续能读，不需要迁移。

**为什么不是别的**：面板可用性（第 8 条）与查询/删除（第 2 条）排在这三件之后——它们影响的是「用起来顺不顺」，而前三件影响的是「能不能信」。面板在 30 张以内现在还能用，计划量真正涨起来之前还有时间。
