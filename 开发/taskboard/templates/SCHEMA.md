# 模板 schema（v3 · 完成权模型）

> **这是语义定义。改它 = 破坏性更新。**

---

## 一、分类轴：谁有完成权

四个大类不是按"内容"分的（内容无限，分不完），而是按**谁能把它标记为完成**：

| 大类 | 完成权 | 谁按"完成" | 占位 |
| --- | --- | --- | --- |
| `goal` 目标 | **没人**，子事项全部终结时自动 | 系统推导 | 否 |
| `design` 设计 | **用户**（或 AI，由模板声明） | 点选项 / 采纳 / 驳回 | 否 |
| `record` 记录 | **作者自己** | 写完发布即完 | 否 |
| `work` 工作 | **AI** | 真做出来了 | **是** |

四个在"完成权"上互斥且穷尽。

### 决策为什么是设计、不是工作

它做的事和工作一模一样，**唯一区别是完成权归用户**。

> 决策的本质是工作，一件事情。所以就是以做完为准。只是公开了谁可以做完他。

所以决策一样可以派调研、派决策。

### 工作 = 原子目标

同一个动作，粒度不同就是不同类别：

| 例子 | 类别 | 为什么 |
| --- | --- | --- |
| "跑一条命令看结果对不对" | 工作 | 一次做完 |
| "写个项目，拉库、加特性" | 目标 | 拆不完 |

**"能一次做完"和"能再拆"互斥**，所以：

> **工作不能派工作** —— 能派就说明它本来不是工作。

这也让「升级为目标」成了自然操作：它没改变性质，只改变了粒度。

## 二、派发规则

### 一条总规则

> **不占位的类别可以派同类；占位的类别不能派同类。**

| 大类 | 占位 | 能派同类 | 原因 |
| --- | --- | --- | --- |
| 目标 | 否 | ✅ | 多个目标并存 |
| 设计 | 否 | ✅ | 用户可以同时有多个待决问题 |
| 记录 | 否 | ✅ | 多份文档并存 |
| **工作** | **是** | **⚠️ 只限"项目"** | 见下 |

### 工作能派什么（这条被用户纠正过一次）

**工作可以派任何"项目"**——调研、记录、复盘、设计，都行。

> 工作不能派工作，但他是可以继续派项目的。
> 无论是调研，记录，复盘，还是什么。工作派工作就升级为目标。

**工作不能派"另一件要做的事"**（实现项 / 缺陷 / 起草 / 上色这类）。
那说明它本来就不是原子任务，该升级为目标。

所以判定**按模板，不按 kind**：

| 模板 | kind | 工作能派它吗 | 为什么 |
| --- | --- | --- | --- |
| `GR` 调研 | work | ✅ | 查参考是"项目"，不是"另一件要做的事" |
| `GN` 校验 | work | ✅ | 验一遍是项目 |
| `GJ` 线稿 | work | ✅ | 画一张是项目 |
| `GI` 实现项 | work | ❌ | 这是"要做的事" |
| `GX` 缺陷 | work | ❌ | 同上 |
| `GD` 实现 | work | ❌ | 同上 |

代码里用 `ENTITY_TYPES` 区分：`{GI, GX, GD, GE, GY, GZ}` 是"要做的事"，
其余 work 模板（GR/GN/GJ…）是"项目"。

**为什么"派另一件要做的事"必须禁止**：两个都要占会话位，必然互相抢。
而调研/记录不争抢（调研被领取时才短暂占位，记录根本不占）。

### 完整派发表

| 从 \ 到 | goal | design | record | work |
| --- | --- | --- | --- | --- |
| **goal** | ✅ | ✅ | ✅ | ✅ |
| **design** | ✅ | ✅ | ✅ | ✅ |
| **record** | ✅ | ✅ | ✅ | ✅ |
| **work** | ✅ | ✅ | ✅ | ⚠️ 仅限项目 |

外加一条：

> **草稿不能派任何东西**（"没上去"）。

模板可以用 `dispatch` **收窄**（不能放宽）。

## 三、各状态集

| 大类 | 状态 | 说明 |
| --- | --- | --- |
| **goal** | 无自有状态 | 由子事项推导：未拆解 / 进行中 / 已完成 |
| **design** | 草稿 / 待决 / 需要信息 / 已定 / 已拒 | 待决 = 等用户 |
| **record** | 草稿 / 需要信息 / 已发布 | **不能是「正在进行」** |
| **work** | 草稿 / 提交 / 处理中 / 需要补充 / 完成 / 失败 / 取消 / 拒绝 | 九态（A2A 对齐） |

### 记录的三个状态

```
草稿  →  需要信息  →  已发布
```

- **草稿**：还在写，**没上去**，不能派任何东西
- **需要信息**：卡住了、缺东西，这是它唯一允许的"停"
- **已发布**：定了

**要改就得退回草稿** —— 「如果要可以改，他就要是草稿」。

记录**不能是「正在进行」**：它不占会话位，没有人"在跑"它。

> 待定（用户说"现在先不想"）：记录能不能是「需要授权」。

## 四、模板字段

| 字段 | 必填 | 取值 | 含义 |
| --- | --- | --- | --- |
| `name` | ✅ | `X · 中文名` | 显示名，首字母必须等于 type |
| `default_kind` | ✅ | `goal`/`design`/`record`/`work` | 默认大类（**实例可改**，见粒度升级） |
| `behavior` | ✅ | 见下表 | 界面形态 |
| `domain` | | `general`/`code`/`art`/`writing` | 领域，用于过滤下拉；缺省 `general` |
| `description` | | 字符串 | 一句话说明 |
| `dispatch` | | 大类列表 | 收窄可派发范围；缺省按「占位」规则 |
| `hints` | | 见下 | 给 AI 的操作指引，按时机分 |
| `body` | ✅ | 章节数组 | 标题 + 提示 |

### kind 是实例属性，模板只给默认值

同一套章节在不同粒度下都能用：

```yaml
name: 校验
default_kind: work       # 默认是一次能跑完的工作
```

如果发现拆不完 → **升级为目标**，`kind` 变成 `goal`，章节不变。

### behavior

| behavior | 用在哪 | 界面 |
| --- | --- | --- |
| `answer` | 目标 / 设计 | 表单 + 派发按钮 / 一问一答 |
| `decide` | 设计 | **选项卡**（可选项 / 可填 / 可拒 / 可要求调研） |
| `propose` | 设计 | 长文 + 采纳 / 打回 |
| `write` | 记录 | 长文，草稿态可改 |
| `block` | 记录 | 阻碍卡片（唯一非自终结的记录） |
| `execute` | 工作 | 正文 + 产出清单 |

## 五、hints 的时机

| 键 | 何时给 AI 看 |
| --- | --- |
| `create` | 新建时 |
| `fail` | 变成「失败」时 |
| `blocked` | 被阻碍时 |
| `resume` | 从搁置态恢复时 |
| `reject` | 被拒 / 被打回时 |

**`fail` 的硬规矩：禁止穷举。** 要求写「卡在哪 + 一个原因 + 下一件该试的事」，
不许罗列试过的一切。列清单是逃避判断。

## 六、章节提示 = 教 AI 怎么想

```yaml
body:
  - type: textarea
    id: how
    attributes:
      label: 怎么查
      description: |          # ← 不是给人看的灰字，是给 AI 的启发式清单
        找找发布平台？游戏官网、游戏社区。
        或者找找 github 有没有仓库？
        作者能写的话他就肯定会做，看看他的足迹有没有出现教程？
```

`description` 教 AI「怎么想」，不是「写什么」。

## 七、领域

同一批模板里，代码和非代码的章节结构完全不同：

| 领域 | 设计 | 工作 |
| --- | --- | --- |
| `code` | 接口、方案 | 实现、调研 |
| `art` | 风格设定、透视方案 | 线稿、上色 |
| `writing` | 人物设定、场景设定 | 起草、修改 |

`domain` 是**固定枚举**，不是自由标签（用户明确：不做 tag，只要枚举语义）。
