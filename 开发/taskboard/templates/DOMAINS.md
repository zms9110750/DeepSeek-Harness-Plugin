# 非代码领域的模板

> 绘画（`domain: art`，4 个）与小说（`domain: writing`，4 个）。
> 大类划分照 `SCHEMA.md` 的**唯一一条轴**：谁能把它标记为完成。
> 不是按"这活像什么"分，是按"谁说了算"分。

---

## 一、八个模板

| 编号 | 名称 | `default_kind` | `behavior` | `domain` | 完成权归谁 | 干什么 |
| --- | --- | --- | --- | --- | --- | --- |
| `ML` | 画作 | `goal` | `answer` | art | **没有人**（子事项全终结自动） | 一张画的立项：画什么、什么算画完、哪步最可能翻车 |
| `SV` | 定调 | `design` | `propose` | art | **用户**（点头 / 打回） | 视平线、灭点、画风、主色、光源，一次定死 |
| `GJ` | 线稿 | `work` | `execute` | art | **AI**（真画出来了） | 把定调落实成线：剪影 → 大块 → 切分 → 细节 |
| `GZ` | 上色 | `work` | `execute` | art | **AI** | 铺底 → 定光源 → 三层明度 → 色相 → 高光 |
| `MT` | 小说 | `goal` | `answer` | writing | **没有人** | 一本书的立项：篇幅、读者、人称、有没有结局 |
| `JT` | 设定集 | `record` | `write` | writing | **作者自己**（写完即发布） | 人物 / 场景 / 故事 / 硬约束，起草的宪法 |
| `GE` | 起草 | `work` | `execute` | writing | **AI** | 把一章从无写到有，一遍写完不回头改 |
| `GY` | 修改 | `work` | `execute` | writing | **AI** | 一轮只改一种毛病，改完留对照 |

两条流程（`──派──>` 是父子；`──依赖──>` 是靠 `links` 的先后关）：

```
绘画： ML 画作 ──派──> SV 定调
              ──派──> GJ 线稿 ──依赖──> GZ 上色
              （依赖：SV ──> GJ，即定调没点头前，线稿不能领取）

小说： MT 小说 ──派──> JT 设定集
              ──派──> GE 起草 ──依赖──> GY 修改
              （依赖：JT ──> GE，即设定集没发布前，起草不能领取）
```

三个结构性决定，都是为了让"完成"能正确推导：

1. **工作必须挂在目标下面，不能挂在设计下面。** 目标靠"子事项全部终结"自动完成，
   只有工作真的是目标的子节点，画完/写完时目标才会自己收口。
   如果把 `GJ` 挂到 `SV` 下面，`ML` 永远等不到子事项终结。
2. **`GJ` → `GZ` 用依赖，不用父子。** 上色不占线稿的完成条件，
   线稿完成了上色才能开始——这是"下一道关"，不是"其中一部分"。
   （同 `GN 校验` 用依赖挂在 `GD 实现` 后面的道理。）
3. **设计用依赖挡在工作的前面，而不是当工作的父节点。**
   `SV` 定完了，`GJ` 才能领取；但 `SV` 不是 `GJ` 的一部分。

`ML` / `MT` 也可以跳过 `SV` / `JT`：参考已明确就直接派 `GJ`，
短篇没有设定集就直接派 `GE`。反过来不行——`GJ` / `GZ` / `GE` / `GY` 都是
`dispatch: [design, record]`，工作类不派同类。

## 二、为什么这样分大类

### 两个 `goal`：`ML` / `MT`

判据是"能不能一次做完"。一张画、一本书做不完——中间的透视、构图、章节改动能无限往下拆。
而且**没人能替它按完成**：用户说"画吧"不等于画完了，作者说"写吧"也不等于写完了，
只有子事项全部终结它才自动完成。这正是 `goal` 的定义。

它们和 `MG 用户提出` 的区别：`MG` 是"用户甩过来的一堆要求"，
`ML` / `MT` 是**一个已经有边界的作品**。同一件事的两种粒度，所以是两个模板而不是一个。

`MT` 的 `dispatch` 保留了全部四类：小说可能派决策（这个结局要不要）、
派记录（设定集、章节大纲）、派工作（起草、修改）、甚至派子目标（分卷）。
`ML` 收窄到 `[goal, design, work]`——画很少需要一份持续维护的文字记录，
设定通常直接写在定调里。

### 一个 `design`：`SV 定调`

`SV 定调` 是**设计**，因为视平线和色调定了之后整张图所有线都要服从它。
它做的事和工作一模一样（也是在一件具体的事上做判断），唯一区别是**完成权在用户**：
用户不点头就开始描线，画完也得整张重来。这就是 `SCHEMA.md` 说的"决策的本质是工作，
只是公开了谁可以做完他"。

它用 `propose` 而不是 `decide`：视角和调子是**开放**的（能从无数角度里选），
不是二选一。所以给方案 + 代价 + 什么情况下这个方案是错的，等用户采纳或打回。

> 透视和风格合并成一条，是这份设计里最关键的判断。
> 拆成"透视方案"和"风格方案"两条，用户会分别点头，
> 然后发现仰视配暖光是脏的、特写配大远景配色是空的——两个各自都对的答案合起来是错的。
> 必须一次看到"这个角度 + 这个调子"，才能判断它成不成立。

### 一个 `record`：`JT 设定集`

**作者写出来就完**，没有人动手、不占会话位，所以是 `record` 而不是 `work`。
它没有"正在进行"这个状态——只有草稿 / 需要信息 / 已发布。

它在整条链路里的作用很具体：**起草时照它写，正文和它冲突以它为准**。
所以它的 `hints.blocked` 只给了三种缺信息的情形（只有作者知道 / 自己该查 / 子事项没回来），
并且明确禁止"先随便写一版占位"——占位设定会被后面当成真的引用。

### 四个 `work`：`GJ` / `GZ` / `GE` / `GY`

都满足"一次能做完"，且完成权归 AI——画出来了、写完了，就是完了。

| 编号 | 为什么是工作 | 为什么和相邻的不合并 |
| --- | --- | --- |
| `GJ` 线稿 | 一张线稿，一次画完 | 和上色分开：线稿没验就上色 = 把错的比例刷上颜色，返工要连颜色一起重来 |
| `GZ` 上色 | 铺一遍色，一次铺完 | 分开才能单独验收明度关系 |
| `GE` 起草 | 一章，一次写到结尾 | 和修改分开：**边写边改会永远写不完**。起草的任务是"写到结尾"，不是"写得好" |
| `GY` 修改 | 一轮修改，一轮改完 | 一轮只改一种毛病，否则分不清是哪个动作起了作用 |

`GE` 和 `GY` 必须是两条，这是小说领域最容易做错的地方。把"起草和修改"合成一条，
结果是永远在磨第一章——因为修改是即时反馈，起草没有。

## 三、`dispatch` 为什么这样收窄

| 模板 | dispatch | 理由 |
| --- | --- | --- |
| `ML` | `[goal, design, work]` | 能派子目标（系列里的每张）、派设计（要不要这个视角）、派工作（画）、派调研找参考。不派记录 |
| `SV` | `[design, record, work]` | 能派子设计（某个细节要不要）、派调研（补参考图）、派工作（线稿）；卡住派记录 |
| `GJ` | `[design, record]` | 工作不派同类。缺参考 → 见下，走「需要补充」+ 另起调研 |
| `GZ` | `[design, record]` | 同上 |
| `MT` | `[goal, design, record, work]` | 四类都要：分卷是子目标、结局是要拍板、设定集是记录、章节是工作 |
| `JT` | `[goal, design, record, work]` | 记录不占位，可以派同类（多份设定）、派调研、派提问 |
| `GE` | `[design, record]` | 工作不派同类；缺设定 → 回 JT，缺拍板 → 派设计 |
| `GY` | `[design, record]` | 同上 |

`SCHEMA.md` 的规则里，`work` 只能派 `design` / `record`，
所以 `GJ` / `GZ` / `GE` / `GY` **在字面上不能再派工作（包括调研）**。
这四个模板的 `hints.fail` 里显式写了绕法：**先把本条置为「需要补充」，
再另起一条调研挂在父目标（`ML` / `MT`）下面**——不要写成"从工作派工作"，
那会被 `assertParent` 直接拒掉。这是这套模型在非代码领域的第一个真实摩擦点，见文末。

## 四、`hints` 的写法

`create` 教"怎么想"，不教"写什么"。例如 `MT` 的一句话前提：

> 一个人想要 X，但 Y 挡着，做不到就会 Z。三样缺一样，这个故事就没有骨头。

`fail` **一律防穷举**：每个模板的 `fail` 都写成"先判断属于哪一种，只写一个原因 + 下一件该试的事"，
并且把常见死法预先列成 3–4 条带箭头的判断分支，让 AI 做选择而不是做罗列。

例（`GE` 起草）：

```
· 不知道这一章要发生什么 → 回「JT 设定集」的故事一节，别在正文里瞎试
· 知道发生什么，但场景写不动 → 人还没立住，回"他想要什么 / 他怕什么"
· 缺的是外部事实（这个年代的称谓、这个职业的流程）→ 置为「需要补充」，
  另起一条调研去查，别在正文里编一个
· 语气不对 → 这是修改的活，先写完再改
· 越写越长 → 这一章装了两件事，拆成两章
```

注意这几条都是**指向去处**（回哪一条 / 另起哪一条），而不是"再努力试试"。
`fail` 只要求写一句"卡在哪 + 一个原因 + 下一件该做的事"，
其中"下一件"是**交接给另一个事项**，不是在这条里继续挣扎——这是防穷举的关键。

## 五、`description` 为什么都写成可执行的判据

反例是"注意构图和光影"。这 8 个模板里每一句都尽量落到一个**能验的数或一个具体动作**：

- `ML`：画幅比 / 成品尺寸 / 300dpi；"缩到 25% 还能一眼看出主体"
- `SV`：视平线（过眼睛 / 高过人头 / 低于腰）；60/30/10；"同高的东西必须落在同一条水平线上"
- `GJ`：成人 7-8 头身、少年 6-7、Q 版 3-4；"先定脚接触点，再往上叠人"
- `GZ`：暗 30% / 中 50% / 亮 20%；"转灰度糊成一块 = 明度没做"
- `MT`：短篇 < 1.5 万 / 中篇 1.5–5 万 / 长篇 > 10 万；"前 300 字必须让读者知道有事要发生"
- `JT`：四行人物卡（想要 / 怕 / 说话习惯 / 绝不做）；伏笔登记要写回收章
- `GE`：一个场景 500–1500 字就该有变化；"第一段别超过 5 行"
- `GY`：一句话超过 40 字就拆；"改前 / 改后对照最多给三处，再多说明你在重写"

## 六、⚠️ 这 8 个模板目前还取不到（需要改 index.js，本次未改）

写文件只是第一步。`task_template` 不接受任意编号，它先过白名单：

```js
// index.js:61
const TYPES = ['MG','MO','SQ','SP','SK','SC','SA','JB','JW','JF','GR','GD','GI','GX','GN'];
```

`loadTemplate()` 在 `!TYPES.includes(wanted)` 时直接抛错，所以现在对 `ML` 调用
会得到「模板类型必须是 MG/MO/… ，收到「ML」」。

要真正启用，`index.js` 里**三处**都要加（漏一处会出不一致）：

| 位置 | 加什么 | 漏了会怎样 |
| --- | --- | --- |
| `TYPES`（:61） | `'ML','SV','GJ','GZ','MT','JT','GE','GY'` | 取模板直接报错，整个不可用 |
| `TYPE_NAMES`（:106） | `ML:'画作', SV:'定调', …` | 工具描述和面板里显示成空名字 |
| `TYPE_TO_KIND`（:184） | `ML:'goal', SV:'design', GJ:'work', …` | 新建时 kind 落到 `?? 'work'`，设计类会被当成可领取的工作 |

风险最高的是第三处：`resolveKindArg` 查不到就 `return 'work'`，
于是 `SV 定调` 会变成一个**可被 AI 领取的工作**——"完成权归用户"这条就没了。
我没有改 `index.js`（按任务要求），所以这三处登记留给实现者。

另外 `/task-templates` 只遍历 `TYPES`，不加就既不显示也不报错，是静默缺失。

## 七、这套模型在非代码领域的真实不足

说三点我认为最要紧的，都是设计这 8 个模板时**真的卡住**的地方，不是理论担忧。

**第一，`work` 不能派 `work`，在创作领域是硬伤。**
绘画和写作里最高频的动作恰恰是"画不动了去查一张参考"、"写不动了去找同类作品对照"，
而调研/查参考在模型里是 `work`（要动手查）。但 `SCHEMA.md` 规定工作不派同类，
于是 `GJ` / `GZ` / `GE` / `GY` 的 `dispatch` 只能是 `[design, record]`——**字面上派不出调研**。

四个模板的 `hints.fail` 里我写了绕法（先置「需要补充」→ 另起一条调研挂在父目标下面），
这个绕法能走通，但代价是真实的：**"一次只能做一个工作"的占位规则会把它变成串行。**
线稿画到一半要查参考，线稿就得先停下来；查完了再重新领取、重新进入状态。
创作恰恰是**边画边查**的——参考经常是画到某个局部才意识到缺的。
代码领域这个矛盾不明显（查文档通常发生在动手前），创作领域它每一步都在发生。
这不是模板能修的，是"工作占位"这个前提在探索型任务上的代价。

**第二，`record` 的"写完即完"和创作的真实状态不匹配。**
`JT 设定集` 我做成 `record`，因为"作者写出来就算完"。但设定集在创作中**永远在变**：
写到第七章发现这个人物不该怕水。`record` 只有草稿 → 需要信息 → 已发布三个状态，
"要改就得退回草稿"。于是实际用起来会变成：起草一条 → 设定退回草稿 → 改 → 再发布 →
起草继续。步骤是对的，但**语义上是错的**：设定集不是"发布了一份文档"，
它是一份**还在被正文检验的假设**。创作领域的记录大多是这种"活文档"，
而 `record` 模型假定了它是"交付物"。代码领域的记录（复盘、汇报）确实是交付物，所以没暴露这个问题。

**第三，`design` 的完成权给了用户，但创作领域经常没有"用户"。**
`SV 定调` 假定有人能给视角和调子点头。作者自己画的时候，点头的人就是作者自己——
那这条设计的"完成权归用户"就退化成了"AI 问、作者答"，中间那一层 `decide` / `propose`
的界面（选项卡、采纳/打回）没有真正的决策者，只是多了一道自我确认。
这不是错，但它让设计类在单人创作里变得像强制停顿。
我仍然把它做成 `design`，因为**停下来看一眼确实必要**（透视错了整张重画），
只是这个"必要"是流程上的必要，不是权限上的必要——而模型只有权限这一种表达方式。

另外两个小问题：

- **`domain` 是固定枚举，只有 `art` / `writing` 两个非代码值**，
  但绘画里的"分镜 / 漫画"和小说里的"剧本 / 游戏文案"两头都沾，只能挑一个。
  `SCHEMA.md` 明确说"不做 tag，只要枚举语义"，所以这是有意的取舍，不是遗漏——
  只是在这个取舍下，跨界创作者会被迫二选一。
- **`behavior` 里没有"画"这个形态**。`execute` 的界面是"正文 + 产出清单"，
  对文字产出合适（清单可以列章节），对图片产出只能列文件路径和截图，
  "产出好不好"仍然得靠人看。这没法靠模板解决，是界面形态的问题。
