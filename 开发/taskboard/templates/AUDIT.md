## 一、总体结论

四类别模型（谁能标完成）已经落实到模板、代码、测试三处，且三者互相对得上：
27 个模板文件的文件名、`name` 前缀、`TYPES` 白名单、`TYPE_TO_KIND` 映射完全一致，没有孤儿文件，
也没有"文件在、代码不认"的情况。

本轮真正修掉的问题分五类：

1. **旧编号残留**（改名留下的尾巴）—— 15 处模板正文里的交叉引用还写着拼音编号，
   AI 会照着去派一个不存在的模板。已全部改成英文编号。
2. **互斥写法不彻底** —— 8 个章节原本把两种互斥情形塞进同一个框
   （`RB` 能不能绕、`WF` 修根因/绕过、`WV` 怎么验、`WV` 结论、`DB` 先例、`GO` 有多糟、
   `WX` 顺序、`WD` 开头）。已按「标题并列 + 判断指令 + 两支判据 + 写错代价」改写，见 §5。
3. **`hints.fail` 防穷举覆盖不全** —— 14 个模板的 `fail` 里没有"不要罗列"的收口，
   对 `record`/`design` 这类"不会失败"的模板尤其缺（它们会退化成流水账）。已全部补齐。
4. **`framed` 字段全库缺失** —— 面板缺字段默认 `true`，于是 `GU 用户任务`
   （设计上是一个空白框）会被渲染成十来个分槽位输入框，语义静默反转。已 27/27 显式声明。
5. **「其他」章节全库缺失** —— 你要求的硬规则，27 个带框架的模板一个都没有。已全部补齐，
   且提示语按各模板的盲区定制，不是套同一句。

新增 4 个模板：`RD` 缺陷报告、`RE` 功能请求、`WX` 文档、`WP` 性能。

## 二、覆盖度裁定：加什么、不加什么

> 这一节记录**判断过程**，因为其中一条我先判错、后被纠正，理由值得留下。

### 2.1 `WP` 性能 —— 加（我先前判"不加"，是错的）

我最初的判断是「已被 `GO 优化` 覆盖」，理由是 `GO` 的必填节已经包含了
「现象 → 现在有多糟 → 什么程度算够好」。**这个判断只看了章节内容，漏看了完成权。**

`GO` 的 `default_kind` 是 `goal`，而**目标不可领取**（`KINDS.goal.claimable === false`）。
性能排查恰恰是"量一次、改一处、再量一次"就能做完的活，完成权应归 AI —— 它必须是 `work`。
用 `GO` 建一条性能任务，结果是**永远领不了**。

这就是四类别模型最容易被绕开的地方：**kind 决定能不能领取，比章节长什么样更根本。**
`WP` 的必填节直接复用 `GO` 的思路（基线 / 时间花在哪 / 改了什么 / 改完再测 / 代价），
但 `default_kind: work`，并进 `ENTITY_TYPES`（它是"要做的事"，工作不能再派它）。

### 2.2 `WX` 文档 —— 加（真缺口）

27 个模板里，`RR 汇报` 是"给已经知道上下文的人看结论"，
但**没有一个模板是"写给不知道上下文的人照着做"**。两件事的章节结构方向相反：

- 汇报：结论 → 依据 → 不确定的地方（读者已经知道你在干什么）
- 文档：读者是谁 → 主路径 → 必须讲清 → 怎么验证（读者什么都不知道）

现有做法只能硬塞进 `RR` 或 `WI` 的正文，而 `RR` 的必填节是「结论」，正好写反。
这是**结构性缺口**，不是偏好问题。

### 2.3 `RL` 大纲 —— 不加

两个理由叠加：

1. `RS 设定集` 的「故事」节已经包含大纲的核心，而且精度更高
   （一句话前提 / 三段转折 / **时间线与读者认知双顺序** / **伏笔登记表带回收章**）。
2. 小说是单人创作，多一个模板就多一次"该写哪"的犹豫；而它若落在 `work`，
   "写大纲"就变成要占位的活，对创作是负担。

按「勉强的不加」处理。**这条我把握不如 `WP`**，如果你认为该有，我更倾向让它做 `record`
（大纲是"排出来的序列"，不是"要动手做的一件事"），而不是 `work`。

### 2.4 `RV` 安全漏洞 —— 不落地，只留建议

处置路径确实与普通工作不同（私下报、披露时间线、可能要对外沟通），
但它**不该走这个任务板的主流程** —— 混进来会让"私密"这件事被登记在一个人人可见的库里。

建议（不落地）：安全类问题若需要登记，应走独立的私有渠道，或在任务板上只存一个
不含细节的占位条目（标题写"安全事项"，正文指向私有渠道），细节不进 `body`。

### 2.5 结论

**加 4 个（`RD` / `RE` / `WX` / `WP`），不加 1 个（`RL`），不落地 1 个（`RV`）。**

## 五、互斥章节：全量扫描结果

### 5.1 判据

一个章节构成"互斥"要同时满足三条：

1. 存在**两种互斥情形**（能重现 / 不能；能绕 / 不能；新能力 / 改进）
2. 两种情形**需要写的内容不同**（不是同一件事换个说法）
3. **只会有一种成立**（不会同时为真）

只满足 1、2 不满足 3 的（比如"改什么 / 不改什么"），是**并列**，不是互斥——
两项都要写，不应该改成二选一。这个区分很重要，否则会把该填满的章节改成漏填。

### 5.2 扫描结果（全量 27 个模板）

判据落地后，全库一共 16 个章节被逐个判定过，其中 **11 个是真互斥（二选一 / 三选一）**，
5 个是并列（两项都要写、故意不改）。其中 8 个互斥章节是**本轮改写**的（另 3 个新建时就是对的）。
逐条判定如下：

| 模板 | 章节 | 判定 | 处理 |
| --- | --- | --- | --- |
| `RD` | 最小复现 / 出现频率 | ✅ **真互斥** | 新建时即按二选一写 |
| `RE` | 新能力 / 改进现有 | ✅ **真互斥** | 新建时即按二选一写 |
| `WP` | 有基线 / 无基线 | ✅ **真互斥** | 新建时即按二选一写 |
| `RB` | 能不能绕 | ✅ **真互斥** | **本轮改写**（原为两行并列） |
| `WF` | 修根因 / 临时绕过 | ✅ **真互斥** | **本轮改写**（原「改了什么」两样混写） |
| `WV` | 能自动验 / 只能人工验 | ✅ **真互斥** | **本轮改写**（原「怎么验」两种可信度混写） |
| `WV` | 通过 / 不通过 / 部分通过 | ✅ **真互斥（三选一）** | **本轮改写**（原「结论」允许"基本通过"） |
| `DB` | 有先例 / 没有先例 | ✅ **真互斥** | **本轮改写**（原只写"没有就写没有"，缺判断指令） |
| `GO` | 有数据 / 只能靠感觉 | ✅ **真互斥** | **本轮改写**（原「现在有多糟」把两种情形混成一段） |
| `WX` | 必须按顺序 / 顺序无所谓 | ✅ **真互斥** | **本轮改写**（原用"如果…；如果…"把判断推给填表人） |
| `WD` | 从动作中间 / 从对话 / 从环境 | ✅ **真互斥（三选一）** | **本轮改写**（原「怎么开头」列三种却没说只挑一种） |
| `DB` | 痛点 / 验收 | ❌ **并列** | 两句都要写，不动 |
| `WE` | 改前 / 改后对照 | ❌ **并列** | 对照，不是二选一 |
| `WC` | 故意留下的和拍脑袋定的 | ❌ **并列** | 两类都要写，不动 |
| `WF` | 期望 vs 实际 | ❌ **并列** | 对照着写，不是二选一 |
| `WE` | 改什么，不改什么 | ❌ **并列** | 两个方向都要划，不动 |

其余 15 个模板的章节都是单值字段，不存在互斥结构。

> 两条判错的边界，说明一下判据怎么用：
>
> **`WF` 的「期望 vs 实际」不算互斥** —— 这两个**同时成立**（既要有期望，也要有实际），
> 缺一个就没法判断"是不是缺陷"。互斥的判据第 3 条（只会有一种成立）它不满足。
>
> **`WE` 的「改什么，不改什么」不算互斥** —— 它是用逗号写的，看着像一句话，
> 实际是**两个方向都要划**（不改什么是这轮范围的边界）。硬改成二选一，
> 结果就是每轮都漏掉边界，改到后面发现整本都在动手。

### 5.3 三条改写要点（`RB` / `WF` / `WV`）

**`RB` 能不能绕** —— 原文两行并列，等于没判断。

改后：判断指令 + 两支判据 + 写错代价。关键在最后一句：**"能绕还派阻碍，会把好事打断"**——
不给代价，AI 会用"两个都写保险一点"回避判断。

**`WF` 修根因 / 临时绕过** —— 原文是「改了什么」一节，把根因修复和绕过混在同一个框里，
再补一句"如果只是绕过去，要写明这是绕过"。问题在于：**只要框是同一个，绕过就会被记成修好**。
改成二选一后，"根因还在"这句话在绕过支里是强制出现的，而不是可选提醒。

**`WV` 能自动验 / 只能人工验** —— 原文「怎么验」同时接受命令和"点了什么路径"。
两种验证的**可信度不同**（一个以后会自己守着，一个下次不一定有人做），混着写会让
"通过"看起来比实际硬。拆开后，人工验那支必须补一句"为什么不自动验"——
否则下一个人会以为"只是懒得写测试"。

**`WV` 通过 / 不通过 / 部分通过** —— 原来只写"不要写有些问题"，但没堵住"基本通过"。
现在三选一且强制：通过 → 交出去；不通过 → 回实现；部分通过 → 必须列出分界。

### 5.4 一个顺带发现

结构自检发现 `DP.yml` 的 `plan`（打算怎么做）是全库**唯一**没有 `description` 的章节。
已补：要求写到"另一个人照着能动手"的粒度，并明确禁止"重构一下""优化性能"这种动作名。

## 七、hints 质量抽查（防穷举）

`fail` 的硬规矩是"卡在哪 + 一个原因 + 下一件该试的事"，不许罗列。

| 模板 | 防穷举措辞 | 评价 |

| `RF` | 「复盘只回答：如果当初知道哪一件事，结果就会不同？」 | 把禁令翻译成可执行自问 |
| `RB` | 「**一个**原因，不是清单」+ 兜底「不知道下一步 → 派调研」 | 三段结构 + 堵住"想不出来" |
| `WC`/`WD`/`WE`/`WL` | 先"判断是哪一种"，再列 3–5 条带箭头的分支，最后由「不要罗列"我试过…"」收口 | 分支指向**去处**（回哪一条 / 另起哪一条），不是"再努力试试" |
| `WF` | 「不要罗列"我试了 A、B、C"——那是流水账」 | 合格 |

整体上 `fail` 质量是好的：多数模板已经做到"给分支让 AI 做选择"，而不是"给禁令让 AI 猜"。

### 七之一、本轮补的 14 处收口（按模板定制，不套通用句）

抽查发现 **14 个模板的 `fail` 完全没有防穷举收口**。分两种情形，处理方式不同：

**A. `record` / `design` 类（"不会失败"的模板）—— 这类最容易漏**

它们本来就没有真正的失败形态，如果只写"不会失败"，AI 会退化成写过程：
把做过的每一步都记进来，因为"反正没有失败可写"。所以要防的是**把过程当结论**：

| 模板 | 补的收口 | 防的是什么 |
| --- | --- | --- |
| `RR` 汇报 | 「但也**不要罗列过程**：读者要的是结论，过程只留支撑结论的那几条依据」 | 汇报退化成流水账 |
| `RF` 复盘 | 「但复盘不等于流水账：不要罗列做过的事，只写一个根因」 | 复盘退化成日志 |
| `RS` 设定集 | 「也不要罗列所有想过的可能设定 —— 那不是设定集，是草稿箱」 | 把没定的东西堆成"设定" |
| `RD` 缺陷报告 | 「只写**最后排除它的那一条证据**，不要罗列排查过的每个可能原因」 | 排查过程当结论 |
| `RE` 功能请求 | 「只写最要紧的那一条理由，不要罗列所有被考虑过的替代做法」 | 把犹豫写成需求 |
| `WX` 文档 | 「也不要罗列所有可能出错的地方：只写读者真会卡住的那几条」 | 文档写成备忘录 |
| `DB` 问题 | 「只写**最要紧的那一条**理由，不要罗列所有考虑过的做法」 | 同上 |
| `RB` 阻碍 | 「不要罗列你试过的每一种绕法 —— 那是流水账，只留最后判断的那一条」 | 阻碍写成过程日志 |
| `DI` 接口 | 「不要重写整份契约，也不要罗列所有改法」 | 打回后整篇重写 |
| `DP` 方案 | 「只写：哪一步卡住 + 一个原因 + 下一件该试的事。不要罗列所有被否掉的方案」 | 方案收尾时回溯 |
| `DC` 决策 | 「**不要穷举**所有可能的方向：列一堆选项再让用户筛，等于把判断推回给用户」 | 选项无穷多 |
| `DQ` 提问 | 「**不要罗列**所有想问的，一个问号一条提问」 | 一次甩一串问题 |

**B. `goal` 类 —— 防的是"罗列所有可能方向"**

目标不会失败，但会卡在"要求互相矛盾"。这类补的是"只写矛盾在哪 + 两条方向"：

| 模板 | 补的收口 |
| --- | --- |
| `GU` 用户任务 | 「停下来只写：矛盾在哪一句 + 两条可选方向各一句。不要穷举所有可能」 |
| `GO` 优化 | 「不要罗列"我试过 A、B、C"：那是工作的失败，不是目标的」 |
| `DT` 定调 | 「不要罗列试过的每一个角度 —— 试了几个不重要，哪个数没定才重要」 |

`GA`/`GV`/`WF`/`WI`/`WL`/`WC`/`WD`/`WE`/`WR`/`WV`/`WT`/`WP` 本来就有（它们真的会失败，或原文已带收口），未动。

> 原则：**只给禁令不给理由，AI 会绕过去。** 每一条收口都带了"为什么"，
> 而不是干巴巴一句"不要穷举"。

### 一个仍未解决的张力

`RD`/`RE` 的 `fail` 写的是「不会失败，只有几个结局」，这是一个**诚实的说法**，
但它和九态里"记录没有失败态"是对齐的——前提是代码真的不给 record 提供「失败」。

需要确认：`task_state` 目前对任何 kind 都接受全部九态（`STATUS` 是全局的）。
也就是说一条 `record` 仍然可以被设成「失败」。**模板说"不会失败"，代码却允许**——
这是文档与实现的软冲突，不影响本轮功能，但要么在 `SCHEMA.md` 里承认
"记录可以进入失败态但语义上无意义"，要么在代码里按 kind 收窄状态集。属于后续项。

## 九、结构补齐：`framed` 与「其他」章节

这两项不是你点名要的，但它们是 schema 里写了、实际一个模板都没做到的硬规则，
而缺了会**静默改变语义**，所以我按「每个带框架的模板必须有「其他」章节」直接补了。

### 9.1 `framed` 字段：27 个模板全部缺失（已补）

`SCHEMA.md` 定义了 `framed`（true = 分槽位，false = 单个空白框），面板 `isFramed()` 也读它：

```js
function isFramed(yaml) {
  const match = /^framed:\s*(\w+)$/mu.exec(String(yaml || ''));
  if (match) return match[1] !== 'false';
  return true;          // ← 缺字段 = 默认 true
}
```

**风险在于默认值方向**：`GU 用户任务` 的设计是"一个空白框，用户想到什么写什么"
（加框架等于逼他先学我们的分类法），它必须是 `framed: false`。
但字段一缺，面板就按 `true` 处理 —— 用户任务会被渲染成十来个分槽位输入框，
**语义反过来了，而且不会报任何错**。

本轮 27 个模板全部显式声明：`GU` 为 `false`，其余 26 个为 `true`。
（`GU` 是唯一一个"用户自己写"的模板；`RR`/`RB` 这些虽然是记录，但都是 AI 写的，仍然要框架。）

### 9.2 「其他」章节：27 个带框架的模板全部缺失（已补）

你的要求是"每个带框架的模板必须有「其他」章节（id: other）"。补的时候没套同一句话，
而是**按该模板的盲区定制**——否则「其他」会变成"没话找话"的空框。举五个：

| 模板 | 「其他」写的是它的什么盲区 |
| --- | --- |
| `RB` 阻碍 | 阻碍背后其实是两件事（要拆），以及"谁有权确认它解除了" |
| `WX` 文档 | 多语言、文档对应哪个版本、要不要配图或录屏（决定它会不会一发布就过期） |
| `RF` 复盘 | 多个根因并存时先修哪个，以及这条教训要不要升级成规则 / 模板改动 |
| `WP` 性能 | 要不要设监控把数字盯住（否则三个月后慢慢退回去），以及会不会在别的场景变慢 |
| `GA` 画作 | 分层要求、水印、尺寸变体、要不要保留过程稿 |

每个「其他」都以同一句收口："如果这里反复被填，说明模板缺了一节 —— 回头改模板，
别让它一直兜底。" 这句是给未来的自己看的：**「其他」被频繁使用就是模板该改的信号**。

## 十、这次审查没能覆盖的（需要你定）

1. **`RD` 与 `WF` 的配对怎么串**：现在 `RD`（记录）复现 → `WF`（工作）修复，
   靠 `依赖` 串。但如果一条缺陷**修不掉**，`WF` 失败会把依赖它的下游全取消
   （`cascadeClose` 的既有行为）。实际用起来，"修不掉"更常见的处理是回退成
   "已知问题"写回 `RD`，而不是取消。这条要不要在 `RD` 的 `fail` 里写明"修不掉 → 回 RD 标注，
   别让 WF 失败"？我倾向要，但这改的是工作流语义，得你点头。
2. **性能与安全要不要和优化分家**：我加 `WP` 的理由是**完成权**（`GO` 是目标，领不了），
   不是章节。按同一逻辑，安全漏洞（`RV`）也该有独立模板 —— 但它不适合进人人可见的库。
   我只在 §2.4 留了建议，没落地。
3. **`WX` 文档的 `default_kind`**：现在是 `record`（写出来即完）。但"维护一份会过期的文档"
   其实更接近 `goal`（永远没写完）。选 `record` 是按"一次写完一篇"的粒度，
   如果你们的实际用法是"一篇文档长期跟着代码改"，那它该是 `goal`，章节也要重写。
4. **`framed` 的默认值方向** —— **已修**。面板 `isFramed()` 从「缺字段 → `true`」
   改成「缺字段 → `false`」。理由：缺失默认 `true` 会把"空白框"的模板渲染成十几个槽位，
   是**语义静默反转**；缺失默认 `false` 最多是"该分槽的没分"，用户看到一个大框，
   内容不会丢。**宁可少分，不可错分。** 27 个模板现在都显式声明了，但默认值方向
   决定了以后漏写时的后果。
