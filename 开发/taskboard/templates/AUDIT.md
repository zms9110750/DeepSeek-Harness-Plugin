## 一、总体结论

四类别模型（谁能标完成）已经落实到模板、代码、测试三处，且三者互相对得上：
27 个模板文件的文件名、`name` 前缀、`TYPES` 白名单、`TYPE_TO_KIND` 映射完全一致，没有孤儿文件，
也没有"文件在、代码不认"的情况。

本轮真正修掉的问题分三类：

1. **旧编号残留**（改名留下的尾巴）—— 15 处模板正文里的交叉引用还写着拼音编号，
   AI 会照着去派一个不存在的模板。已全部改成英文编号。
2. **互斥写法不彻底** —— `RB` 的「能不能绕」是典型的两行并列，等于把判断推给填表的人。已改写。
3. **`hints.fail` 防穷举覆盖不全** —— 14 个模板的 `fail` 里没有"不要罗列"的收口，
   对 `record`/`design` 这类"不会失败"的模板尤其缺（它们会退化成流水账）。已全部补齐。

新增 4 个模板：`RD` 缺陷报告、`RE` 功能请求、`WX` 文档、`WP` 性能。

## 一之二、两个覆盖度裁定的最终结论（含修订）

> 这一节记录**判断过程**，因为其中一条我先判错、后被纠正，理由值得留下。

### `WP` 性能 —— 加（我先前判"不加"，是错的）

我最初的判断是「已被 `GO 优化` 覆盖」，理由是 `GO` 的必填节已经包含了
「现象 → 现在有多糟 → 什么程度算够好」。**这个判断只看了章节内容，漏看了完成权。**

`GO` 的 `default_kind` 是 `goal`，而**目标不可领取**（`KINDS.goal.claimable === false`）。
性能排查恰恰是"量一次、改一处、再量一次"就能做完的活，完成权应归 AI —— 它必须是 `work`。
用 `GO` 建一条性能任务，结果是**永远领不了**。

这正是四类别模型的核心：模板的 kind 决定它能不能被领取，比章节长什么样更根本。
`WP` 的必填节直接复用 `GO` 的思路（基线 / 时间花在哪 / 改了什么 / 改完再测 / 代价），
但 `default_kind: work`，并进 `ENTITY_TYPES`（它是"要做的事"，工作不能再派它）。

### `RL` 大纲 —— 不加

两个理由叠加：

1. `RS 设定集` 的「故事」节已经包含大纲的核心，而且精度更高
   （一句话前提 / 三段转折 / **时间线与读者认知双顺序** / **伏笔登记表带回收章**）。
2. 小说是单人创作，多一个模板就多一次"该写哪"的犹豫；而它若落在 `work`，
   "写大纲"就变成要占位的活，对创作是负担。

按「勉强的不加」处理。

### `RV` 安全漏洞 —— 不落地，只留建议

处置路径确实与普通工作不同（私下报、披露时间线、可能要对外沟通），
但它**不该走这个任务板的主流程** —— 混进来会让"私密"这件事被登记在一个人人可见的库里。

建议（不落地）：安全类问题若需要登记，应走独立的私有渠道，或在任务板上只存一个
不含细节的占位条目（标题写"安全事项"，正文指向私有渠道），细节不进 `body`。

## 四、覆盖度判断（初判，已被 §一之二 修订）

> **本节保留我最初的判断，作为记录。** 其中 `WP` 那条是**错的**，最终结论以 §一之二 为准。

我最初点名三个候选，判断是"只加一个"。

### ✅ `WX` 文档 —— 真的缺

27 个模板里，`RR 汇报` 是"给已经知道上下文的人看结论"，但**没有一个模板是"写给不知道上下文的人照着做"**。
这两件事的章节结构完全不同：

- 汇报：结论 → 依据 → 不确定的地方（读者已经知道你在干什么）
- 文档：读者是谁 → 主路径 → 必须讲清 → 怎么验证（读者什么都不知道）

现有做法只能硬塞进 `RR` 或 `WI` 的正文，而 `RR` 的必填节是「结论」，方向正好相反。
这是**结构性缺口**，不是偏好问题。

### ⚠️ `WP` 性能 —— 初判"不加"，**这个判断是错的**

我当时的理由：性能优化已经被 `GO 优化` 覆盖得比较完整。`GO` 的必填节是
「哪里不对（现象）→ 现在有多糟（有数字写数字）→ 什么程度算够好」，`create` hint 里还写明
"下一步通常不是动手，而是派一个调研去把到底哪里慢量出来。没有测量过的优化都是瞎猜"。
还担心多一个近义模板会让 AI 在 `GO` / `WP` 之间选不出来。

**错在哪：只看了章节内容，没看完成权。** `GO` 是 `goal`，目标不可领取——
用 `GO` 建性能任务会永远领不了。详见 §一之二。

教训：四类别模型下，**先判 kind（能不能领取），再看章节**。章节相似不构成"重复"，
完成权不同就是两个模板。

### ❌ `RO` 大纲 —— 不加（最终仍不加）

理由：`RS 设定集` 的「故事」一节已经包含了大纲的核心成分，而且精度更高：

- 一句话前提
- 三段转折（想要 → 代价 → 应得的但不是想要的）
- 时间线（发生顺序 vs 读者知道顺序）
- **伏笔登记表：埋在第几章 / 在第几章回收**（"没登记回收章的伏笔就是坑"）

大纲真正独有的东西是"章节级排序"，但那属于 `WD 起草` 每一条的「这一章要发生什么」，
以及拆解阶段派多条 `WD` 时自然形成的顺序。单独抽一个 `RO` 会和 `RS` 抢地盘：
写大纲的人不知道该往 `RS` 的「故事」写还是往 `RO` 写，结果两边各写一半。

### 结论（修订后）

**加 2 个（WX / WP），不加 1 个（RO）。** 另有一个不落地（RV，见 §一之二）。

## 五、互斥章节：全量扫描结果

### 5.1 判据

一个章节构成"互斥"要同时满足三条：

1. 存在**两种互斥情形**（能重现 / 不能；能绕 / 不能；新能力 / 改进）
2. 两种情形**需要写的内容不同**（不是同一件事换个说法）
3. **只会有一种成立**（不会同时为真）

只满足 1、2 不满足 3 的（比如"改什么 / 不改什么"），是**并列**，不是互斥——
两项都要写，不应该改成二选一。这个区分很重要，否则会把该填满的章节改成漏填。

### 5.2 扫描结果

| 模板 | 章节 | 判定 | 处理 |
| --- | --- | --- | --- |
| `RD` | 最小复现 / 出现频率 | ✅ 互斥 | 本轮新建，已按二选一写 |
| `RE` | 新能力 / 改进现有 | ✅ 互斥 | 本轮新建，已按二选一写 |
| `RB` | 能不能绕 | ✅ 互斥 | **本轮改写**（原为两行并列） |
| `WE` | 改什么 / 不改什么 | ❌ 并列 | 两项都要写，不动 |
| `WC` | 故意留下的 / 拍脑袋定的 | ❌ 并列 | 两类都要写，不动 |
| `WF` | 期望 vs 实际 | ❌ 并列 | 对照着写，不是二选一 |
| `WE` | 改前 / 改后对照 | ❌ 并列 | 对照，不是二选一 |

其余 19 个模板的章节都是单值字段，不存在互斥结构。

### 5.3 `RB` 的改写要点

原文（两行并列，等于没判断）：

```yaml
description: |
  如果能绕：绕法是什么、绕过去会欠下什么。
  如果不能绕：写"不能绕"，并说明缺的是什么（权限？信息？外部依赖？）。
```

改后（判断指令 + 两支判据 + 写错代价）：

```yaml
label: 能不能绕（二选一）
description: |
  **先判断能不能绕，只写那一半。** 两半都写，等于没判断——绕得过去的事不该算阻碍。

  ▸ 能绕 → 写绕法，以及绕过去会欠下什么（技术债？绕过的是入口还是根因？）
    能绕还派阻碍，会把好事打断；绕法写给下一个接手的人。

  ▸ 不能绕 → 写"不能绕"，再补一句缺的到底是什么：权限、信息、还是外部依赖。
    缺什么决定谁来解 —— 缺权限要用户动，缺信息派调研，缺外部依赖只能等。
    写不出缺什么，说明还没定位到那一步，先派一条调研。
```

三个要件都在：判断指令、每支判据、**写错的代价**（第三条最容易被漏，但它是防穷举的机制——
不给代价，AI 会用"两个都写保险一点"回避判断）。

### 5.4 一个顺带发现

结构自检发现 `DP.yml` 的 `plan`（打算怎么做）是全库**唯一**没有 `description` 的章节。
已补：要求写到"另一个人照着能动手"的粒度，并明确禁止"重构一下""优化性能"这种动作名。

## 七、hints 质量抽查（防穷举）

`fail` 的硬规矩是"卡在哪 + 一个原因 + 下一件该试的事"，不许罗列。

| 模板 | 防穷举措辞 | 评价 |
| --- | --- | --- |
| `WR` | 「"没找到"不等于"不存在"——除非你能说明找全了」 | 最好的一条：把举证责任交给写的人，而不是禁止列清单 |
| `RF` | 「复盘只回答：如果当初知道哪一件事，结果就会不同？」 | 把禁令翻译成可执行自问 |
| `RB` | 「**一个**原因，不是清单」+ 兜底「不知道下一步 → 派调研」 | 三段结构 + 堵住"想不出来" |
| `WC`/`WD`/`WE`/`WL` | 先"判断是哪一种"，再列 3–5 条带箭头的分支，最后由「不要罗列"我试过…"」收口 | 分支指向**去处**（回哪一条 / 另起哪一条），不是"再努力试试" |
| `WF` | 「不要罗列"我试了 A、B、C"——那是流水账」 | 合格 |

整体上 `fail` 质量是好的：多数模板已经做到"给分支让 AI 做选择"，而不是"给禁令让 AI 猜"。

### 七之一、本轮补的 14 处收口（按模板定制，不套通用句）

抽查发现 **14 个模板的 `fail` 完全没有防穷举收口**。分两种情形，处理方式不同：

**A. `record` / `design` 类（"不会失败"的模板）—— 这类最容易漏**

它们本来就没有真正的失败形态，如果只写"不会失败"，AI 会退化成写过程：
把做过的每一步都记进来，因为"反正没有失败可写"。所以要防的是**把过程当结论**：

| 模板 | 补的收口 | 防的是什么 |
| --- | --- | --- |
| `RR` 汇报 | 「但也**不要罗列过程**：读者要的是结论，过程只留支撑结论的那几条依据」 | 汇报退化成流水账 |
| `RF` 复盘 | 「但复盘不等于流水账：不要罗列做过的事，只写一个根因」 | 复盘退化成日志 |
| `RS` 设定集 | 「也不要罗列所有想过的可能设定 —— 那不是设定集，是草稿箱」 | 把没定的东西堆成"设定" |
| `RD` 缺陷报告 | 「只写**最后排除它的那一条证据**，不要罗列排查过的每个可能原因」 | 排查过程当结论 |
| `RE` 功能请求 | 「只写最要紧的那一条理由，不要罗列所有被考虑过的替代做法」 | 把犹豫写成需求 |
| `WX` 文档 | 「也不要罗列所有可能出错的地方：只写读者真会卡住的那几条」 | 文档写成备忘录 |
| `DB` 问题 | 「只写**最要紧的那一条**理由，不要罗列所有考虑过的做法」 | 同上 |
| `RB` 阻碍 | 「不要罗列你试过的每一种绕法 —— 那是流水账，只留最后判断的那一条」 | 阻碍写成过程日志 |
| `DI` 接口 | 「不要重写整份契约，也不要罗列所有改法」 | 打回后整篇重写 |
| `DP` 方案 | 「只写：哪一步卡住 + 一个原因 + 下一件该试的事。不要罗列所有被否掉的方案」 | 方案收尾时回溯 |
| `DC` 决策 | 「**不要穷举**所有可能的方向：列一堆选项再让用户筛，等于把判断推回给用户」 | 选项无穷多 |
| `DQ` 提问 | 「不要罗列所有想问的，一个问号一条提问」 | 一次甩一串问题 |

**B. `goal` 类 —— 防的是"罗列所有可能方向"**

目标不会失败，但会卡在"要求互相矛盾"。这类补的是"只写矛盾在哪 + 两条方向"：

| 模板 | 补的收口 |
| --- | --- |
| `GU` 用户任务 | 「停下来只写：矛盾在哪一句 + 两条可选方向各一句。不要穷举所有可能」 |
| `GO` 优化 | 「不要罗列"我试过 A、B、C"：那是工作的失败，不是目标的」 |
| `DT` 定调 | 「不要罗列试过的每一个角度 —— 试了几个不重要，哪个数没定才重要」 |

`WF`/`WI`/`WL`/`WC`/`WD`/`WE`/`WR`/`WV`/`WT`/`WT`/`WP` 本来就有（它们真的会失败），未动。

> 原则：**只给禁令不给理由，AI 会绕过去。** 每一条收口都带了"为什么"，
> 而不是干巴巴一句"不要穷举"。

### 一个仍未解决的张力

`RD`/`RE` 的 `fail` 写的是「不会失败，只有几个结局」，这是一个**诚实的说法**，
但它和九态里"记录没有失败态"是对齐的——前提是代码真的不给 record 提供「失败」。

需要确认：`task_state` 目前对任何 kind 都接受全部九态（`STATUS` 是全局的）。
也就是说一条 `record` 仍然可以被设成「失败」。**模板说"不会失败"，代码却允许**——
这是文档与实现的软冲突，不影响本轮功能，但要么在 `SCHEMA.md` 里承认
"记录可以进入失败态但语义上无意义"，要么在代码里按 kind 收窄状态集。属于后续项。
