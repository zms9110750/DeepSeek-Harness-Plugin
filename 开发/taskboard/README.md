# 任务库（@local/taskboard）

计划既是存储里的一条记录，也是对话面板里的卡片。
存储是**单个 JSONL**：`%USERPROFILE%\.dsh\taskboard\plans.jsonl`（可用环境变量 `TASKBOARD_STORE` 覆盖）。
宿主侧给模型 9 个工具、给面板 12 条命令，并把「按计划」权限档注入宿主。

## 存储（JSONL）

- 一个文件、追加写，一行一个事件：`{"op":"upsert","task":{…}}`；读取时按顺序折叠成当前状态
  （同一 `id` 后写的覆盖前面的；也兼容 `{"op":"patch","id":…,"patch":{…}}` 的合并写法）。
- 计划字段：`id` / `title` / `type` / `status` / `parent` / `links` / `workspace` /
  `workspaces` / `permission` / `claimed_by` / `body` / `note`。
- 新建计划编号取当前最大 `T-###` + 1（进程内写锁串行化读改写，撞号重试）。
- `links` 是逗号分隔的 `类型:目标`（`依赖:` / `派生:` / `取代:` / `来源:` …），
  保存时去重（大小写与空格归一）。
- 老格式（`任务\*.md`，目录可用 `TASKBOARD_ROOT` 覆盖，默认 `X:\temp\dsh\任务`）只在
  第一次读不到 JSONL 时一次性导入，成功后写 `plans.jsonl.migrated` 标记，之后不再导入。
- 坏事件行会被跳过；备份/搬迁只需要搬这一个文件。

## 九态

| 状态 | 意思 | 怎么进入 / 注意 |
| --- | --- | --- |
| `未指定` | 没有采纳：AI 提交的草稿，用户还没表态，不能领取 | `task_submit`、`/task-create` 默认；`task_update` 只能改这个状态的内容 |
| `提交` | 采纳：用户认可，可以领取 | **只有用户路径能进**：`/task-approve`、`/task-create status=提交`、`/task-state`（byUser=true）；模型工具 `task_state` 改提交会被拒 |
| `处理中` | 接取在做：某个会话领走了 | `task_claim`、`/task-state <id> 处理中`；要过「一次一个」+ 依赖/派生规则，并写 `claimed_by` |
| `需要信息` | 搁置：缺信息，等用户补 | `task_state` / `/task-state`；离开「处理中」时清 `claimed_by` |
| `需要授权` | 搁置：等用户确认再继续 | 同上 |
| `完成` | 交付：计划做完了 | `task_state` / `/task-state`；会级联取消仍搁置的子计划 |
| `失败` | 不能继续：做不下去了 | `task_state` / `/task-state` |
| `取消` | 不做了：父计划交付后仍搁置的子任务，或「取代」后旧计划的派生下游，被自动取消 | 级联自动改；也可 `/task-state` |
| `拒绝` | 用户否决了这份计划 | `/task-reject`、`/task-state`；被「取代」的旧计划也会自动转拒绝 |

状态规则的硬约定：

- 模型提交的一律是「未指定」；**采纳只能由用户做**（命令路径 `byUser=true`）。
- `claimed_by` 只在该计划「处理中」时有意义：**离开「处理中」去任何状态都会清空它**
  （包括完成 / 失败 / 取消 / 拒绝，以及需要信息 / 需要授权）。

### 状态转移规则（安全边界 + 工作流）

**只有一条是安全边界：**

| 转移 | 结果 |
| --- | --- |
| `未指定`（草稿）→ `处理中` | **禁止** |

理由：计划只有在「处理中」时才会把 `workspace` / `permission` 交给守卫。草稿是模型自己能写的，
如果草稿能直接进「处理中」，模型就能绕过「采纳只能由用户做」，给自己发一张写着「完全权限」的计划。
**这条曾经是洞，已修复（T-016）。**

其它边按工作流放开：

| 从 | 能到 |
| --- | --- |
| `未指定` | `提交`（仅用户）、`需要信息`、`需要授权`、`拒绝`、`取消` |
| `提交` | `处理中`、`完成`、`失败`、`取消`、`拒绝`、`需要信息`、`需要授权` |
| `处理中` | `完成`、`失败`、`取消`、`需要信息`、`需要授权`、`拒绝` |
| `需要信息` / `需要授权` | `处理中`、`取消`、`拒绝` |
| 终态（`完成` / `失败` / `取消` / `拒绝`） | 只能重开回 `提交`（**仅用户**） |

**重开（T-030 决议）**：终态可以被用户重开回「提交」，然后重新领取、继续往下挂新的子任务。
模型不能重开（`byUser` 检查）。理由：有些目标没有明确终点（「修好这个东西」），
bug 也是后来才发现的，一刀切锁死会让这类计划只能 fork 出一堆幽灵副本。

**失败 ≠ 取消**：失败是「尝试了但做不成」，取消是「决定不做了」。
「处理中」两个按钮都有（T-038 第 2 条）。

### 分组：一个状态可以属于多个组

| 组 | 状态 | 意思 |
| --- | --- | --- |
| **进行** | `提交` / `处理中` / `需要信息` / `需要授权` | 还活着：在做，或者停下来等人但没放弃 |
| **搁置** | `需要信息` / `需要授权` | 停下来等人 |
| **完成** | `完成` / `失败` / `取消` / `拒绝` | 终结了 |

**`需要信息` 和 `需要授权` 同时属于「进行」和「搁置」**——它们是**进行中的暂停**，不是终结。
所以 `GROUP_OF` 的值是数组，判定必须用 `hasGroup(status, '搁置')`，不能写 `=== '搁置'`。

`未指定`（草稿）不属于任何组。

定义在 `index.js` 的 `GROUP_OF`；面板有一份同样的 `STATUS_GROUPS`（`client.src.js`），
两边要一起改。`/task-groups` 输出权威定义，面板可以据此自检。

### 三分类（级联只看这三类，由分组派生）

| 分类 | 状态 | 挡父计划「完成」 | 父搁置时 | 父终止时 |
| --- | --- | --- | --- | --- |
| **进行态** | `提交` / `处理中` / `需要信息` / `需要授权` | **挡** | → 需要授权 | → 取消 |
| **草稿** | `未指定` | 不挡 | 不动 | 不动 |
| **完成态** | `完成` / `失败` / `取消` / `拒绝` | 不挡 | 不动 | 不动 |

- `提交` 算进行态：已采纳、已派发、只是还没人领。它挡父计划完成，父计划终止时被主动取消。
- `未指定` 是草稿：没采纳就没生效，不作数 —— 既不挡完成，也不跟着取消。
- 完成态是已交付的记录：不销毁、不改写、也不阻挡父计划收尾。

### 派生（父子结构）的两条语义

1. **上行**：父任务需要细化才派生任务；子计划里只要还有进行态，就不许把父计划标「完成」。
2. **下行**：父计划一旦进入终止态（完成 / 失败 / 取消 / 拒绝，全是「完成态」），
   进行态的子计划一律「取消」，递归到孙计划。

两条自洽：父计划正常走完时子计划本来就都终结了，下行级联是空操作。

### 依赖链的单向终结

- 前者 `完成` → 不级联，后者照常领取。
- 前者 `失败` / `取消` / `拒绝` → 进行态的下游全部「取消」，递归。
- 理由：已采纳的计划不能改，只能 fork 重来；留着「提交」会让人误以为还能领。

### 级联会穿过整片下游

一个计划终结后，下游按**广度优先**一路收掉（`cascadeClose`）：被取消的下游自己也算「终止」，
所以它自己的子计划和依赖方继续往下收，`seen` 集合防环。

两者的区别只在根节点：

| 根计划的状态 | 收子计划 | 收依赖方 |
| --- | --- | --- |
| `完成` | 收 | **不收**（我做成了，等我的下游照常可领） |
| `失败` / `取消` / `拒绝` | 收 | 收（我没做成，依赖我的都是死路） |

## 领取（task_claim）规则

`task_claim` 只接受「提交」的计划，并按下面顺序检查：

1. **状态必须是「提交」**：未指定 / 拒绝 / 完成 / 需要信息 / 需要授权 都会拒
   （未指定会提示等用户采纳）。状态判断在「一次一个」之前，报错不会被后者盖住。
2. **一次一个（按会话）**：同一会话同一时刻只能有一个「处理中」的计划；
   手上还有时领不了新的，要先把它完成/失败/取消。不同会话可以各领一个并行
   （口径：一个消息循环实体一个任务）。
3. **依赖**：自己 `links` 里的 `依赖:X`，X 必须已经「完成」（X 不存在也拒）。
4. **父计划**：有 `parent` 的，父计划必须「处理中」。
5. **派生**：别人 `links` 里有 `派生:我` 的，那个派生源必须是「处理中」。

领取成功后：状态 → `处理中`，`claimed_by` = 会话 id，并把计划的 `workspace` / `permission`
交给权限侧（用于「按计划」档）。面板上的「领取」走 `/task-state <id> 处理中`，
同样受以上规则约束。

## 取代（采纳时的级联）

新计划的 `links` 写 `取代:X`。当新计划被真正采纳成「提交」时（`/task-approve`、
`/task-state … 提交`、`/task-create status=提交` 都会触发），一次性做三件事：

1. **依赖转移**：所有指向 X 的 `依赖:X` 改成 `依赖:<新计划>`；
2. **旧计划 → 拒绝**（同时清 `claimed_by`），并把它自己的下游一起收掉
   （子计划 + 还没转移走的依赖方，走 `cascadeClose`）；
3. **`links` 里 `派生:X` 写法的下游**递归取消。

**顺序有讲究**：必须先把依赖转移走，再判旧计划死刑。反过来的话，旧计划一转「拒绝」
就会把那些依赖方当成死路一起取消，而它们本该在替代关系里活下来、改指向新计划。

重复采纳同一份已「提交」的计划是幂等的（直接返回「已经是提交」），不会重放级联。

### 已知行为：不拦截正在做的事情

被替代的 X 如果正被别的会话领在手上（`claimed_by` 非空、状态 `处理中`），
转「拒绝」会把那份活直接抽走。**这是已确认的行为：不拦、不提示、不加确认。**
问题以后单独处理。

## 给模型的工具（9 个）

| 工具 | 作用 |
| --- | --- |
| `task_list` | 列出所有计划头（id/标题/类型/状态/父/链接/子工作空间/权限档位/备注摘要） |
| `task_get` | 读一份计划的全文（头部 + 正文 + 备注） |
| `task_submit` | 提交一份草稿（状态固定「未指定」，用户采纳后才能领取） |
| `task_claim` | 领取一份「提交」的计划 → 「处理中」；返回子工作空间/权限档位；规则见上 |
| `task_note` | 改备注 / 搁置理由；**不受「只有未指定可改」限制**，进行中也能写；空串清空 |
| `task_history` | 读一份计划的**事件历史**（时间 / 谁改的 / from→to / 备注）；**只读**，不改任何东西 |
| `task_template` | 按类型（A/B/C/D/R/F，或留空 = 空模板）取一份计划模板（GitHub issue forms 的 YAML） |
| `task_state` | 改状态（九态之一）；**不能改「提交」**（要用户采纳）；可顺带写 `note`；终止态会触发派生/依赖的取消级联 |
| `task_update` | 改已有计划的**内容**（标题/类型/父/关联/子工作空间/权限/正文），只改内容不改状态；**只有「未指定」的计划可改** |

### 备注（note）

- 字段：`note`，纯文本，上限 4000 字。
- 用途：写清「为什么停在这里」——为什么需要授权、为什么缺信息、在等谁。
- **与 `task_update` 的区别**：备注不是计划内容，所以**不要求计划处于「未指定」**。
  进行中的计划正需要补一句「我在等什么」，因此单独给了 `task_note` 和 `/task-note`。
- `task_state` 可以一次写完状态 + 理由：`{id, status: '需要授权', note: '要花钱买 X'}`。
- 面板详情层有「备注 / 搁置理由」一节：可直接编辑保存；停在搁置态却没写理由时会提示补一句。
- 列表里备注只显示前 40 字的摘要。

### 事件历史（T-019）

每条新事件在原有 `{op, task}` 之上**并列新增**四个字段：

```json
{"op":"upsert","ts":"2026-10-25T02:30:00.000Z","actor":"session-xxx","from":"未指定","to":"提交","task":{…}}
```

- `ts`：UTC ISO 时间戳。
- `actor`：会话 id，或 `user`（用户路径），兜底 `unknown`。
- `from` / `to`：**只在状态真的变化时才写**；改备注、改正文不带这两个字段。

**极其保守的兼容策略**（用户明确要求「不要随便改日志」）：

- 事件形状不变，仍是一行一个 `upsert`，老读代码只认 `op`/`task`，完全不受影响。
- 老事件没有这些字段 → 读的时候缺就缺，**不报错、不补写、不迁移**。
- 坏事件行照旧跳过，不影响其它行读取。
- 读历史是**纯只读操作**：有测试专门断言「读完之后文件字节完全不变」。

`task_history(id, limit?)` 返回事件列表；面板详情层有「历史」一节显示时间线（最近 30 条）。

### 工作区：`workspace` + `workspaces`

| 字段 | 含义 | 形式 |
| --- | --- | --- |
| `workspace` | **子工作区**（主战场），单个 | 绝对路径；空 = 按会话 cwd |
| `workspaces` | **额外工作区**（要读写的其它目录） | 逗号分隔的绝对路径；空 = 没有 |

- 额外工作区必须是绝对路径（盘符 / UNC / 以 `/` 开头），相对路径直接拒；
  存进去时统一成 `\` 分隔、去空去重。
- 「工作区内修改」档下，写操作落在 `workspace` **或** `workspaces` 任一项内都放行；
  都不在则拒，错误文案会列出全部允许目录。
- `task_claim` / `planClaims.effective` 都会带回两者：`workspace` 是字符串，
  `workspaces` 是数组（外部调度器好直接用）。

## 给面板的命令（12 条）

| 命令 | 作用 |
| --- | --- |
| `/tasks` | 输出全部计划头的 JSON（面板读取；每条多一个 `summary` 正文首行和 `groups` 分组数组，不含正文和文件名） |
| `/task-groups` | 输出九态分组定义：`{groups, status:[{status,groups}]}`；面板据此着色/自检 |
| `/task-get <id>` | 输出一份计划的全文 JSON（面板读取正文与备注） |
| `/task-note <id> <文本>` | 改备注 / 搁置理由；只在第一个空格处切出 id，其余整段（含空格换行）都是备注；返回 `{id,note}` |
| `/task-approve <id>` | 用户采纳（→ `提交`），并触发「取代」级联；已经是「提交」时幂等返回 |
| `/task-reject <id>` | 用户打回（→ `拒绝`，清 `claimed_by`），走同一个改状态入口，照样触发级联 |
| `/task-create <json>` | 新建计划；入参 `{title,type,body,parent,links,workspace,permission,status}`，返回 `{id,status}`。状态默认 `未指定`，只允许 `未指定` 或 `提交`（其它状态走 `/task-state`）；`type` 可留空 = 空模板 |
| `/task-update <json>` | 改已有计划的**内容**；入参 `{id,title?,type?,body?,parent?,links?,workspace?,permission?}`；只有「未指定」的计划可改 |
| `/task-state <id> <状态> [备注]` | 用户改状态（byUser=true）：能采纳成「提交」、能在面板「领取」；第三个参数起是备注（含空格）；与 `task_claim` 共享「一次一个」+ 依赖/派生规则 |
| `/task-templates` | 输出全部模板的 JSON：`[{type,yaml}]`（26 份，见「模板」一节） |
| /task-paths | 输出计划库与模板的绝对路径（面板读取，避免硬编码用户目录） |
| /task-history <id> [limit] | 输出一份计划的事件历史 JSON（面板时间线） |

`/task-create` 的 `rawInput` 是一整段 JSON，例如：

```json
{"title":"面板里加刷新按钮","type":"D","body":"## 目标\n点一下重新拉 /tasks。","workspace":"X:\\temp\\dsh\\开发\\composer-drawer","permission":"工作区内修改"}
```

## 宿主服务：planClaims

插件通过 `ctx.provide('planClaims', …)` 暴露一个按**会话 id**操作的领取服务，给
「一个计划 fork 一个会话」的调度器用（子智能体/团队走自己的权限档，不接这个口子）：

| 方法 | 作用 |
| --- | --- |
| `current(sessionId)` | 该会话当前正在做的计划（`处理中` 且 `claimed_by` 匹配）；没有则 `undefined` |
| `claim(sessionId, planId)` | 为某个会话领取一份「提交」的计划；一次只能一个，规则与 `task_claim` 相同 |
| `release(sessionId, nextStatus?)` | 释放该会话的领取；默认退回「提交」，也可指定九态之一，并清 `claimed_by` |
| `list()` | 只读列出当前全部领取（`{id,title,claimedBy,workspace,permission}`） |

`current` / `claim` / `release` 直接读存储（按 `claimed_by` 严格匹配会话 id）；
「按计划」守卫另有一份进程内快取，DSH 重启后从存储里状态为「处理中」的计划重建。

### 会话隔离（一个会话一个任务）

一个**会话** = 一个消息循环实体（主会话、子 AI、团队 AI 各算一个）。

- 同一 `sessionId` 同一时刻只能有一个「处理中」的计划；换任务必须先结束或搁置当前那张。
- 不同 `sessionId` 可以**并发**各领一张，各按自己那份计划的 `workspace` / `permission` 干活。

**权限不并集**：守卫每次只解析出**一个** claim，用它一方的 workspace + permission；
解析不出就是没有，直接拒（失败即关），不会「合并」两个计划的权限。

早期版本的 `resolveClaim` 有一条危险回落：`claimed_by` 为空的「处理中」计划会被**任何**会话
当成自己的。两个会话同时命中，就等于 A 的 workspace 配 B 的 permission 一起生效。
**这条回落已删除**：认不出就是没有 claim，必须走 `task_claim`（领取会写 `claimed_by`）。

### 给自管子 AI 留的门

`planClaims` 的 `sessionId` 是**任意稳定字符串**，不要求是真实的 DSH 会话对象。
外部调度器（含以后的自管子 AI）只要给每个子 AI 一个稳定 id，就能：

```js
await planClaims.claim('subai-alpha', 'T-020');   // 子 AI A 领 T-020
await planClaims.claim('subai-beta', 'T-021');   // 子 AI B 同时领 T-021
await planClaims.effective('subai-alpha');       // { id, workspace, permission } —— 自己实现守卫
await planClaims.release('subai-alpha', '完成'); // 释放后快取同步清空
await planClaims.list();                         // 全部在做的
```

子智能体 / 团队 AI 自己的权限档**不是**「按计划」，所以本插件的守卫本来就不管它们——
这是设计，不是漏洞。它们可以完全不接这个口子；接了也只是取得「该干什么、按哪个目录、什么权限」
这三样信息，实际限制仍由它们自己的权限档说话。

| 大类 | 前缀 | 模板 |
| --- | --- | --- |
| 目标 **G**oal | G | `GU` 用户任务 · `GO` 优化 · `GA` 画作 · `GV` 小说 |
| 设计 **D**esign | D | `DC` 决策 · `DP` 方案 · `DQ` 提问 · `DI` 接口 · `DB` 问题 · `DT` 定调 |

## 权限：按计划

插件会往权限目录里注入一档 **「按计划」**（`plan`，sandbox 取 `danger-full-access`、
approval 为 `never`，真正的收窄由守卫按领取的计划做）：

- 只有会话档位是「按计划」时这个守卫才生效；其它档位（仅可查看 / 工作区内修改 /
  完全权限 / 工具全关）按会话自己的档位走，与计划无关。
- **计划管理类工具**（`task_list` / `task_get` / `task_submit` / `task_claim` /
  `task_state` / `task_update` / `task_template` / `task_note`）在任何档位都放行——否则「按计划」档下
  连 `task_list` / `task_claim` 都被拒，永远领不到任务。

### 不死锁（切任务永远可行）

计划写的权限**不能挡住切任务**：

| 计划权限 | 工作区类工具 | 计划管理工具（含 `task_state`） |
| --- | --- | --- |
| `工具全关` | 拒 | **放行** |
| `仅可查看` | 写/外部类拒、纯读放行 | **放行** |
| `工作区内修改` | 必须在 `workspace` / `workspaces` 内 | **放行** |
| `完全权限` | 放行（仍尊重 `deny`） | **放行** |

所以 AI 永远能：`task_state` 把当前计划改成「完成 / 失败 / 需要信息 / 需要授权」→
`task_list` → `task_claim` 领下一张。被挡时的报错文案会直接写出这条出路。

### 工具描述符（T-023）：白名单口径

每个工具带四个描述，**守卫按描述判，不按名字清单判**：

| 描述 | 含义 | 只读档 | 工作区内修改 |
| --- | --- | --- | --- |
| `write` | 改工作区内容 | 拒 | 要过路径校验 |
| `destructive` | 可能不可逆地删/覆盖 | 拒 | 放行（可被 `deny` 关掉） |
| `external` | 离开本机/本进程（联网、起子进程、装包） | **拒** | 放行（可被 `deny` 关掉） |
| `idempotent` | 同参重放结果一致 | 不影响 | 不影响 |

**未知工具按最保守处理**（四个描述全按危险算），所以新装的插件不会自动获得权限。
`mcp__*` 一律按 `write + destructive + external` 处理。

这修掉了旧实现的一个真洞：以前是 `WRITE_TOOLS` 黑名单，只认
`write` / `edit` / `delete` / `pwsh` / `bash` / `terminal_open` 五个名字，
`plugin_manager`（能装插件）、`subagent`（能起不受本守卫约束的子智能体）、
任何 `mcp__*` 写工具**全部漏放行**，等于绕过整个权限模型。

### 计划级 `deny`：比权限档细一档

计划可以写 `deny`（逗号分隔的描述符名），在权限档之上**再收窄**：

```json
{"id":"T-100","permission":"完全权限","deny":"destructive,external"}
```

- 只能收窄，不能放宽：`deny` 空着的计划仍然受权限档约束。
- 例：给完全权限但禁掉破坏性操作，AI 能写文件、跑只读命令，但不能 `Remove-Item`。

- 没领取计划时，其余工具全被拒（提示先 `task_list` + `task_claim`）。
- 领取后按计划里的 `permission` 收窄，规则见上表；`工作区内修改` 要求写操作必须落在
  `workspace` **或** `workspaces` 里任一目录内（`workspace` 为空时用会话 cwd 兜底；
  命令类要求命令里出现其中某个目录）。
- 领取快取在进程内，DSH 重启后从存储重建（见上）。
- 插件还会往系统提示里塞一段执行约定（`order: 60`），让模型知道「按计划」档怎么领任务、
  怎么用 `task_submit` 加计划、怎么用 `task_state` 收尾。
