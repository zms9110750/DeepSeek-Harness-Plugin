# 模板分类和状态转移

> 四类是什么，九态怎么变，谁能改。
>
> 代码：`packages/core/index.js`

---

# 一、九个状态

| 状态 | 所属组 | 含义 |
| --- | --- | --- |
| 未指定 | —（无组） | 还没交出去 |
| 提交 | 进行 | 已采纳，等人领 |
| 处理中 | 进行 | 有人在做了 |
| 需要信息 | **进行 + 搁置** | 卡住，缺信息（AI 能自己解决） |
| 需要授权 | **进行 + 搁置** | 卡住，缺许可（只有人能解决） |
| 成功 | 结束 | 做完了 |
| 失败 | 结束 | 没做成 |
| 取消 | 结束 | 主动放弃 |
| 拒绝 | 结束 | 被驳回 |

## 组名的来历

原名「完成」，只覆盖成功那一支。改成「结束」，覆盖 成功/失败/拒绝/取消 四个。

`未指定` 不属于任何组 —— 它是草稿，不参与任何计数。

# 二、四类（kind）

每条任务必属一类。类别决定它**怎么被对待**，不是决定内容。

| 类别 | 名字 | 谁来干 | 占工位 | 能领取 | 状态怎么来 |
| --- | --- | --- | --- | --- | --- |
| `goal` | 目标 | 无（由派生任务决定） | ❌ | ❌ | **推导** |
| `design` | 设计 | 用户 | ❌ | ❌ | 手动（只有人能改） |
| `work` | 工作 | AI | ✅ | ✅ | 手动 + 计算 |
| `record` | 记录 | 无（写出来即完） | ❌ | ❌ | 手动（只有人能改） |

## 「占工位」是什么意思

同一会话同一时刻只能有一个「处理中」的工作。
**目标和记录根本不参与这个竞争** —— 它们不占位。

这条解开过一个死锁：旧模型里「父节点占着会话位」，领了父就领不了子。
现在能当容器的父节点（目标）根本不可领取，争位这个情况不存在。

## 类和模板的关系

**一个类对应多个模板。**

```
目标   GU 用户需求 / MM 预期不符 / FN 新增功能 / OP 项目优化 / TS 项目测试
设计   DQ 提问 / DC 决策 / DI 接口界面 / IM 底层实现
工作   WR 调研 / WV 校验 / WT 实现项
记录   RB 阻碍 / RW 交付 / RF 复盘 / RL 留档
```

模板决定**内容长什么样**，类决定**怎么被对待**。
同一个类的不同模板，状态行为完全一样。

详见 [模板和章节.md](./模板和章节.md)。

# 二点五、工作组 vs 状态组

两个都叫「组」，但是**完全不同的东西**。历史上都叫「分组」，已改名。

| | **工作组** | **状态组** |
| --- | --- | --- |
| 是什么 | 一个工作组 = 一件事 / 一个项目 | 九态的归类 |
| 有几个 | 用户随便建 | **固定三个**：进行 / 搁置 / 结束 |
| 一条任务属于几个 | **1 个** | 1-2 个（需要信息同时属进行和搁置） |
| 存下来吗 | **存**（`groups.jsonl`） | **不存**，算出来的 |
| 会变吗 | **不能变**（建好后不可迁移） | 随时变 |
| 谁定义 | 用户建 | 代码写死 |
| 用途 | 组织工作 | 筛选 + 取色 |
| 对应函数 | `listGroups()` | `groupsOf()` |
| 对应入口 | `task_group` 工具 | `task-groups` 命令 |

## 工作组

一个工作组 = 一件事 / 一个项目。用户原话：

> 分组是没有关联的事情。一个程序做的怎么样跟另一个程序无关。
> 而用户一个时候只会验收一个程序，只有一个主要目标。

```
工作组 A「任务板插件」
  ├─ GU-01 用户需求
  ├─ WI-01 实现
  └─ DC-01 决策

工作组 B「沙盘研究」
  └─ …
```

**硬规则：一个任务只能属于一个工作组，且建好后不能迁移。**

为什么不能迁移：工作组代表「这件事是哪次工作里提出的」，
事后改归属会让历史失真。

**归档是对工作组归档的** —— 整组一起收起来。

## 状态组

只有三个，代码写死：

```
进行    提交 / 处理中 / 需要信息 / 需要授权
搁置    需要信息 / 需要授权
结束    成功 / 失败 / 取消 / 拒绝
```

**没有任何存储。** 一个状态属于哪一组由 `GROUP_OF` 表决定。

「需要信息」「需要授权」**同时属于两组**（进行 + 搁置）——
它们是"进行中的暂停"，不是终结。

用途只有两个：

```
筛选    面板上点「搁置」只显示卡在等人的任务
取色    卡片和状态点的颜色按组取（但失败和完成要分开，见 UI.md）
```

# 三、最关键的一条区分：授权 vs 信息


**这是全系统最容易搞混、也最容易被实现错的一条。**

```
需要授权 = 用户拍板，AI 无权改
需要信息 = AI 去查，用户不需要动
```

## 为什么这条重要

它决定**初始状态**：

| 类别 | 初始状态 | 为什么 |
| --- | --- | --- |
| 目标 | 未指定 | 要人「采纳」才进推导 |
| 工作 | 未指定 | 要人「采纳」才能领 |
| **设计** | **需要授权** | AI 无权自己决定 |
| **记录** | **需要授权** | 要人看过才作数 |

## 一个具体的误解

我最初以为「DQ 提问」初始应该是「需要信息」—— 因为「提问」听起来是在要信息。

**这是错的。** 用户的原话：

> 授权，意味着这个东西必须由用户拍板。ai无权从需要授权转变状态。
> 而信息是ai可以操作的

提问的答案是**人**给的。AI 不能自己把答案填上、然后标成功。
所以它是「需要授权」，不是「需要信息」。

判据不是「听起来像什么」，而是：**这件事 AI 能不能自己搞定。**

```
AI 能自己搞定的（查文档、跑一遍、试一下）  → 需要信息
AI 不能自己搞定的（要人拍板、要人给权限）    → 需要授权
```

## 落到代码里

`packages/tools/index.js` 的 `task_submit`：

```js
const initialStatus = kind === 'design' || kind === 'record' ? '需要授权' : '未指定';
```

`packages/core/index.js` 的 `transitionBlocker`：

```js
/* 设计：AI 完全无权改状态 */
if (kind === 'design' && byUser !== true) {
  return '「设计」的状态只能由用户改…';
}
```

**`byUser` 是这条规则的执行点。** 它由调用方传：

```
tools/index.js:1566   setState(parts[0], parts[1], agent, true, ...)   ← 命令 = 用户
tools/index.js:execute  不传                                          ← 工具 = AI
```

所以 `/task-state <id> 成功` 能过，而 `task_state` 工具会被拒 —— 这是**设计意图**，不是不一致。

# 四、两类状态：存的 vs 算的

## 存储态

由人/AI 的动作写进 `status` 字段：

```
未指定 --采纳(人)--> 提交 --领取--> 处理中
处理中 --交付成功(人批准)--> 成功
处理中 --满足守卫--> 失败
任意 --取消--> 取消
任意 --拒绝(人)--> 拒绝
```

## 计算态

**不存**，每次由派生任务算出来：

```
需要信息 / 需要授权
```

计算态是**覆盖层**。梗阻消失后不是「回到」某个状态，而是重新算一遍，
发现没有梗阻，露出底下的存储态。

## 为什么要分

因为「有子任务在等你补信息」这件事**不是一个可以存下来的状态** ——
它是从数据推导出来的事实。存下来就要维护一致性，必然出错。

# 五、四类各自的计算规则

`COMPUTED_RULES` 是声明式规则表，**数组顺序就是优先级**。

## 目标（`goal`）

用户原话（1.1–1.10，后者成立需前者不成立）：

| # | 规则 | 结果 |
| --- | --- | --- |
| 1.1 | 没采纳 | 未开始（不计算） |
| 1.2 | 没有子任务，或子任务全是未指定 | 提交 |
| 1.3 | 有子任务在处理中或提交 | 处理中 |
| 1.4 | 有子任务需要信息 | 需要信息 |
| 1.5 | 有子任务需要授权 | 需要授权 |
| 1.6 | 有失败且没有任何成功 | 失败 |
| 1.7 | 有任何成功 | 成功 |
| — | 兜底：子任务全是取消/拒绝 | 取消 |

### 1.3 为什么压在 1.4 上面

用户原话：

> 处理中，那么意味着 ai 要继续。你变成需要信息，那做一个停一个？
> 用户需要无人值守。

一条在跑、一条在等你补信息 → 目标显示「处理中」。
「等你」这件事在**子任务那一层**看得见，不需要冒到目标上把整块板变成红色。

## 设计（`design`）

| 规则 | 结果 |
| --- | --- |
| 2.2 有未结束的调研子任务 | 需要信息 |

2.1 / 2.3 / 2.4 是手动规则，不在计算表里。

## 工作（`work`）

| 规则 | 结果 |
| --- | --- |
| 3.3 有未结束的调研或设计子任务 | 需要信息 |
| 3.4 有需要授权的阻碍子任务 | 需要授权 |

**3.3 优先于 3.4**（数组顺序）。

## 记录（`record`）

**没有计算态。** 记录不靠子任务，写出来就等人看。

# 六、人机权限

| 类别 | 采纳 | 领取 | 转成功 | 转失败 | 拒绝 | 取消 |
| --- | --- | --- | --- | --- | --- | --- |
| 目标 | 人 | — | 推导 | 推导 | ✗（1.9） | 人 |
| 设计 | — | — | 人 | 不会失败 | 人 | 人 |
| 工作 | 人 | 人 + AI | 人 / AI（守卫） | 人 / AI（守卫） | 人 | 人 + AI |
| 记录 | — | — | 人 | 人 | — | — |

## 3.5 / 3.6 的守卫

> 3.5 必须有一个失败的「阻碍」子任务或一个失败的「交付」子任务，
>     ai 才可以转化为「失败」。用户转化为失败不受限制。
> 3.6 必须有一个成功的「交付」子任务，ai 才可以转化为「成功」。
>     用户转化不受限制。

```
AI 转失败 → 必须有一条 kind=record 且 status=失败 的 RB 或 RW
AI 转成功 → 必须有一条 kind=record 且 status=成功 的 RW
用户走这两条都不查
```

## 1.9 目标不会成为「拒绝」

要放弃整个目标，用「取消」。

## 1.10 复盘约束

```
失败的工作数 ÷ 3 向下取整 ≤ 成功的复盘数
```

不满足时**不能创建工作子任务**（只拦 AI，用户不受影响）。

### 这不是缺陷，是刹车

我一度把它当成 bug 报上去，理由是它破坏无人值守。**这个判断是错的。**

用户原话：

> 复盘真的复盘对了吗？复盘错了，自动。那就是穷举。多烧钱？
> 你一个东西错三次，那能让你继续吗？路径就错了。

```
AI 失败 3 次
  → 停下来，写一份复盘
  → 等人看这份复盘
  → 人判断：路径对不对？
       对 → 放行，继续
       错 → 这条路径本身错了，不该继续
```

自动放行的后果是：AI 写复盘 → 自己标成功 → 继续用同一条错路径 →
再错 3 次 → 再写一份 → **那就是穷举，而穷举是烧钱**。

**无人值守不等于无人负责。**

# 七、阻碍的语义

## 判据

```
阻碍 = "我无权决定"，不是"物理上过不去"
```

这些**全都是阻碍**，因为它们都该用户拍板：

```
我算出来代价大   → 但我可能算错（O(n²) 可能是唯一解）
我觉得方案烂     → 但用户可能接受
用户说别做了     → 但我不能替用户关掉（取消是完成态，用户决定的）
缺权限 / 缺信息  → 要人给，或者要我去查
```

## 九项理由

```
需要授权：代价过大 / 用户转移话题 / 方案缺陷过大 / 资源被占用 / 缺权限 / 环境不对
需要信息：缺用户信息 / 需要先调研 / 子任务未回收
```

## 阻碍不写解决方式

因为：
1. 你可能根本不知道原因（那就该先派一条调研）
2. 你可能判断错了（代价大 ≠ 真的大）

解决方式只有用户说了「要解决」之后，才在派生任务里写。

## 阻碍 vs 留档

| | RB 阻碍 | RL 留档 |
| --- | --- | --- |
| 什么时候用 | 我现在决定不了，要人拍板 | 这事已经过去，记一笔 |
| 对父工作的影响 | 让它变「需要授权」 | 无 |
| 谁看 | 要人裁决 | 以后踩坑的人 |
