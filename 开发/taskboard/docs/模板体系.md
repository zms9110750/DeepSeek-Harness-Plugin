# 模板体系

> 模板 = 「创建一条事项时要填什么」。
> 文件在 `packages/templates/templates/`（core）和 `packages/extra-templates/templates/code/`（code 域）。

---

# 一、四类 · 十六个模板

| 类别 | core | code 域 |
| --- | --- | --- |
| **目标** | `GU` 用户需求 | `MM` 预期不符 · `FN` 新增功能 · `OP` 项目优化 · `TS` 项目测试 |
| **设计** | `DQ` 提问 · `DC` 决策 | `DI` 接口界面 · `IM` 底层实现 |
| **工作** | `WR` 调研 · `WV` 校验 | `WT` 实现项 |
| **记录** | `RB` 阻碍 · `RW` 交付 · `RF` 复盘 · `RL` 留档 | — |

## core 和 code 的分界

core 是**不受任何开关控制**的地基 —— 关掉所有领域开关，这九条还在。

code 域要开 `code` 开关才有。判据是：**这件事只有代码域有吗？**

- 「接口界面」「底层实现」—— 只有代码有封装，所以是 code
- 「预期不符」—— 只有代码有可验证的约定和文档，所以是 code
- 「阻碍」「交付」—— 写作绘画也有，所以是 core

---

# 二、模板格式

```yaml
name: RB · 阻碍                    # 显示名，编号 + 简短名
default_kind: record               # goal / design / work / record
behavior: block                    # propose / decide / answer / execute / write / block
description: 我决定不了，要人拍板    # 一句话，给面板列表用
domain: core                       # core / code
framed: true                       # 是否带开场说明
dispatch: [goal, design, record, work]   # 能派哪几类子事项
hints:                             # 给 AI 看的提示词，不进 UI
  create: |
    ...
body:                              # 章节，进 UI
  - type: textarea
    id: where
    attributes:
      label: 卡在哪一步
      description: |
        ...
    validations:
      required: true
```

## behavior 六种

| behavior | 含义 | 谁用 |
| --- | --- | --- |
| `propose` | AI 提方案，用户审 | `DI` `IM` |
| `decide` | 让用户在选项里拍板 | `DC` |
| `answer` | 只问一件事，答了就完 | `GU` `DQ` `MM` `FN` `OP` `TS` |
| `execute` | 动手做 | `WR` `WV` `WT` |
| `write` | 只登记 / 成稿，不改东西 | `RW` `RF` `RL` |
| `block` | 登记阻碍，把父工作踢出进行 | `RB` |

## 章节的 type

| type | 说明 |
| --- | --- |
| `markdown` | 只读说明，不占填写位置 |
| `textarea` | 多行文本 |
| `input` | 单行 |
| `[ask, textarea]` | 选择题 + 可自填。`max_picks` 默认 1（单选），99 = 多选 |
| `[rank, textarea]` | 可排序的集合 |
| `[derive, textarea]` | 能派子事项就派，派不了再写 |

**`[a, b]` 的顺序就是默认。** 第一个是主路径。

# 三、core 九条

## GU · 用户需求（目标）

**只有一章。** 用户说了什么，原样抄。

**为什么只有一章**：目标的完成靠子事项推导（状态规则 1.2–1.7），
不靠「什么算做到了」那一章。边界和拆法都是子事项的事。

**提示词要点**

```
不要改写、不要提炼、不要替他总结。
你的提炼会丢掉"他为什么这么说"。
而那句理由往往是后面判断"什么算做到了"的唯一依据。
```

## DQ · 提问（设计）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `ask` 问什么 | textarea | ✅ |
| `why` 为什么要问 | textarea | ✅ |
| `guess` 我的猜测 | textarea | ✅ |
| `options` 能给选项就给 | [ask, textarea] | — |
| `other` 其他 | textarea | — |

**初始状态是「需要授权」，不是「需要信息」。**
答案是**人**给的，AI 不能自己填上然后标成功。

## DC · 决策（设计）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `question` 要定什么 | textarea | ✅ |
| `options` 选项 | [ask, textarea, rank] | ✅ |
| `unknown` 我还不知道什么 | textarea | — |
| `recommend` 我的建议 | textarea | ✅ |
| `other` 其他 | textarea | — |

**选项必须互斥。** 给三个方案，不是给三个方向。

## WR · 调研（工作）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `target` 要查什么 | textarea | ✅ |
| `how` 怎么查 | textarea | ✅ |
| `conclusion` 结论 | textarea | ✅ |
| `evidence` 证据 | textarea | ✅ |
| `other` 其他 | textarea | — |

**`evidence` 改必填了**：调研没有依据就是猜。

**WR 是状态规则 3.3 那个「需要信息」的触发源** ——
父工作下面只要有未结束的调研，父工作就显示「需要信息」。

## WV · 校验（工作）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `target` 验什么 | textarea | ✅ |
| `how` 能自动验 / 只能人工验 | [ask, textarea] | ✅ |
| `result` 实际看到什么 | textarea | ✅ |
| `verdict` 通过 / 不通过 / 部分通过 | [ask, textarea] | ✅ |
| `other` 其他 | textarea | — |

**`how` 和 `verdict` 加了 ask** —— 标签本身写着「二选一」「三选一」，
控件却是自由文本，读的人要自己判断「这算通过没有」。

**校验也要交付。** 就算 AI 验过了，用户也未必认可它的验法：

```
WT 实现项
  └─ WV 校验        ← 验 WT
       └─ RW 交付    ← 验 WV 的凭证（记录层，不再往下）

停在记录层。
```

## RB · 阻碍（记录）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `where` 卡在哪一步 | textarea | ✅ |
| `consequence` **不解决会怎么样** | textarea | ✅ |
| `bypass` 能不能绕 | [ask, textarea] | ✅ |
| `reason` 停下来的原因 | [ask, textarea] | ✅ |
| `next` 下一步最该试的一件事 | [derive, textarea] | ✅ |
| `other` 其他 | textarea | — |

**删了 `why`（为什么过不去）。** 因为你可能完全不知道原因 ——
那就该派一条调研，而不是在阻碍里瞎猜。

**删了 `deliver`（交付）。** 阻碍不产出东西，要有交付说明它装错了类别。

**判据**：阻碍 = 「我无权决定」，不是「物理上过不去」。
详见 [状态规则.md](./状态规则.md) 第六节。

## RW · 交付（记录）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `what` 交付了什么 | textarea | ✅ |
| `where` 在哪 | textarea | ✅ |
| `how` 怎么用 | textarea | ✅ |
| `for` 因为什么交付 | [ask, textarea] | ✅ |
| `verify` 你怎么验过 | textarea | ✅ |
| `not` 没做什么 | textarea | — |
| `other` 其他 | textarea | — |

**`what` 写的是"实体类型"，不是描述。**

```
好：core/index.js 里的 derivedStatus 函数
    一个 mcp 服务，地址 http://127.0.0.1:52311
    一个 cli 程序，入口 bin/taskboard

坏：完成了状态推导的重构

判据：这个东西能不能被单独拿走用。
```

**删了 `stale`（什么时候过时）。** 交付物是活的（mcp 网址、cli 程序），
「什么时候过时」不可预知 —— 能写的只有「怎么验证它还在正常工作」，
而那是 `verify` 的事。

**`for`（由头）**：一条交付挂在工作 A 下面，但用户看到时可能在目标层。
没有由头，他不知道自己为什么在看这个。

**RW 是状态规则 3.6 的唯一解锁条件。**

## RF · 复盘（记录）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `blocked` 为什么受阻 | textarea | ✅ |
| `how_know` 我如何知道要怎么做 | [ask, textarea] | ✅ |
| `confident` 我如何确信下次会成功 | textarea | ✅ |
| `apply` 这条教训该改哪里 | textarea | — |
| `other` 其他 | textarea | — |

**三章全换。** 原来的是 `outcome` / `root` / `lesson` / `deliver`。

**没有 `deliver`。** 复盘可能开子任务去查文档（那是调研），
研究才交付。复盘自己不需要交付。

**`confident` 要写判据，不是"下次注意"**

```
好：下次开工前先跑一遍 X，跑通就说明路径对了
    如果又出现 Y 现象，说明还是同一个根因

坏：下次会更小心

写不出判据 → 说明还没想清为什么失败。
而想不清就继续做，等于用同一条错路径再试一遍。
```

## RL · 留档（记录）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `what` 踩到了什么 | textarea | ✅ |
| `why` 为什么 | textarea | — |
| `disposition` 这条现在什么状态 | [ask, textarea] | ✅ |
| `avoid` 下次怎么避 | textarea | ✅ |
| `other` 其他 | textarea | — |

**`disposition` 是这一条的核心** —— 它允许「不修」：

```
已修      根因消掉了
绕过了    能用，根子还在
没修      记着，以后再说
不是缺陷  意图如此，是乌龙
```

绕过也是解决问题的一种，但根子还在。
如果不写清，下一个踩到的人会以为这里没毛病。

**`why` 不是必填** —— 很多坑真不知道原因。逼着填，AI 会编一个理由，留档反而变成误导。

# 四、code 域七条

## MM · 预期不符（目标）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `what` 什么和预期不符 | textarea | ✅ |
| `expect` 我预期什么 | textarea | ✅ |
| `basis` **这个预期的依据是什么** | textarea | ✅ |
| `actual` 实际看到什么 | textarea | ✅ |
| `repro` 能复现吗 | [ask, textarea] | — |
| `scope` 影响面 | textarea | — |
| `disposition` 怎么处理 | [ask, textarea] | ✅ |
| `other` 其他 | textarea | — |

**这里不预设是 bug。** 「预期」是主观的：

```
你可能：真发现了一个缺陷
       没读文档，约定本来就是这样（乌龙）
       理解了但不同意（那是设计讨论，不是 bug）
```

**`basis` 是防乌龙的那一章。** 依据只有四种来源：

```
文档里写着
既有约定（同类功能都这么做）
用户的明确说法
可验证的规范（RFC / 标准 / 类型定义）

"我觉得应该"不是依据。
```

**`repro` 三档**（不是旧的二选一）：

```
能稳定重现  → 写最小复现
偶发        → 写出现频率
复现不了    → 写"只出现过一次，没有可复现路径"
```

第三档必须留着 —— 下次再出现时能对上就是证据。

**`disposition` 决定后面派什么**：

```
修        派 DC 决策 → 派 WT 实现项
绕        派 DC 决策（绕法 + 代价）→ 派 WT
          另派一条 RL 留档
搁置      本条转「取消」
不是问题  转「取消」
```

**为什么它不适用于绘画**：绘画没有「预期」，只有「感觉」。

## FN · 新增功能（目标）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `want` 要什么 | textarea | ✅ |
| `why` 为什么要它 | textarea | ✅ |
| `concerns` **要考虑什么** | [ask, rank, textarea] | ✅ |
| `not` 这次不做什么 | textarea | — |
| `other` 其他 | textarea | — |

**`concerns` 这一章是核心。** 预置八项：

```
安全性 / 幂等 / 数据丢失 / 并发 / 权限 / 性能 / 兼容 / 可观测
```

**用户不会说这些。你要替他想：**

```
用户说"要能发消息"
  → 立刻有一个安全问题：谁能发、发给谁、发出去收不回怎么办

用户说"要能存档"
  → 立刻有三个问题：重复存档会怎样（幂等）
                   存档到一半崩了会怎样（丢失）
                   能存几个（存档槽）
```

## OP · 项目优化（目标）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `aspect` **优化什么** | [ask, rank, textarea] | ✅ |
| `where` 哪里不好 | textarea | ✅ |
| `target` 优化到什么程度算完 | textarea | ✅ |
| `not` 这次不动什么 | textarea | — |
| `other` 其他 | textarea | — |

**先定 `aspect`，因为不同方向完成标准完全不同：**

```
性能优化   要有数字（基线 → 目标）
语义优化   要有新旧对照 + 迁移方案
可读性     要有"改完之后另一个能看懂"的验证
扩展性     要有"加一件新事要改几个文件"的对比
```

**`target` 必须按 `aspect` 写：**

```
性能：P95 从 800ms 降到 200ms 以下
语义：X 改名为 Y，所有调用点更新，旧的 Y 加 deprecation
可读性：core/index.js 拆成 5 个文件，每个不超过 300 行
```

## TS · 项目测试（目标）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `kind` **测什么** | [ask, rank, textarea] | ✅ |
| `target` 测哪个东西 | textarea | ✅ |
| `standard` 什么算通过 | textarea | ✅ |
| `environment` 在什么环境测 | textarea | — |
| `not` 不测什么 | textarea | — |
| `other` 其他 | textarea | — |

**三种测试合并成一条，靠 `kind` 区分**：冒烟 / 边缘 / 性能 / 回归 / 兼容。

**`standard` 必须可判断：**

```
好：首屏 P95 < 500ms    连续点 10 次不崩    空数据时不报错
坏：性能可以接受        没有明显问题
```

写不出判据的测试跑完也没意义 —— 你不知道该不该放行。

## DI · 接口界面（设计）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `goal` 这次定哪个入口 | textarea | ✅ |
| `exposed` 暴露给谁 | [ask, textarea] | ✅ |
| `naming` 望文生义 | textarea | ✅ |
| `contract` 契约 | textarea | ✅ |
| `behavior` 什么情况下做什么 | [ask, textarea] | ✅ |
| `errors` 出错时怎么办 | textarea | ✅ |
| `breaking` 以后改它会破坏什么 | textarea | — |
| `other` 其他 | textarea | — |

**这是「封装」。** 给使用者看什么，要望文生义，也包括 UX。

**`exposed` 是改名的理由：**

```
最终用户   界面、文案、交互
调用方     函数签名、返回结构、错误码
运维       日志、配置项、监控点
```

> uiux 同样是对用户暴露。api 也是对使用者暴露。

**这里不写实现。** 「用 React 的 X 组件」是错的，「点了之后出现二级菜单」是对的。
实现是 `IM` 的事。

**危险操作要有行为设计：**

```
"删除"不是画个红色就完了，要写清：
  什么情况下出现
  点了之后发生什么（二次确认？可撤销？）
  撤不撤销得掉
```

## IM · 底层实现（设计）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `goal` 这次定哪部分实现 | textarea | ✅ |
| `deps` 用什么库 / 服务，为什么 | textarea | ✅ |
| `wiring` 它们怎么联系 | textarea | ✅ |
| `magic` 一拍脑袋定的数 | [rank, textarea] | ✅ |
| `pressure` 背压 / 限流 / 重试 | textarea | — |
| `swap` 换掉它要动哪里 | textarea | — |
| `other` 其他 | textarea | — |

**为什么和 `DI` 分开：**

> 一个接口设计可以有多个底层实现。是可以否决，切换，替代，底层实现的。

**`magic` 这一章是它存在的理由。** 每个数字写三样：值、依据、推翻代价。

```
缓存 7 天    依据：上游每周更新一次       推翻代价：改一个常量 + 重测
超时 3 秒    依据：P99 是 1.2 秒          推翻代价：调大可能掩盖问题
并发 8       依据：没算过，试出来的       推翻代价：低，随便改

"没算过，试出来的"必须写出来 ——
后来的人才知道这不是深思熟虑的结果，可以随便改。
```

## WT · 实现项（工作）

| 章节 | 行为 | 必填 |
| --- | --- | --- |
| `deliver` 交付 | textarea | ✅ |
| `change` 改动清单 | [rank, textarea] | ✅ |
| `verify` 怎么验证的 | textarea | ✅ |
| `other` 其他 | textarea | — |

**`change` 加了 rank** —— 改动通常有先后依赖（先改 schema 再改渲染器）。

**做完不等于完成。** 要标成功得有一条成功的 `RW` 挂在你下面（3.6）。

# 五、为什么要删掉那 11 个

| 编号 | 名字 | 被谁覆盖 |
| --- | --- | --- |
| `RD` | 缺陷报告 | `MM` 预期不符（登记 + 处置） |
| `WF` | 缺陷 | `MM` + `WT` |
| `WP` | 性能 | `OP` + `TS` |
| `GV` `RS` `WD` `WE` | 写作 4 个 | 用户决定这次不做 |
| `DT` `GA` `WC` `WL` | 绘画 4 个 | 同上 |
| `DB` `GO` `RE` `WX` | general 4 个 | `DB`→`DC`/`DQ`，`GO`/`RE`→`GU`，`WX`→`RW` |

**内容留在** [研究/沙盘/待删模板.md](../../../研究/沙盘/待删模板.md)。

里面有三条值得抢救的**建模判断**：

```
RD.repro   能稳定重现 → 最小复现 / 不能 → 出现频率
           两个都写 = 两个都没写清
           （这个已搬进 MM.repro）
WF.hints   修起来要动好几个地方 → 不是工作，是目标
           （这个还没搬）
WP.hints   动手前必须有一个数字；没有基线就开始改，
           等于把"感觉快了"当成结果
           （这个已搬进 OP.target）
```

# 六、加模板的步骤

1. 在 `packages/templates/templates/`（core）或 `packages/extra-templates/templates/code/`（code）下建 `XX.yml`
2. 顶层字段写全：`name` / `default_kind` / `behavior` / `description` / `domain` / `framed` / `dispatch`
3. `hints.create` 写清「这一条什么时候用、什么时候不该用」
4. `body` 每章至少一个 `required: true`
5. 在 `packages/core/index.js` 注册：
   - `TYPES` 数组加编号
   - `TYPE_TO_KIND` 加映射
   - `TYPE_NAMES` 加中文名
6. 跑 `node --test test/taskboard.test.mjs`
