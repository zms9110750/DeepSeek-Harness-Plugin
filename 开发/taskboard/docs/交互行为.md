# 交互行为

> 「行为」在代码里叫 action。它决定**这一章能不能跟用户互动、怎么互动**。
>
> 代码：`packages/actions/index.js`

---

# 一、先分清两个「行为」

这个词在项目里有两个意思，混起来会说不清：

| | 意思 | 在哪 |
| --- | --- | --- |
| **模板的 behavior** | 这一个任务**要用户做什么**（提方案 / 拍板 / 回答 / 执行 / 登记 / 阻塞） | 模板顶层 `behavior:` |
| **章节的 action** | 这一章**用什么控件**（文本 / 只读 / 选择 / 排序 / 派发） | 章节 `type:` |

这份文档讲的是第二个。第一个见 [模板和章节.md](./模板和章节.md)。

---

# 二、五个内置 action

只有五个。少是有意的 —— 每加一个都要写渲染器。

| action | 干什么 | 用户能做的动作 |
| --- | --- | --- |
| `text` | 一段可编辑文本 | 打字（**标了 `aiWritable` 才能写进展**） |
| `markdown` | 只读富文本 | 看，不能改 |
| `ask` | 从选项里挑 | 点选项 / 自己填 |
| `rank` | 排先后 | 拖 |
| `derive` | 派生派生任务 | 选模板，建子卡 |

## text

```yaml
- type: textarea
  id: want
```

在代码里 `textarea` 是 `text` 的别名。它是默认值 —— 不写 `type` 就是它。

**什么时候用**：内容是从零开始写的，没法枚举。
比如「用户原话」「为什么过不去」「交出去了什么」。

**`row` 控制高度**，默认 3。

### `aiWritable` —— 让这一章变成「进展」

默认 `false`。**任务一被采纳，整个正文就锁死，谁都不能改。**

置 `true` 之后它变成「进展」：

```
AI 能写
用户也能写
任务采纳之后照样能写
终结（成功/失败/取消/拒绝）之后也能写
```

**为什么是 text 的一个属性，不是新 action**：

因为文本框前面本来就要有 `label` / `description` 说清"这是啥"。
新开一个 action 只是换个名字，其余全一样 —— 白白多一个名字要记。

**什么时候用**：

这一章的内容是**随时间变化的**，而不是"填一次就定"。

判断标准：**这件事在任务被采纳之后还会变吗？**

```
会     → 置 aiWritable: true
不会   → 保持默认（否则整份正文就全开放了）
```

典型用途：AI 自己定的阶段目标、阶段性进展记录、卡住时的临时说明。

**写它的工具是 `task_progress`**，不是 `task_update`：

```
task_update    有锁，只有「未指定」能改
task_progress  无锁，采纳后、终结后都能写
```

实测：

```
① 已采纳状态，写标了 aiWritable 的章节     ✅ 通过
② 写没标 aiWritable 的章节                ✅ 被拒
③ 终结态（成功）之后还能写                 ✅ 通过
```

## markdown

```yaml
- type: markdown
  attributes:
    value: |
      这一份只写"用户要什么"。
```

**只读**。用户改不了，但它占位置、能显示格式。

**什么时候用**：开场说明、章节之间的分隔、注意任务。

**它不是「提示词」** —— 提示词在 `hints:` 里，AI 看人看不到。`markdown` 是给人看的。

## ask

```yaml
- type: [ask, textarea]
  id: reason
  attributes:
    max_picks: 1
    options:
      - 需要授权 · 代价过大
      - 需要授权 · 缺权限
```

**五个里最复杂的一个。**

`max_picks` 决定单选还是多选：

```
1      单选
99     多选
```

**自填框永远在。** 用户想答选项之外的，直接写。
这是刻意的 —— 选项永远不可能穷尽，留个口子比堵死强。

### `[ask, textarea]` 这个写法

写在方括号里的意思是「这一章接受这几种 action」，**第一个是默认**。

所以：

```
[ask, textarea]     → 默认渲染成选择题，也能退化成文本框
[textarea, derive]  → 默认渲染成文本框，也能派派生任务
[derive, textarea]  → 默认派派生任务，派不出去才写文字
```

**顺序有意义。** 它表达「主路径是哪条」。

### ask 装了两类东西

这是目前最含混的地方：

| 类型 | 选项从哪来 | 例子 |
| --- | --- | --- |
| **封闭词表** | 模板里写死 | `RB.reason` 九项、`WV.verdict` 三档、`RL.disposition` 四档 |
| **实例选项** | AI 临时生成 | `DQ.options`（给用户挑）、`DC.options`（方案） |

两者共用 `ask` 这个标签，作者分不清自己写的是哪种。

**待定：要不要拆成 `choose` / `options` 两个 action。**

## rank

```yaml
- type: [rank, textarea]
  id: options
  attributes:
    items:
      - title: 方案 A
        placeholder: 写代价
```

**必须提供 `items`。** 不提供就渲染成空白 —— 这是踩过的坑，
`IM.magic` 和 `WT.change` 曾经因此一直显示空白，没人发现。

**目前只在 `DC.options` 用**，因为那里确实要比较方案优先级。

### 为什么其他四处不用它了

原来有 5 处用 `rank`，核实后**零处需要全序**：

```
OP.aspect   要的是"哪个决定验收"      → 一个指针就够
TS.kind     要的是"哪个决定放行"      → 同上
FN.concerns 要的是穷举（全部都要考虑）  → 不需要排序
IM.magic    要的是理由               → 写在文字里
WT.change   要的是执行顺序            → 写在文字里还能写原因
```

**排序表达「名次」，我们要的是「谁说了算」。** 前者要全链，后者只要一个指针。

所以改成 `aspect`（多选）+ `aspect_primary`（单选）。

## derive

```yaml
- type: [derive, textarea]
  id: next
```

**它不是一个「栏位」，是一个动作。** 点它 → 选模板 → 建子卡。

放在 `body` 里其实是偷懒：让表单承担了派发逻辑。

**什么时候用**：这一章的产物应该是**派生任务**而不是一段文字。
比如「怎么拆」「下一步该试什么」。

# 三、渲染流程

```
模板 YAML
  ↓  parse-template.js      解析章节定义
  ↓  compiler.js            编译成 mdx 字符串
mdx（如 <Ask key="reason" options={[...]} picked={[]} />）
  ↓  mdx-runtime.js         渲染成 DOM
界面
```

## 为什么中间要过一层 mdx

因为渲染器要能**被换掉**。现在 `mdx-runtime.js` 是一份实现，
但它只认 mdx 这一个中间格式 —— 换个渲染器只要认同一份 mdx。

## 参数只当字面量

**所有参数都用 `JSON.stringify` 塞进 mdx**（`lit()` / `attr()`），
从不拼进 `{}` 表达式。

```js
'<Ask key=' + lit(key) + ' options={' + lit(options) + '} />'
```

为什么：拼表达式等于让模板内容变成可执行代码。一个填错的引号就能把界面搞崩。

## key 写在 mdx 里

```
<Ask key="reason" ... />
```

**章节身份从标签自己身上读，不按「第几个」猜。**

以前的实现是按位置对齐的（`keys[index]`），一旦标签数和 keys 数对不上
（`body.want = null`、章节缺 `action`、旧字符串正文），
之后每一章都错开一格 —— **用户改 A 章，值写进 B 章，静默生效**。

# 四、加一个 action 要改哪

1. `packages/actions/index.js` 里 `defineAction({ name, schema, ... })`
2. `packages/actions/check-body.js` 加校验
3. 渲染器里加对应组件（`mdx-runtime.js` 的 `MDX_COMPONENTS`）
4. 模板里才能用 `type: 你的名字`

**没有第 3 步的话，模板能过校验但渲染成灰卡。** 这是设计好的 ——
运行时才发现的问题比编译期报错更贵，所以灰卡要显眼。
