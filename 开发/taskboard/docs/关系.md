# 关系

> 任务之间怎么连。父子是一棵树，关系是跨树的边。
>
> 代码：`packages/core/index.js` 的 `RELATIONS`、`linkPairs`、`cascadeClose`

---

# 一、两套结构，别混

```
父子   一棵树。一个任务只有一个 parent。
       它决定"谁是谁的下属"，也决定状态推导。

关系   links 里的边。可以有任意多条、指向任意地方。
       它决定"谁影响谁"，但不参与状态推导。
```

**父子不是关系的一种。** 父子管层级，关系管牵连。

| | 父子 | 关系 |
| --- | --- | --- |
| 一条能有几个 | 1 个 parent，N 个 child | 任意多 |
| 存在哪 | `task.parent` | `task.links` |
| 影响状态推导 | ✅（目标由派生任务推导） | ❌ |
| 能否跨树 | ❌ 只能在自己的树里 | ✅ 可以指向任何任务 |

---

# 二、六种关系

三个维度决定一种关系：

```
① 有没有方向
② 有没有行为（阻断 / 级联）
③ 影不影响状态
```

| 类型 | 方向 | 行为 | 典型用法 |
| --- | --- | --- | --- |
| **依赖** | 有向 | 阻断领取 + 上游失败则下游取消 | A 做完才能做 B |
| **相关** | 无向 | 无 | 一期 / 二期、同类问题 |
| **约束** | 有向 | 阻断领取（**宽松：只警告**） | 查资料被"没有梯子"约束 |
| **参考** | 有向 | 无 | 做这事时该看那条记录 |
| **取代** | 有向 | 旧转拒绝 + 依赖转移 | 新方案替代旧方案 |
| **派生** | 有向 | 无 | 父子结构（就是 `parent` 字段） |

## 依赖 vs 约束 —— 都是「阻断」，但硬度不同

```
依赖   硬的。上游没做完，下游领不了。
约束   软的。只警告，不硬拒。
```

为什么约束要软：约束常常是「有这件事，但你可以先不管」。
硬拒会把正常用法挡掉。

## 约束 vs 阻碍 —— 最容易混的一对

用户明确区分过：

> 约束，是一个关系。阻碍，是一个性质，他可没说阻碍谁啊。
> 不同的事情也可以被一个无关的东西阻碍。例如搜什么东西，然后约束于没有梯子。

```
阻碍（RB）  任务的性质       "我被卡住了"，自身不指向谁
约束（links）两个任务之间的关系  可以跨树指向一件完全无关的事
```

所以：

- **阻碍**是**一个任务**（`kind: record`），一出现父工作变「需要授权」
- **约束**是**一条边**，存在 `links` 里，不产生新任务

## 派生是遗留字段

父子结构才是主路径。`派生:X` 只用于老数据兼容。

**但级联还认它** —— `cascadeClose` 会顺着 `派生` 链把下游取消。
所以别轻易删。

# 三、写法

存在 `task.links` 里，**逗号分隔的字符串**：

```
依赖:WI-01, 依赖:WI-02, 相关:DC-03
```

格式是 `类型:目标编号`。

## 为什么要写成字符串不用数组

历史原因：最早存在 JSONL 的一行里，字符串最省事。
**现在这是技术债** —— 数组更好处理。但改动会牵到存储格式，一直没动。

**判断依据**：如果你在改关系相关的代码，遇到字符串拼接的别扭，
可以提出来重构成数组。

# 四、两类行为

## ① 阻断领取（依赖 / 约束）

`依赖` 是硬阻断：

```
A 依赖 B，B 没完成   →  A 领不了
                     →  报错要说清"依赖 B 还没完成（当前状态）"
```

`约束` 是软警告：

```
A 约束于 B，B 还没做   →  能领，但提一句
```

**为什么有这个区别**：「依赖」是逻辑上必须先有；
「约束」是「最好先看看」，但你可以硬上。

## ② 级联取消（依赖 / 派生）

```
上游失败 / 取消 / 拒绝
  →  下游全部取消（递归，防环）
```

**只有失败/取消/拒绝会级联。成功不级联** —— 上游做成了，下游照常可以领。

这条规则的理由：上游没做成，下游的前提就不存在了；上游做成了，只是解除了一个前提。

## 取代

```
新方案被采纳（提交）
  →  旧的 links 里写了「取代:旧编号」的那些，直接转「拒绝」
  →  旧的依赖关系转移到新的
```

用途：改方案的时候不用手工去关掉旧的那张。

# 六、这块的已知问题（还没改）

按重要性排：

## ① `links` 是字符串不是数组

拼接和解析到处都有，容易出错。想改，但牵到存储。

## ② `派生` 和父子并存

父子才是主路径，`派生` 是遗留。两套并存会让人不知道该用哪个。

## ③ 关系的界面很弱

现在只能在详情页看到一串 `依赖:WI-01`，没有可视化。
科技树画的是**父子**，不画关系边。

**这可能是最该改的** —— 关系是跨树的，恰恰最需要图。

## ④ 没有关系的反向索引

想知道「谁依赖我」，得把所有任务的 links 都扫一遍。

## ⑤ `约束` 的软警告怎么呈现，还没定

现在是报错文本里提一句。更好的做法大概是界面上标一下。
