## 分包依据

一个开关 = 一个**可替换的实现领域**。判据按优先级：

1. **能回答「关掉之后怎么变」才配拥有开关。** 关掉它若等于「没人能调核心」，那它不该有开关。
2. **桥接只在「对端不可控」时成立。** 模型和用户的协议是固定的，所以要桥接（⑨⑪）；浏览器是我们自己发布的，不需要。
3. **单独打开没用 → 不单独成包。**（⑩ 的提供层与两个入口）
4. **强依赖、不可解耦的进核心。**（⑧）
5. **能靠 `register()` 扩展的，不做成插件替换。**（③ 里的分类与模板靠注册加内容）
6. **机制不可谈：包级 `inject` 环 = 死锁。**（③ 的四块必须同包）
7. **不设数量上限。** 数量由上面六条推出。

**服务名是对外契约，包名不是。** 替换品必须提供同名服务才能接上。

## 已经取消的

| 原来的 | 现在 | 理由 |
| --- | --- | --- |
| `command`（接口面，浏览器可调） | **取消** | 浏览器是自有终端，可破坏性更新，自己就能桥接；接口面就是核心的 public 方法。桥接层没有开关语义 —— 关掉它等于没人能调核心 |

---

## 三条硬规矩

1. **patch 里的条目数 = 插件包数（11）。** 一个插件包可以包含多个开发期模块。
2. **上层只通过服务调用下层，不 import 实现。** 唯一例外是纯数据类型与类型契约。
3. **`core` 不 import `ui` / `ai-tool` / `dsh-command`。** 方向是它们依赖 core。

## 层次

```
0 层   ① store   ② action   ③ types   ④ relation   ⑤ search
1 层   ⑥ workgroup(需 ③)      ⑦ taskcard(需 ③④)
2 层   ⑧ core(需 0–1 层全部)
3 层   ⑨ ai-tool   ⑩ ui   ⑪ dsh-command(需 ⑧)
```

0 层五个包**互不依赖**，可以并行开工。
