## 二、已确定的语义

### 2.1 空间 = 集合，持有成员

- **卡不知道空间** —— 卡上**没有**空间字段【用户指令，2026-11-01 04:05】
- **归属由容器的成员关系表达**
- 容器**不关心卡里有什么**

【推断】因为一空间一库，「成员关系」在物理上就是**卡属于哪个库**，不需要另存一张成员表。**⇒ 成员关系是存储边界，不是数据。**

### 2.2 用户创建 + 命名 → 清洗成 id

- 用户手动填名字【用户指令，2026-11-01 >05:07】
- 名字**经清洗**变成 id / 文件名
- **重名由清洗消解**（不是拒绝创建）【用户指令，2026-11-01 05:18】
- **改名不支持**（见 ① 文档 2.7，含「用户起名没有第二次机会」的知情项）

**⚠ 术语区分（防误读）**：

| 术语 | 属于谁 | 含义 |
|---|---|---|
| **工作空间** | 任务板 | 用户创建的容器，一个 = 一个 `.db` |
| **子工作区** | **dsh 之外、另一个 mod**【用户指令，2026-11-01 >05:18】 | agent 工作区的子路径 |
| **额外工作区** | 同上 | 另一个 mod 的概念 |

**⇒ 任务板的工作空间没有层级结构。** 用户原话：「这没有层级结构，是工作区的元数据。」

### 2.3 一个空间一个 `.db`

`<dshHome>/taskboard/<workspaceId>.db`。归档的移进 `archive/`。

**⇒ 迁移 = 拖一个文件**【用户指令，2026-11-01 04:05】。空间元信息存在该空间自己的 `.db` 里，拖走文件即带走全部信息（含名字、含工作区元数据）。

### 2.4 归档

- **默认列表不含归档**；「显示已归档」才列出
- **归档可取消**
- 实现 = **移进 `archive/` 子目录**（关句柄 → `rename`）
- 归档**不是**只读：归档空间的文件仍是普通库，可打开读写

【推断】选「移目录」而非「`meta` 布尔标记」，因为：`meta` 布尔让**默认列表也要开 N 个库**才能过滤；移目录让**归档在物理上就不在默认扫描路径上** —— 这是「永远不看归档 + 懒加载」的**结构性**保证，而不是代码纪律。

### 2.5 无删除入口

- **只能归档**【用户指令，2026-11-01 >05:07】
- **物理删除由用户自己在文件系统做**
- **这是「数据重要的标准处理方式」，是正面设计，不是「暂不实现」**

【推断】这不是「非目标、成本高」，而是**刻意不提供**。措辞不能混。

**连带结论**：「删空间时成员卡怎么办」这个问题**不存在** —— 用户物理删文件时，整库连同卡一起没了。

### 2.6 卡不能跨空间移动

- 【用户指令，2026-11-01 04:20】卡归属空间，不能移动
- 【用户指令，2026-11-01 05:28】**卡只能属于一个空间**，连关系都不能跨工作区联系

**⇒ 成员关系一次性写入，此后不可变更。**

**⚠ 关键约束**：**若提供「移除成员」+「加入成员」的组合，那就是变相移动** ⇒ **不提供。**

**⇒ 成员管理 API 只有「创建时加入」，没有移除。**

### 2.7 当前空间指针：会话级

- **每个会话各记各的当前空间**【用户指令，2026-11-01 04:53】
- **多个会话可指向同一个空间**（不独占）
- **空间全局可见** —— 所有会话都能看到、访问所有工作空间；「当前」只是「这个会话正看着哪个」，**不是权限或数据隔离**
- 存 **`_global.db`**（store 的 `globalKv`），key 含不透明 sessionId

【推断】用户给的理由（上下文长了 AI 变钝、开新会话继续做）说明这是**高频工作流机制**，不是配置项。

**⑥ 提供的接口（⑥ 不抛业务错、不出文案）**：

```ts
resolveCurrent(sessionId):
  | { status: 'none' }                        // kv 里从未有该 session 的键
  | { status: 'ok', workspaceId: string }     // 键存在且 db 存在
  | { status: 'stale', lastWorkspaceId }      // 键存在但 db 不存在
```

- **报错策略归 core**（「无当前空间则报错」是 core 的事）
- **`stale` 只可观察一次**：读时发现悬空 → 返回旧值 + 幂等删键。**下一次读就是 `none`**
- **删键失败时仍返回 `stale` 并保留键**（不假装成功）⇒ **`stale` 可能重复出现**，core 文案要能重复展示
- **代价为零**：旧 id 本来就在 kv 里，读时顺便拿到，**不需要额外历史表**

### 2.8 空间元信息存该空间自己的 `.db` 的 `meta` 表

存放内容：
- `name`（最终显示名，清洗+去重后的结果）
- （可选）`nameRaw`（用户最初输入，仅溯源，**不参与显示**）
- `aiWriteGrants`（见 2.9）

【推断】元信息跟着空间文件走 ⇒ 拖走一个 `.db` 带走名字与授权。**这与【用户指令，2026-11-01 04:05】「迁移拖文件」一致。**

### 2.9 子工作区 / 额外工作区：只存不执法

【用户指令，2026-11-01 >05:18】**任务板只储存这个元数据，不限制行为。**
【用户指令，2026-11-01 >05:18】**他没有行为，但是在 ui 上面是用户可以读写更改的。**

**⇒ 四层拆开（这是最容易混的地方）**：

| 层 | 有/没有 |
|---|---|
| **存储**（任务板存这组数据） | ✅ **有** |
| **UI**（用户可读写更改） | ✅ **有** |
| **行为**（检查越界、限制路径、权限判断） | ❌ **没有** |
| **功能本身**（子工作区如何生效） | ❌ **二期另一个 mod** |

**「没有行为」≠「没有交互」。**

**目的**：【用户指令，2026-11-01 >05:18】「今天的工作区首先要**为了兼容而留下这个数据的入口**」⇒ 这是**为兼容留存**，不是「顺便存一下」。

**结构**（存在 `meta` 里，一个键，值是不透明 JSON 对象）：

```json
{
  "workspaceRoot":   "X:\\temp\\dsh\\开发\\taskboard2",
  "subWorkspace":    "X:\\temp\\dsh\\开发\\taskboard2\\_scratch",
  "extraWorkspaces": [
    { "path": "X:\\temp\\dsh\\其他项目", "access": "read" },
    { "path": "X:\\temp\\dsh\\某子目录", "access": "exclude" },
    { "path": "X:\\temp\\dsh\\另一个",   "access": "readwrite" }
  ]
}
```

| 键 | 中文术语 | 形态 | 权限 |
|---|---|---|---|
| `workspaceRoot` | 工作区 | 单值字符串 | 只读（固定） |
| **`subWorkspace`** | **子工作区** | **单值字符串** | 可写（固定） |
| `extraWorkspaces` | 额外工作区 | **数组，每项是对象** | 每项自带三态 |

**三态**：`read` / `readwrite` / `exclude`。
【用户指令，2026-11-01 05:28】`exclude` 的语义是**按优先级覆盖**（「优先级高的可能是优先级低的一个子目录，所以可能排除读写」）—— **显式撤销**某路径权限，不是「不存在」。

**为什么子工作区没有权限字段**【实现判断】：它的权限**语义已固定**（用户原话「这个路径里面 ai 可以写」）⇒ 不需要第二种可能。而额外工作区是**独立引入的外部路径**，可能与 `workspaceRoot` 形成覆盖关系 ⇒ 才需要三态。**不对称来自被描述对象的性质差异，不是设计不一致。**

**⑥ 不做的事（「没有行为」的精确边界）**：
- ❌ 不检查 AI 有没有越界
- ❌ 不限制任何路径
- ❌ 不做权限判断
- ❌ 不校验路径是否存在
- ❌ 不校验是否绝对路径、是否在子路径关系上
- ❌ 不检查「子工作区是否真的在 `workspaceRoot` 之下」
- ❌ 不提供默认值、不自动推导

**⇒ ⑥ 是这组数据的保管员，不是执法者。**

**为兼容留入口的落点**：⑥ 存的是**不透明 JSON 对象**，不检查有哪些键。未来 mod 需要什么字段，塞进这个对象即可，**⑥ 一行不改**。

【用户指令，2026-11-01 05:28】「至少还要存…」——「至少」意味着字段可能更多，**⑥ 不需要知道全部字段，只需要保证容器装得下。**

### 2.10 域（domain）：纯展示

【用户指令，2026-11-01 12:48】「domain 保持纯展示」

- **不产生行为**
- **中文，不校验语言**

## 三、我的判断与实现选择

### 3.1 ⑥ 不直接碰 SQLite

【实现判断】⑥ 只经 ① store 的 public 面访问存储。否则 ⑥ 会绑死 SQLite，「可替换实现领域」的独立性就没了。

### 3.2 归档的物理动作经 ① 的 `archiveDb` / `unarchiveDb`

- **业务判断归 ⑥**（何时归档、UI 怎么做）
- **物理安全归 ①**（关句柄 → `rename`）
- 【Lead 指令，2026-11-01 13:20】命名 `archiveDb` / `unarchiveDb` 已确认

【实现判断】理由：① 掌握库句柄缓存，只有它知道「该关哪个句柄」。**若让 ⑥ 直接 `fs.rename()`，会在库还开着时移动文件** —— WAL 边车留在原地，库可能无法恢复。

### 3.3 成员关系不单独存表

【实现判断】一空间一库 ⇒ 成员关系 = 卡在哪个库里。**不需要成员表、不需要成员 id 列表。**

【推断】这与「卡不能跨空间移动」互相锁定：既然不可移动，成员关系天然是「一次性写入」的存储边界事实。

### 3.4 列表顺序由 ⑥ 决定

【实现判断】`.db` 文件名是清洗后的 id，Windows 上不区分大小写 ⇒ **目录读取顺序不是稳定语义**。⑥ 若要稳定顺序（比如按名字），需排序。**但空间名存在各库 `meta` 里，排序 = 开 N 个库**（见 ① 文档 6.4 缺口 B）。

## 六、需要与其它成员对齐的

### 6.1 与 ① store

| 项 | 约定 |
|---|---|
| ⑥ 是否直接碰 SQLite | **不碰**，只经 ① 的 public 面 |
| 空间元信息 | 存该空间 `.db` 的 `meta` 表（`readMeta` / `writeMetaKey`） |
| 归档物理动作 | 调 ① 的 `archiveDb` / `unarchiveDb` |
| 列空间 | 调 ① 的 `listWorkspaces()` → `{id, archived}[]` |
| 当前空间指针 | 存 ① 的 `globalKv`（`current:<sessionId>` → workspaceId） |
| 库路径 | 调 ① 的 `dbPath(wsId, archived)` |

**⚠ 一条需要与 ① 共同确认的边界**：① 的 `globalKv` 已从「不公开」改为**公开**（理由：⑥ 是独立包，只能经 public 面访问）。⑥ 是它唯一的业务使用者，**靠约定而不靠 API 削减来防止「谁都能改当前空间」。**

### 6.2 与 ⑧ core

| 项 | 约定 |
|---|---|
| **机制在 ⑥，策略在 core** | ⑥ 只返回状态（`none` / `ok` / `stale`），**不抛业务错、不出文案** |
| 「无当前空间则报错」 | **归 core** |
| `stale` 可重复出现 | ⑥ 删键失败时仍返回 `stale` 并保留键 ⇒ **core 文案要能重复展示**，不做一次性假设 |
| 空间名显示 | core 若要在 UI 显示空间名，**走 ⑥**，不直接调 ① |

### 6.3 与 ⑦ taskcard

| 项 | 约定 |
|---|---|
| 卡上是否有空间字段 | **没有**（卡不知道空间） |
| 卡能否跨空间 | **不能**，连关系都不能跨【用户指令，2026-11-01 05:28】 |
| 成员关系 | 一次性写入，⑧ 负责「创建时放进哪个库」；⑥ 不提供移除/加入组合 |

### 6.4 与 ③ types

| 项 | 约定 |
|---|---|
| 领域（domain） | **归 ③**（模板的一个维度），⑥ 不建领域注册表 |
| 空间 id | ⑥ 的清洗规则与**卡编号规则各自独立** —— 一个是用户可读名字的洗白，一个是生成器产出，语义不同 |
| 编号 | ③ 是纯函数，⑥ 不参与 |
