## 二、已确定的语义

### 2.1 六种边

依赖 / 取代 / 约束 / 相关 / 参考 / 派生。

**【推断】** 早前「派生是否保留」的疑问已经关闭 —— 依据 1.3，`派生` 不是第七种边、也不是多余标签，
它就是**父指针本身**，读的时候反向解读。因此六种里 `派生` 与「父子结构」是同一份数据，不是两份。

### 2.2 方向

**只有 `相关` 是双向的**（1.4）。其余五种（依赖 / 取代 / 约束 / 参考 / 派生）为有向。

**`参考` 单向已由用户点名确认**（1.15①，`【用户指令，2026-11-01 06:03】`
「参考 是单向的。相关，是双向的。」）—— 此前只是我的字面推断，**现在是裁决**。

**【推断】** 「有向」按字面理解为两边语义不对等；用户没有说明是否允许两边各存一条反向边。
**但 2.18 提供了反例式的答案**：父指针只存一侧（子存父），反向由内存计算 ——
**⇒ 有向边默认只存一侧、反向靠计算。** 这是我的推断，非用户明说。

### 2.3 `派生` 的三条拆解（来自 1.3，非推断）

1. **存储**：只有子任务记「我的父任务是谁」；父任务不储存子任务清单。
2. **展示**：渲染图与专有名词都说「父任务派生子任务」—— 展示方向与存储方向相反。
3. **结论**：不额外引入「父任务」关系类型；`派生` 即该关系。

### 2.4 边的引用方式 = 编号（**已裁决，永久成立**）

依据 1.7（编号在同一工作空间内唯一、卡归属空间且不能移动）**以及 1.9 的直接裁决**
（`【用户指令，2026-11-01 05:28】`「一个卡连关系都无法跨工作区去联系」）：

- 一条边指向另一张卡时，**只写编号**。
- **不需要 `(空间, 编号)` 复合键。** 因为边不可能跨空间，编号在同一空间内已唯一，
  容器内解析即可。
- **【推断】** 此前担心的「编号撞名」在跨空间被禁止后**不成立** —— 同一空间内编号唯一，
  不同空间的编号根本不可能出现在同一条边上。
- **状态**：此项**不再是待裁项**。原 5.1 已关闭（见 4.6）。
- **⚠ 原「隐患」已消解（5.14 已裁决）**：提交前确实没有编号，但**提交前也不写任何边**
  （卡只在内存、尚未纳入管理）。取代边在**采纳时**才执行，那时双方都已是草稿、都有编号。
  ⇒ 「边的持有者没编号」这种情况**不会出现**。

### 2.5 只算不写（先前立场，本轮无新时间戳）

本层产出**计划**：哪些卡、从什么变到什么、因为哪条边。写盘与事务由 ⑧ core 执行。
理由（先前提过，非本轮原话）：边算边写是四段平行实现各写一遍 BFS，改一处不会提醒另一处；
且「根失败收下游、根成功不收」只有在计划上才可断言。

## 三、我的判断与实现选择

以下**全部是我的判断**，不具用户授权效力，可被随时推翻。

### 3.1 传播的走法【实现判断】

- 起点：某张卡的状态变了（关闭 / 失败 / 取消 / 拒绝 / 被取代 …）。
- **依赖走反向**：找「谁在等我」。
- **父子走向下**：找直接的子卡（即 `派生` 的反向解读）。
- **只收进行态**：草稿与终态不动，走到即停。
- **成功不收**：失败 / 取消 / 拒绝收依赖方；成功结束不收 —— 我做成了，等我的照常可领。
- **环**：遍历带「已访问」集合，同一张卡第二次走到即并入已有结果。
- **先算清单后落盘**：第一步只读产出计划；第二步交 ⑧ core 执行。
  【已按 3.6 修正】执行 = **在一个事务里对多张卡做 `UPDATE`**，不是「写整库」。见 3.6。

### 3.2 取代的顺序【推断，触发时机已由用户裁决】

**必须先转移依赖，再判旧卡死刑。** 反序的后果不是「慢」，而是**结果不同**：

- 旧卡一旦转成拒绝 / 取消，立刻触发「上游死了 → 收下游」；
- 那一刻依赖方还指着旧卡，会被当作死路一起收掉；
- 而它们本该改指新卡、活下来。

**【已裁决，1.13】触发时机 = 采纳时，不是提交时**：

> 【用户指令，2026-11-01 05:52】
> 取代关系是不可编辑的。然后这个卡**采纳了，才执行取代**。

**⇒ 顺序不变，触发点变了**：卡被**采纳**的那一刻执行取代流程（先转移依赖 → 再判旧卡死刑），
而不是在「提交 / 落库」时。这点已不再是【待澄清】。

**⚠ 仍需注意（推断）**：①「采纳」与「提交」在九态里是不同的状态值（草稿 → 提交），
所以「采纳时才执行」意味着**执行点在状态转移的某个确定时刻**；具体挂在哪个转移边，
属 ③ types 的转移规则，④ 只声明「在采纳时被调用」。

**⭐ 新增一条独立佐证（来自 06:13，比 05:52 更硬）**：

> 【用户指令，2026-11-01 06:13】
> 只有采纳了（非草稿的，也就是冻结了的任务卡），才能出现在关系这个的候选里面。
> 也就是说，草稿的关系也不能写草稿。

【推断，但推理链很短】若取代的**转移**在 fork 时（新卡还是草稿）执行，

### 3.3 一个完整场景：A 依赖 B，B 失败【设想】

3. **算**：进行态 → 收下并继续沿它的边外走；草稿 / 终态 → 跳过且不再往下。全程只读，产出计划。
4. **交**：计划给 ⑧ core —— 【已按 3.6 修正】是**一批卡的 `UPDATE`，在一个事务里执行**，

5. **结果**：B 失败；进行态的 A 及其进行态的依赖方被收；草稿与已终态不动。

2. **实现简单**：不复制、不做一致性协议、不需要在每次查询前取快照。

3. **张力处理**：共享带来「物理上可误改」的风险，用**只读约束**（`Object.freeze` 或 TS 只读类型）

### 5.20 「取子任务」归 ④ 还是 ⑤ —— **【实现判断】：归 ⑤**

2. **符合职责划分**（1.14）：⑤ = 筛选过滤；这正是筛选。
3. **实现最简单**：不新增能力、不改变 ④ 的数据来源。

**⚠ 但「列子任务」≠「沿边展开」**（与 1.12「不展开」不冲突）：

### 5.25 草稿卡没有子任务（**准入保证的不变量，含 fork 例外，非用户直述**）

**推导链**：

1. `parent` 由**子任务**持有，指向**父卡** ⇒ `parent` 这条关系的**目标**是父卡。
2. 06:13「草稿的关系也不能写草稿」⇒ **目标不能是草稿**。
3. ⇒ **任何人不能把 `parent` 指向一张草稿卡**。
4. ⇒ **草稿卡没有子任务。**

**⚠ 这是「不可能有」，不是「不显示」** —— 区别重要：

- 写成「不显示」会让人以为有一层读时过滤；
- 写成「不可能有」就是**准入保证的不变量**，下游可以放心假设。

**⚠ 但必须写成「稳态」，不是无条件不变量**（mod-kind 指正）：
fork 时若"未完成子任务要转移"，新卡（草稿）会成为这些子任务的父 —— **这是唯一例外**，
且它靠「**转移在采纳时才写**」（3.2）规避，那时新卡已非草稿。

**⇒ 精确表述**：
> **稳态下草稿卡没有子任务；fork 转移在采纳时才建立这些父子边，因此不破坏该不变量。**

**⚠ 我上一稿写错了方向，此处改正**：我曾写「草稿卡的子任务列表里理论上不该出现草稿子任务」——
**方向反了**：禁的是「**父卡是草稿**」（目标端违规），不是「子任务是草稿」（源端合法）。
修正来自 mod-kind 的指正。

**⭐ 对本模块的简化（推论）**：
④ 的级联「向下收子任务」这一步**不会遇到草稿父卡** ⇒ 「只收进行态」在这条路径上不会因草稿而漏判。

**⚠ 理由要说准**：**不是因为"草稿没有子任务"这个不变量，而是因为「写入父子边时父卡恒为非草稿」**
（fork 转移在采纳时写、其余写入受准入保证）。**这个理由更结实**，且在采纳事务内也成立
（转移那一刻新卡刚变成非草稿）。

### 5.26 一条独立原则：可推导的东西不要落库（**推断，非用户原话**）

**由两处独立证据归并而出**：

1. 本文 2.18 / 4.10：**反向边只在内存算，不持久化**（用户：只存父任务）。
2. mod-kind 的 `deriveInactive`：**计算态不可持久化** —— 落库就与取代边形成两处真值。

**⇒ 【推断】同一条原则：凡是能由别的真值推导出来的，不要落库。**

**理由（我的判断）**：两份真值必然漂移，且漂移是静默的（没有任何一处会报错）。

**⇒ 对 ④ 的适用**：
- 双边图（正向 + 反向）是**推导物**，不落库 ✓（已符合）。
- 级联计划是**推导物**，不落库 ✓（只算不写，2.5）。
- **草稿过滤结果同样是推导物**，不该落成字段（与 5.21 的「不写可见性字段」一致）。

**⚠ 这是推断，不是用户裁决。** 建议与 mod-kind / mod-search 一起报 Lead，作为一条可复用的原则。
