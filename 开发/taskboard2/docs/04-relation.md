## 二、已确定的语义

### 2.1 六种关系 = 5 个 link 标签 + 1 个 `parent` 指针

`links` 里只有五种标签：**依赖 / 取代 / 约束 / 相关 / 参考**；
第 6 种 **`派生` 由 `parent` 字段承载**，**不是 links 里的标签**（1.1 原话）。

**【事实·已查实】** 旧版 `packages/core/index.js:2095-2102` 的注释亦如此写：
「派生 = 父子结构。它不是 links 里的标签（是 parent 字段）」。

### 2.2 词汇表 `LINK_KINDS`（对象数组，`as const`）

一份定义同时承载 **方向 / 有行为 / 显示名**，供运行时与编译期两种用途。

```ts
export const LINK_KINDS = [
  { id: 'dependsOn',  displayName: '依赖', direction: 'forward', hasBehavior: true  },
  { id: 'supersedes', displayName: '取代', direction: 'forward', hasBehavior: false },
  { id: 'constrains', displayName: '约束', direction: 'forward', hasBehavior: false },
  { id: 'related',    displayName: '相关', direction: 'both',    hasBehavior: false },
  { id: 'references', displayName: '参考', direction: 'forward', hasBehavior: false },
] as const;
```

**`id` 用英文标识、中文 `displayName` 与其并列 —— 已裁（1.16）。**

**⚠ 关于「④ 不产中文文案」与 `displayName` 是否冲突 → 不冲突（见 2.2b）。**

**`hasBehavior`：只有 `dependsOn` 是 `true`**（1.16 用户直述）。
**⚠ 别把两件事当"行为"**：
- `supersedes` 的**不可编辑**曾是编辑规则 —— **该规则已作废**（1.17：取代可编辑、可新建、可多个）；
- `related` 的**双向**是**方向属性**（`direction: 'both'`），**不是行为**。

**编译期断言**：词汇表必须**至少 2 条**，且 **`direction === 'both'` 的条目恰好一条**。

```ts
type LinkLabel         = (typeof LINK_KINDS)[number]['id'];
// ⚠ 不再有 EditableLinkLabel —— 所有 label 都可编辑（1.17）
```

**【实现判断】为什么用对象数组而不是字符串数组**：⑤ 判方向、⑨ 判有行为、⑩ 取显示名，
若各自持有字符串列表，词汇会散成三份。**一份定义、多处派生类型**。
代价：取标识集合需 `map(k => k.id)`，**不要假设它是字符串数组**（契约事实）。

### 2.2b `displayName` 是词汇的一部分，不是"终端中文文案"

**问题**：④ 的立场是「不产中文文案」（用户 03:10「9 态的中文只在终端」），
而 `LINK_KINDS[].displayName` 是中文 —— 冲突吗？

**【实现判断】(甲)：不冲突，`displayName` 是词汇表的一项，不是"终端组织的文案"。**

三条区分：

| | 终端中文文案 | 词汇表 `displayName` |
| --- | --- | --- |
| 谁拥有 | 终端（⑨⑪⑩） | **词汇所有者（④）** |
| 内容 | 句子、提示语、警告措辞 | **一个名词**（`依赖` / `取代` / …） |
| 会随上下文变吗 | 会（同一关系在不同工具里说法可不同） | **不会**（它就是那个名字） |

**依据**：用户 1.16 原话「关系是有行为的。所以是**英文和显示名**」——
**"英文和显示名"被并列成词汇的两个部分**，说明**显示名与标识同属词汇表**，
不是终端自行组织的文案。

**⇒ 结论**：**`displayName` 归 ④ 的 `LINK_KINDS`，与 `id` 并列。**
**⇒ ④ 仍然不产句子**（软警告文字仍归 ⑨⑪，见 1.3）；它只提供**名词**。

### 2.3 形状与接口

```ts
type RelationEntry = { label: LinkLabel; to: CardId };

// ④ 私有，不导出
declare const REL: unique symbol;

export type Relations = { readonly [REL]: true } & {
  parent: CardId | '';          // '' = 无父卡；不用 null/undefined（避免两种"无"）
  links:  RelationEntry[];
};

// ⚠ 与 Relations 的 links 相同 —— 所有 label 都可编辑（1.17）
export type EditableRelations = {
  parent: CardId | '';
  links:  RelationEntry[];
};

export function validateRelations(relations: unknown):
  | { ok: true;  value: Relations }
  | { ok: false; issues: Issue[] };

type Issue =
  | { kind: 'link';   index: number; to: string; reason: 'unknown-label' | 'to-empty' }
  | { kind: 'parent';                to: string; reason: 'parent-not-string' };
// target-* 类 reason 不在此列 —— 目标合法性归 core
```

**⚠ `EditableRelations` 与 `Relations` 的 `links` 形状现已相同**（因为不存在"不可编辑的 label"），
**保留两个类型名只为表达"用途不同"**（编辑视图 vs 存储态）。**是否合并成同一个类型，待 ⑦ 定。**

**④ 私有**：`function makeRelations(x): Relations` —— **全仓库唯一允许 cast 成 `Relations` 的地方，不导出、不 provide。**

**❌ 无 `asRelations`、❌ 无 `relations.kind` 字段。**

**【实现判断】`Relations` 的唯一产出点 = `validateRelations` 的成功分支。**
- brand 的有效性**取决于 `REL` 不外泄**；`REL` 一旦导出，brand 立即退化为装饰，且**没有任何编译错误**。
- `makeRelations` 不导出，是为了不给出"官方提供的绕过闸门的钥匙"。

### 2.4 校验范围（④ 只判两件事）

| ④ 的 `validateRelations` **查** | **不查** |
| --- | --- |
| 形状：`relations` 是对象、`links` 是数组、`parent`/`to` 是非空字符串、`label` 是非空字符串 | 目标合法性（存在 / 非草稿 / 非墓碑 / 同空间）→ **core** |
| 词汇：`label ∈ LINK_KINDS` | **多条目数量限制**（取代可以有多个，1.17） |

**⚠ 原先列在这里的两项已作废**：
- ~~「`取代` 的来源规则（哪个作者档能新增/保留）」~~ —— **取代可编辑、可新建**（1.17），**无作者档**；
- ~~「合并后取代条目集合相等（后置断言）」~~ —— **用户可以改取代，集合当然会变**（1.17）。

**【实现判断】签名即边界**：`validateRelations(relations)` 是**单一入参、无 options、无 ctx、无回调**。
- 任何"需要知道当前是谁在写、或目标卡是什么状态"的规则，都必须改签名才能进来 ⇒ **改签名是显式动作，会被 review 看见。**
- 契约句：**「它只回答两件事：结构是否成形、词汇是否合法。」**

### 2.5 级联计划 `CascadePlan`（两阶段 + 两个具体类型）

```ts
type RelationsItem = { kind: 'patchRelations'; cardId: CardId; relationPatch: RelationPatch; reasons: Reason[] };
type StatusItem    = { kind: 'setStatus';      cardId: CardId; targetStatus: string;     reasons: Reason[] };

export type CascadePlan = {
  relationsPhase: RelationsItem[];   // 先执行
  statusPhase:    StatusItem[];      // 后执行
};
```

**跨 phase 全序**：`relationsPhase` 全部执行完，再执行 `statusPhase`。
**phase 内**：按 `cardId` **UTF-16 code unit 升序**（`a < b ? -1 : a > b ? 1 : 0`），
**禁用 `localeCompare`** —— 它依赖运行环境 locale，会让同一份计划在两台机器上排序不同，
**导致"两份语义相同的计划深比较不相等"**。
**phase 内顺序无语义，仅确定性**（可重放、可测、可观察）。

**【实现判断】为什么两个数组用两个具体类型，而不是一个联合：**
1. 若两个数组都收 `PlanItem` 联合，"把 `patchRelations` 塞进 `statusPhase`"**在类型上合法** ⇒ 只能靠承诺；
2. **core 里就不会出现 `item.kind === …` 这个分支位置** —— 而那个位置是"未来顺手加个 case"的入口，违反"业务规则不进 core"。
3. 代价：将来加第三类动作（如 `patchNote`）**必须加第三个 phase** —— **而这正是收益**：强制回答"它属于哪个阶段"，而**阶段顺序是唯一有语义的东西**。

**【实现判断】为什么必须分两个 phase**：原定"同一张卡内 `patchRelations` 在 `setStatus` 前"**不成立** ——
真正的顺序是**跨卡的**：A 的「依赖从旧卡改指新卡」必须在**旧卡**置取消之前，**两张卡 `cardId` 不同**。
拆 phase 后，"先转移依赖、再判旧卡死刑"（3.2）**从约定变成结构**。

### 2.6 `RelationPatch` 与 ⑦ 的收口入口

```ts
export type RelationPatch =
  | { op: 'retargetLink'; from: CardId; to: CardId; label: LinkLabel };
  // 判别式联合：新增 op 不破坏签名
```

**语义四条（已与 ⑦ 定稿）**：
1. **匹配** = `label` 等于该值 **且** `to` 等于 `from` 的那一条 link；
2. **改后** = `to` 变新值、`label` 不变；
3. **匹配 0 条 ⇒ 跳过**（`ok`，无 issue）；**匹配 >1 条 ⇒ `Issue`**（数据异常，**不猜哪条对**）；
4. **多个 patch 按数组顺序应用**（顺序影响结果）。

**⑦ 侧入口（D1，Lead 裁定）—— 单入口 + 两种变更来源**：

```ts
export type RelationsChange =
  | { kind: 'edit';  value: EditableRelations }        // 用户/AI 提交的完整编辑视图
  | { kind: 'patch'; patches: RelationPatch[] };       // ④ 的级联计划，按数组顺序应用

applyRelationsChange(card, change: RelationsChange)
  → { ok: true; value: Relations } | { ok: false; issues: Issue[] };

// 内部固定三步（不可省）：
//   1. validateRelations(current)   ← 不采信"调用方已校验"的声称
//   2. 按 change.kind 应用
//   3. validateRelations(merged) → 定型
```

**④ 的 `relationsPhase` 走 `kind:'patch'` 分支。**

**⚠ 无 `author` 参数**（`user` / `fork` / `system-transfer` 三档 **已作废**，1.17）：
取代可编辑、可新建、可多个 ⇒ **不再需要"哪个作者档能新增/保留取代"的判断**。
**唯一的写入者差别只剩 `kind`（edit / patch），而那是"变更来源"不是"作者权限"。**

**【实现判断】为什么不拆成两个函数**：拆开后**两条路各写一遍「先校验 current」** ⇒
**同一规则写两处必漂**；而"不采信已校验声称"这条纪律只有落在一个地方才守得住。

**【实现判断】为什么必须是 ⑦ 收 patch，而不是 core 直接写**：
- **「所有 relations 写入必须经 ⑦」是已立规则**，它是校验唯一收口（现在只保形状+词汇，不保取代条目集合）；
- core 若自己应用 patch ⇒ 要懂"按 label+to 匹配、改 to 保留 label、去重"⇒ **那是关系语义**；
- 若改成「④ 产出最终 links 数组、core 直写」⇒ **④ 得读旧卡全部 relations 来拼数组**，越界。
- **⇒ 只有「⑦ 收 patch」两边都不越界。** Lead 已裁定保留 `patch`（D1）。

### 2.7 输入形状与「只算不写」

- **④ 的输入**：`{ cards: 当前空间全量非墓碑卡（含草稿） }` —— **单只读数组，无 tombstones**。
- **④ 不认识状态、不认识空间、不做目标校验、不写盘、不调 store、不含 `await`。**
- **④ 只产出计划**，执行归 ⑧（store 同步、按 id 整卡覆写）。

**【实现判断】为什么必须含草稿**：草稿卡**不**能从业务卡集里剔除 ——
用户 05:52「所有依赖对象必须处于终态，才能进行领取」，草稿不是终态 ⇒ 依赖草稿的卡**本应被阻断**；
若把草稿卡剔除，领取检查**看不到那条依赖** ⇒ **错误放行**。**剔除 = 静默放宽。**

### 2.8 草稿与关系：能当源，不能当目标

**规则（用户直述 1.10 三句 + 1.15 核对合一）**：
> **草稿卡可以「指向别人」，但草稿卡不能被别人指向。**
> **草稿不能作为关系的目标（`parent` 与 `links[].to` 一视同仁），读时不可见、写时不可选。**

| 角色 | 草稿卡能当吗 | 依据 |
| --- | --- | --- |
| **关系的源**（草稿指向别人） | ✅ 能 | 1.10「草稿卡自己的关系栏可以看到对别人的边」 |
| **关系的目标**（别人指向草稿） | ❌ 不能 | **1.15（`12:48` 已裁）** + 1.10 |

**⇒ 写入侧拒绝，不是只靠 UI 不显示按钮**（1.15 第 2 点）。
**⚠ 归属**：**目标合法性由 core 判**（④ 不认识状态）；④ 的 `validateRelations` **不查目标合法性**（2.4）。

**⇒ 由此推出（【推断】）**：`parent` 由子任务持有、目标是父卡 ⇒ **草稿卡不能有子任务**（稳态）。
**fork 转移是唯一例外**，且靠「转移在采纳时才写」规避（3.2）。
**⇒ 「草稿卡没有子任务」是准入保证的不变量，不是显示过滤。**

**【实现判断】过滤落在哪一层**：**关系栏 / 候选**这类**视图**在出结果时按
「**另一端点是否草稿**」过滤（出边看目标、入边看源）；
**④ 不参与过滤**（不认识状态），**④ 只出全量边**。

### 2.9 取代（`supersedes`）的三条语义（**已被 1.17 推翻重写**）

- **可以编辑**（1.17，推翻原「不可编辑」）；
- **可以新建**（1.17，推翻原「只能由 fork 产生」）；
- **可以有多个**：新建时一次取代多张卡（1.17，推翻原「只能一个」）；
- **方向：新 → 旧**（1.7，**此条不变**）。

**⇒ `fork` 的定位随之改变**：**不是"取代的唯一来源"，是"快速建卡 + 预填字段"**（1.17）。
**⇒ 「取代不可编辑」的两种读法之争（原 5.2）随本条消解** —— 用户直接裁了「可编辑」。

### 2.10 级联触发与「完成」组

**只有进入「完成」组（成功 / 失败 / 取消 / 拒绝）才触发级联。**
**释放、搁置都不触发**（都不是终态）。
**成功不收下游**，其余三种收。

**被取代旧卡的处置（1.9 的直接推论，【推断】）**：

| 旧卡状态 | 处置 | `reason.kind` |
| --- | --- | --- |
| **在「完成」组** | **不动状态**，只转移依赖 | `superseded-noop` |
| **不在「完成」组** | **转「取消」** | `superseded-incomplete` |

**⚠ 我此前误用「成功」当「完成」的分界**（把失败/取消/拒绝挤成"边角情况"）——
用户 1.9 那句「『完成』是一个状态组，而不是完成且成功」纠的正是这个。
**⇒ 判据本来就是一个状态组的两分，不是"二分 + 补丁"。**

## 三、我的判断与实现选择

以下全部是【实现判断】，不具用户授权效力，可被推翻。

### 3.1 关系的可见性：投影，不是输入的变换

**规则**：**关系项的另一端点是草稿 ⇒ 不显示。** 一条规则，不分出边/入边 ——
出边时"另一端点"是目标，入边时是源。

**为什么是"出结果时过滤"而不是"入口裁剪"**：
- 过滤依据是「另一端的状态」，**而状态 ④ 手上没有** ⇒ 只能由拿得到状态的一方、在全量数据上做；
- **在数据层删边会让业务判定静默放宽**（同 2.7 的反例）。

**⚠ 我判错过两次**（见 4.3）：第一次判"归 ⑤"，第二次判"core 交卡集前剔除草稿卡" ——
第二次被自己的反例推翻。**现行结论：卡集全量、过滤只在视图层做；具体归属层未定（各候选都撞原则）。**

### 3.2 取代的执行顺序：先转移依赖，再判旧卡死刑

**反序不是"慢一点"，是结果不同**：
- 旧卡一旦转成拒绝 / 取消，立刻触发「上游死了 → 收下游」；
- 那一刻依赖方还指着旧卡，会被当作死路一起收掉；
- 而它们本该改指新卡、活下来。

**触发时机 = 采纳时，不是提交时**（1.7 第二句）。
**【推断】独立佐证**：若取代的转移在 fork 时（新卡还是草稿）执行，转移出的边是「草稿 → 草稿」
⇒ 撞 1.10 的禁写规则；在采纳时执行则规则自动满足。**⇒ 「执行于采纳」不只是偏好，是禁写规则的必然推论。**

### 3.3 关系反查 = 内存双边图

**④ 在内存建双边图**（依据 1.11「关系反查在内存里面建双边图」）。
**【推断】** 只有 `related` 无向、且存储只记一侧 ⇒ 双边图须同时维护正向与反向。

### 3.4 不做的事（边界）

- **不做全图组装**（1.13：画边归 ⑩，连 core 都不负责）。
- **不做多跳遍历**（用户：「不展开。要查就要重新用 id 去看」）。
- **不产出警告文字**（1.3 + 用户 05:52「软警告的文字，dsh 命令和 ai tool 方面自行实现」）——
  ④ 只产出关系数据。
- **不做目标合法性校验**（归 core）。

### 3.5 store 与持久化

**【事实·已查实】** 当前 `packages/store/src/` 仍是 jsonl.zstd 实现
（`jsonl-zstd-store.ts` / `zstd-frames.ts` / `paths.ts` / `index.ts`），`StoreService` 只有
`append / appendMany / readAll / replaceAll / stats`。
**【事实·已查实】** 全目录 grep `sqlite|DatabaseSync|json_extract|ensureIndex` **零命中**。

**设计已定、尚未实现**：SQLite 作为**持久化**（查询走内存，SQLite 不承担查询职责）。
**写回 = 按卡 `UPDATE` 一行**，落盘单位是卡，不是库（不存在"全量替换 vs 增量"的二选一）。

**⇒ ④ 与 store 零接口**：store 只被 core 调用。**④ 的 `inject = []`**（删掉 SQL 时代残留的 `taskboard2Store`，D2）。

## 四、作废与被推翻的方案

### 4.1 `(空间, 编号)` 复合键 —— 作废
编号在空间内唯一、卡归属空间且不可移动（1.6），**边只写编号即可**，容器内解析。

### 4.3 `view` 概念 / 三态 A/B/C —— 作废

我们据此设计的 `{cards, tombstones, view}` 输入形状、三态（不存在 / 存在但不可见 / 存在且可见）

### 4.4 「入口裁剪草稿卡」—— 作废（我自己的反例推翻）
原判「core 在交卡集前剔除草稿卡」。

| # | 规则 | 检查方式 |

| ① | 跨包使用值/纯函数/常量走 `package.json` 依赖，**不进 `inject`** | 人工 |
| ② | **第 0 层包无出边**（④ 零 `@local/*` import） | import 图静态检查 |
| ③ | **每个 `inject` 项须指到实际使用**，指不到即残留 | 人工 + 编译 |
| ④ | **`inject` 方向须与包图层级一致** | 人工 |

**⇒ ④ 的定稿：零 inject、零 `@local/*` import、零出边。它只被 ⑦/⑧ import。**

**可机械检查项（针对本模块的静默失效风险）**：

| 不变量 | 判据 | 负向用例 |
| --- | --- | --- |
| `REL` 不外泄 | **`.d.ts` 的导出列表里无 `REL`**（不是"名字不出现"——未导出的 `declare const` 仍会 emit） | 临时真加 `export const REL` 跑一次 emit |
| brand 未退化为字符串 | brand 成员是不可命名的 symbol，非 `__brand:'Relations'` | 临时改成字符串字段 |
| `makeRelations` 是唯一 cast 点 | grep `as Relations` 只命中 `makeRelations` 体内 | 临时在别处加一句 |

**三条纪律**：① **"查不到"必须判失败，不是跳过**（`declaration:false` / 增量构建会造成假阴性）；
② **负向用例必须在真实链路上跑**（临时改真源码 + emit），不能构造假夹具；
③ **`REL` 不外泄 与 brand 不得退化是同一保护的两半**，必须成对检查。
