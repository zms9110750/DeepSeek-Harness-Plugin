# ③ types —— 类型体系（状态 / 分类 / 模板 / 编号）

> 任务类型的整套词汇与规则。四块：状态、分类、模板、编号。

**状态：草稿。接口与规则待用户设计并同意。**

---

## 一、它是什么

四块，严格单向依赖：

```
status → kind → template → id
状态     分类    模板       编号
```

### status —— 九态

词汇来源：**Agent2Agent (A2A) 协议**的 `TaskState` 枚举。九个值：

`UNSPECIFIED` · `SUBMITTED` · `WORKING` · `INPUT_REQUIRED` · `AUTH_REQUIRED` · `COMPLETED` · `FAILED` · `CANCELED` · `REJECTED`

用户给的分组：

- **草稿**：未指定
- **进行**：提交、处理中
- **搁置**：需要信息、需要授权
- **结束**：成功、失败、拒绝、取消

**状态的联合类型只做一件事：判断某个状态是否属于某个组。** 没有任何行为。

### kind —— 分类

每个分类自带行为：初始状态、能不能领取、占不占会话位、状态转移规则、计算态、能派哪几类、搁置/终止怎么传播。

四个分类：`goal` 目标 · `design` 设计 · `record` 记录 · `work` 工作。

**外部可以注册，可以继续添加。** 加第五个分类 = 写一个类 + 一行注册，核心一行都不用改。

### template —— 模板

模板含章节，章节接受行为。模板声明自己属于哪个分类。

**用代码定义，不用 YAML。** 别人可以自己写模板、加内容 —— 但这是**注册**，不是替换本包。

### id —— 编号

编号 = 模板编号 + 分隔符 + 流水号。流水号按前缀各自独立（`RB-01` 与 `WI-01` 并存）。

- 前缀只有两个来源：模板提供一个字母、分类提供一个字母
- 空模板 → 回落分类字母
- 旧编号升级是**读路径**的事，不产生新编号
- 工作组编号 `g-N` 用同一个生成器

**编号必定存在。** 没有编号就没有任务卡 —— 所以编号是核心能力，可以被替换但**不能被缺失**。

---

## 二、边界

### 做

- 九态定义与分组
- 状态转移的判决（给判决，不做执行）
- 分类的行为（每类一个模块，可注册）
- 模板定义、章节、正文校验
- 编号生成与归一、旧编号升级

### 不做

- 读写存储 → ① store
- 级联 → ④ relation
- 编排 → ⑧ core
- 界面 → ⑩ ui

---

## 三、为什么这四块在同一个包里

它们是**严格单向链**，且：

- 九态是外部协议固定的词汇，**别人没有替换它的意愿**
- 分类与模板靠 `register()` 扩展，**不是靠换插件**
- 拆开会形成包级 `inject` 环 → **死锁，不是慢**

所以：包内自洽，对外零 `inject`。

---

## 四、上下游

- **上游**：无。第 0 层。
- **下游**：⑥ workgroup（编号）· ⑦ taskcard（状态/分类/模板/编号）· ⑧ core
- **不认识** ① store。

---

## 五、使用处（大概）

- 核心判定「这个状态能不能转」时问它
- 任务卡创建时问它「这个模板有哪些章节」
- 工作组生成 `g-N` 时问它
- UI 显示状态词时从它取（不重复定义）

---

## 六、待用户设计并同意

### 状态

- **第 9 态 `UNSPECIFIED` 怎么处置？** 留组外 / 另立一组 / 不进词表
- **`WORKING` 中文用「处理中」还是「进行中」？**
- **字面量取哪层名？** 协议全名 `TASK_STATE_WORKING`，还是线上小写 `working`
- **状态分组归全局还是每分类可不同？**

### 分类（用户已给初稿，但明确说「可以讨论」）

用户给的四类规则初稿存在若干未定义处，**全部待用户裁决**：

- 计算态会不会覆盖终态
- 采纳是否需要独立标志
- 「领取态」与「计算态」谁优先（规则顺序自相矛盾）
- 同一状态有多种子任务情形时无规则覆盖
- 派发规则（工作能派哪些）缺失
- 记录类能否取消 / 拒绝

### 模板 / 编号

- 模板定义放一个文件还是每个一个文件
- `behavior` / `framed` / `domain` 这些字段到底干什么用
- 旧编号升级后要不要重新分配
- 流水号能不能复用
- 补零位数可配否
