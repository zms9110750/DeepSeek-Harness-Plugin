## 二、已确定的语义

### 2.1 存储介质 = SQLite

【用户指令，2026-11-01 04:25】「那就走sqlite。」

- 一空间一库：`<dshHome>/taskboard/<workspaceId>.db`
- **路径运行时推导，不硬编码**：显式配置 > `$DSH_HOME`（空白视为未设置）> `~/.dsh`
- **`taskboard` 与 dsh 的 `sessions` 保持兄弟目录关系**（`dirname(<dshHome>/sessions)` + `/taskboard`）

### 2.2 表结构：只有 `id` 是列

```sql
PRAGMA application_id = <任务板魔数>;   -- 照 dsh 做法，防止误开他库
PRAGMA user_version   = 1;              -- schema 版本

CREATE TABLE cards (
  id   TEXT PRIMARY KEY,
  data TEXT NOT NULL CHECK (json_valid(data))
) STRICT;

CREATE TABLE meta (
  k TEXT PRIMARY KEY,
  v TEXT NOT NULL
) STRICT;
```

- **业务字段一个都不做列**【用户指令，2026-11-01 04:25】「不做列」
- **纯 JSON 存储**：整卡是 `data` 里的一个 JSON 对象
- `id` 是**唯一固定列/主键**【用户指令，2026-11-01 04:25】「编号还是作为主键的。总要有一个唯一值」
- `data` 用 `TEXT` 不用 `BLOB`：JSONB 更省但不可读，与「要能直接看内容」相反

### 2.3 store 值无关的精确边界

> **store 知道「哪些东西是查询维度」，不知道「这些维度是什么意思」。**

| store 知道 | store 不知道 |
|---|---|
| `id` 是主键 | 编号规则、不生成编号 |
| `data` 是合法 JSON | `data` 里有哪些键 |
| 可以按 `json_extract` 某路径建索引 | 那个路径的语义 |
| 有 `meta` 表存键值 | 键值是什么意思 |

**⇒ store 不认 `history`、不认 `deleted`、不认 `parent`、不认任何业务字段名。**

### 2.4 接口（全同步）

```ts
readAll(wsId): Card[]                        // 全量、含墓碑、不过滤、每次新对象
read(wsId, id): Card | undefined
write(wsId, cards): void                     // 按 id 整卡覆写（唯一业务写入口）
purgePhysical(wsId, ids): void               // 纯物理删，绕过墓碑机制
transaction(wsId, fn): T                     // fn 只拿 tx.*；无 await
listWorkspaces(includeArchived?): {id, archived}[]
dbPath(wsId, archived): string
archiveDb(wsId): void
unarchiveDb(wsId): void
readMeta(wsId): Record<string, unknown>
writeMetaKey(wsId, key, value): void         // value === undefined ⇒ 删除该键
globalKv: { get(key), set(key, value), delete(key) }
```

【Lead 指令，2026-11-01 13:20】确认：`listWorkspaces()` 返回 `{id, archived}[]`、`dbPath(wsId, archived)`、`archiveDb`/`unarchiveDb` 命名、① 文档诚实写「知道 `archive` 子目录和 `_global.db`」。

**同步的原因**【实现判断】：`DatabaseSync` 是同步 API，整条链路同步。**这会破坏下游四个包的异步调用方式，已在第六节列为对齐项。**

**事务契约**【实现判断】：
- `fn` 的入参是 `tx` 对象（绑定该连接 + 该事务），**不是让 fn 去调 public 面**
- `fn` 内调 public 面方法 → **直接抛错**（不静默降级，避免把原子性 bug 藏起来）
- `fn` 内**禁止 `await`**（同步事务让出事件循环会跨请求）

**`readAll` 每次返回新对象**【实现判断】：store 不做对象缓存，**内存真值归 core**。代价是 O(整个空间) 的解析，core 应在「激活空间」时读一次、长期持有，不在循环里反复调。

**`globalKv` 公开**【实现判断】：曾考虑不公开（只有 ⑥ 用），但 ⑥ 是独立包、只能经 public 面访问 ① ⇒ 不公开则「当前空间指针」无处可存。公开不破坏值无关：**key 是不透明字符串**，store 不解释。「谁都能改当前空间」是**用**的问题，靠约定解决，不靠削减 API。

### 2.5 归档 = 移进 `archive/` 子目录

- 默认列表**不含归档**；`listWorkspaces(true)` 才列出
- **归档可取消**
- 归档/取消归档 = **关闭句柄 → `rename`**（不是数据库操作）

【事实·已查实】若启用 WAL，SQLite 会生成 `<id>.db-wal` / `-shm` 边车文件。**句柄未关闭时移动主文件，边车留在原地，库可能无法恢复。** ⇒ **必须先关句柄**。

【实现判断】崩溃窗口后果：库仍是未归档状态、数据完好；`rename` 原子。**没有数据损坏风险，只有「操作没生效」风险。**

### 2.6 `archive/` 与 `_global.db` 是 store 的已知事实

**① 知道 `<dshHome>/taskboard/archive/` 这个子目录名，也知道 `<dshHome>/taskboard/_global.db`。**

不宣称「① 不认识归档」——【实现判断】假装中立会制造接口别扭（要造「移到子目录」这种语义模糊的方法）。**业务判断仍归 ⑥**（何时归档、UI 怎么做），**① 只提供物理操作。**

### 2.7 空间 id 清洗

【用户指令，2026-11-01 >05:07】+【2026-11-01 05:18】

```
用户填名字 → sanitize（纯函数、幂等）→ allocate（查重消解）→ 落盘
```

**清洗规则（白名单式，8 步）**【实现判断】：

| 步 | 动作 |
|---|---|
| 1 | Unicode NFKC 归一化 |
| 2 | 只保留 `[A-Za-z0-9\u4e00-\u9fff_-]`，其余替换 `_` |
| 3 | 连续 `_` 折叠为一个 |
| 4 | 去首尾 `_` |
| 5 | Windows 保留名（`CON`/`PRN`/`AUX`/`NUL`/`COM1..9`/`LPT1..9`/`CLOCK$`，不分大小写）→ 前加 `_` |
| 6 | 去结尾的点与空格 |
| 7 | 截断 120 字符 / 200 字节（给 `.db`、`-wal`、`-shm` 留余量） |
| 8 | 结果为空 → `space` |

- **幂等**：对结果再跑一次不变。**确定**：不用哈希、不用随机、不依赖时间戳。
- **大小写不折叠**【实现判断】：折叠会把 `Project` 与 `project` 悄悄合并 —— 那是用户没要求的破坏性操作。**宁可撞了消解，不可悄悄合并。**

**重名自动消解**【用户指令，2026-11-01 05:18】「他的清洗就是考虑重名的」：
- `base` → `base-2` → `base-3`…
- **显示名跟着变**（用户看到的就是最终名，不是「界面 A、磁盘 B」）
- 后缀用 `-N` 而非 ` (2)`（与白名单一致）
- 并发用**排他创建（`O_EXCL`）作最终仲裁**，失败则 +1 重试（不依赖内存锁）

**改名不支持**【实现判断】：
- 支持改名 = 文件名变 = **当前指针全部失效**，而 `_global.db` 里**没有「谁引用了这个空间」的索引**
- 修复要么加引用索引（新机制），要么让所有会话指针静默失效
- **⚠ 知情项**：空间名不可改 + 卡不可跨空间移动 ⇒ **用户起名时没有第二次机会**，UI 应提示

### 2.8 索引：表达式索引 + 便利视图，按需追加

```sql
-- 需要时追加，建表时不预置
CREATE INDEX IF NOT EXISTS idx_cards_status
  ON cards(json_extract(data, '$.status'));

-- 便利视图（不加速，只提供统一查询面）
CREATE VIEW IF NOT EXISTS card_view AS
SELECT id,
       json_extract(data, '$.status') AS status,
       data
FROM cards;
```

**三者的真实能力**【事实·已查实】：

| | 存储仍是纯 JSON | 能否真正加速 | 建表时需预知字段 | 是否「新增列」 |
|---|---|---|---|---|
| `VIEW` | 是 | **否**（纯虚拟表，不能建索引） | 不需要 | 否 |
| **表达式索引** | 是 | **是** | **不需要**（可随时追加） | 否 |
| 生成列 | 是 | 是 | **需要** | **是（`ADD COLUMN`）** |

【实现判断】选表达式索引 + 视图。生成列虽物理不占空间，但**字面上就是 `ADD COLUMN`**，且建表即需预知字段 —— 正是用户否决的。

**全库统一用 `json_extract`**【实现判断】：`json_extract(...)` 与 `data->>'...'` 可能不命中同一索引。

**诚实补充**【事实·已查实】：**表达式索引会占磁盘**（索引条目存了提取出的值）。「不做列」≠「不存那个值」。

**当前不预置任何索引** —— 见第六节。

### 2.9 事务只在一个空间内

一空间一库 ⇒ **跨空间事务技术上不可能**。这是「一空间一文件」的连带代价。

### 2.10 版本与锁

【用户指令，2026-11-01 01:29】判给 store：

- **格式版本** = `PRAGMA user_version`
- **锁** = SQLite 自身文件锁 + `journal_mode`（WAL）
- **事务** = `BEGIN`/`COMMIT`/`ROLLBACK`

【实现判断】不再自建 per-workspace 写队列 —— SQLite 进程内天然串行，跨进程有文件锁 + `busy_timeout`。

## 三、我的判断与实现选择

### 3.1 用 `node:sqlite`，不用 `dsh-storage-sqlite`

【事实·已查实】
- `@deepseek-ai/dsh-storage-sqlite` **在本发行版未安装**：`app.asar/dsh/node_modules/@deepseek-ai/dsh-storage-sqlite/package.json` 不存在；全 asar 搜 `storage-sqlite` 仅 3 处命中，**全是文档表格与链接，无实现代码**
- dsh 自己的 SQLite 先例是 `node:sqlite`：`dsh-session-query-sqlite/lib/index.js:50` → `await import("node:sqlite")` + `new DatabaseSync(path)`
- 运行时 **Node 24.21.0**（`dsh-primary-runtime/runtime.json:7`）
- `DatabaseSync` **同步阻塞 JS 线程、语句不可中断**（asar `:1889419` 原话）

【实现判断】直接用 `node:sqlite`，并照抄 dsh 的建库习惯：`application_id`、`user_version`、`STRICT`、目录/文件权限 `0o700`/`0o600`。

【实现判断】不用 `dsh-storage-sqlite` —— 它是 `kv` facet（key→value），没有自定义 schema 与索引控制，与需求不匹配。

### 3.2 文件名用 workspaceId

【实现判断】理由不是偏好，是安全性：改名存在可能；空间名含 Windows 非法字符与保留名；**dsh 同款做法**是 `SAFE_KEY_RE = /^[a-zA-Z0-9_-]+$/`（`dsh-storage-json/lib/index.js:302`）。

### 3.3 空间元信息存该空间自己的 `.db` 的 `meta` 表

【实现判断】用户要「拖文件就能迁移」⇒ 一个空间的全部信息必须跟着那一个文件走。元信息在库外则拖走文件会丢名字。

### 3.4 同步接口

见 2.4。**这是接口破坏，下游四个包需对齐**（第六节）。

### 3.5 `purgePhysical` 而非 `remove`

【实现判断】**③ 明确「删除是标记删除（`deleted: boolean`），墓碑仍占号」**。若业务删除调物理删，**编号可复用 → 撞主键**。

⇒ 业务删除 = **core 写一张 `data.deleted = true` 的卡（整卡覆写）**；`purgePhysical` 只在物理清理时用，**core 中不存在任何业务调用点**。

**名字比注释有效**（这条是 ⑧ 提议、我采纳）—— 本轮已多次出现「注释写了但没拦住」。

### 3.6 空间名不冗余到 `_global.db`

【Lead 指令，2026-11-01 13:20】先不做，等冒烟测。见第六节缺口 B。

## 四、作废与被推翻的方案

### 4.1 jsonl.zstd 格式 —— 作废

- **被推翻于**：【用户指令，2026-11-01 04:25】「那就走sqlite。 jsonl.zstd 也不是明文可读的。」
- **连带撤回**：曾把「可读 / 可外部编辑」当 jsonl 的优势论证。**压缩后要解压才能看，这条优势不存在。**

### 4.2 追加 + 折叠 —— 作废

- **被推翻于**：同上（SQLite 直接 UPDATE，不需要折叠）
- **连带作废**：事件外壳（`op`/`id`/`record`/`fields`）、折叠规则（LWW、墓碑复活、对已删对象打 patch）、折叠内存缓存

### 4.3 「一事务必在一帧」 —— 作废

- 原为 zstd 帧原子性推导的约束。SQLite 有真事务，前提消失。

### 4.4 固定列 + JSON blob 模型 —— 作废

- **被推翻于**：【用户指令，2026-11-01 04:25】「不做列。因为给储存成员的要求是支持任意的类型。」
- **我的错在哪**：为索引而固定 `status`/`kind`/`template` 成列，等于让 store 预知业务字段 —— **拿值无关换查询性能，用户不接受这个交易。**

### 4.5 `history` 的机制保证 —— 作废

- **被推翻于**：【用户指令，2026-11-01 04:25】「只读是谁读，谁写？谁的历史？」
- **我的错在哪**：把「历史是只读字段」理解成**存储侧完整性要求**，设计了 `write()` 拒绝带 history、保留旧值、`appendHistory()`、SQL 触发器，还得出「store 要知道 history 键名」。
- **正确读法**：「只读」= 不向消费者暴露写入口，**是接口权限**。`history` 就是 `data` 里的普通键。
- **与 4.4 是同一类错误的第二次犯**，共同点：**把上层语义下沉到 store 的机制层。**

### 4.6 用 `dsh-storage-json` / `dsh-storage-sqlite` —— 作废

- `dsh-storage-json`：曾按 1.4 判据是正确选择（有 `root` 入口），但用户裁定 SQLite，明文 JSON 后端不适用
- `dsh-storage-sqlite`：本发行版未安装，且 `kv` facet 抽象不匹配

### 4.7 历史归类错误（记录在案）

- 我曾在「无人认领 9 项」里把**历史**与折叠、迁移、备份并列，报为「不做」
- 【用户指令，2026-11-01 04:25】澄清：那四项是**存储侧历史**，用户说的历史是**卡上的字段**
- **不是用户改主意，是我把「字段」误归成「机制」。** 拆词固定：
  - **历史字段** = 卡上普通键 → 归 ⑦/⑧
  - **历史机制** = 事件溯源 / 折叠 → 不做
  - **历史查询** = 按时间/操作者检索 → 不做

### 4.8 per-workspace 写队列 —— 作废

- SQLite 进程内天然串行，跨进程有文件锁 + `busy_timeout`。自建队列无必要。

### 4.9 「① 对外不承认存在『归档』这个词」—— 作废

- 【实现判断】此说法站不住：`listWorkspaces` 必须知道 `archive/` 目录名，归档操作必须知道往哪移
- **改为诚实表述**：① 知道 `archive/` 与 `_global.db`（见 2.6）

### 4.10 「每空间一份模板」—— 作废

- 【实现判断】模板全空间共享，存文件系统，**不进 store**。理由：每空间一份会引出「新建要复制、改了要同步 N 份、空间删了模板没了、归档空间里的模板算不算当前集」四个新机制，而共享一个都不需要
- 与【用户指令，2026-11-01 04:53】「所有工作空间是全会话可见的」同向

## 六、需要与其它成员对齐的

### 6.1 已对齐（四方，2026-11-01 阶段一）

| 对象 | 结论 |
|---|---|
| **⑧ core** | 接受同步接口，不包 Promise 适配；`transaction` 的 fn 只拿 `tx.*`；内存真值归 core；`readAll` 每次新对象不缓存；业务删除走写墓碑卡，永不调 `purgePhysical` |
| **③ types** | **③ 与 ① 零耦合**；③ 不读 YAML（由 ⑧ 读+解析+`registerTemplate`）；编号是纯函数、不读 store、不需要 `maxId` |
| **④⑤** | **不接触 store**；④ 要「全量、含墓碑、含草稿」→ 我返回全量不过滤，筛在 core；**不做任何字段规整/裁剪**；按 id 整卡覆写是唯一写入口 |
| **⑦ taskcard** | 墓碑是独立字段 `deleted: boolean`（不靠 status）；`data` 是**平铺 JSON 对象**，顶层字段名不再改；⑦ 与 ① 零耦合 |

**责任三层（与 ③⑦ 共同确认）**：
- **① store**：返回全量，**不隐式过滤任何东西**（含墓碑）
- **⑧ 调用方**：算「已用编号集合」时**必须含墓碑**
- **③**：只吃 `usedIds`，不收集、不改写

### 6.2 索引：当前无需求方

**四方确认：④⑤ 走内存、⑦ 不读库、③ 纯函数 ⇒ 全链路无索引需求方。** 所以「不预置」是安全的，不是「暂时欠着」。

**触发条件（⑦ 提出，来源标注清楚）**：
> 若将来 ④/⑤ 改回「从 store 直查」（例如数据量超出内存装载），**`$.parent` 与墓碑标记是第一批需要索引的路径** —— 因为 `parent` 是唯一存子关系的地方（用户「持久化只储存父任务，反向边在内存里画」），一旦不能全量装载，反向查除索引无他路。
