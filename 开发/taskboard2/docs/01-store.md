## 二、已确定的语义

以下每条都能追到第一节的原话。

### 2.1 存储边界 = 工作空间

- **一个工作空间 = 一个 `.db` 文件**（【推断】由 1.6、1.8 锁定）
- 文件路径：`<dshHome>/taskboard/<workspaceId>.db`
- **`dshHome` 运行时推导，不硬编码**：优先显式配置 > `$DSH_HOME`（空白视为未设置）> `~/.dsh`
- **`taskboard` 与 dsh 的 `sessions` 保持兄弟目录关系**（`dirname(<dshHome>/sessions)` + `/taskboard`）
- **文件名用 workspaceId，不用空间名**（【实现判断】理由见 3.4）

### 2.2 存储形态 = 纯 JSON

- 一张表 `cards`，**唯一固定列是 `id`（主键）**
- **整卡存成一个 JSON 文本**，业务字段一个都不做列
- 「值无关」在此的**精确落点**：store 只知道两件事 —— **`id` 是主键**；**`data` 是合法 JSON**。其余一概不知。

### 2.3 事务归 store

【用户指令，2026-11-01 01:29】已把「事务、格式版本、锁」判给 store 自己写。

【推断】SQLite 落地后这三样都有天然载体：
- **事务** = SQLite `BEGIN` / `COMMIT` / `ROLLBACK`
- **格式版本** = `PRAGMA user_version`
- **锁** = SQLite 自身的文件锁 + `journal_mode`

【推断】**事务只能在一个空间内**（一个空间一个库）。跨空间事务做不到，这是「一空间一文件」的连带代价。

### 2.4 历史不归 store

**`history` 是 `data` JSON 里的一个普通键。** store 存它、取它，**不看内容、不认键名、不做特殊处理、不提供专用接口**。

谁在变更时追加 —— 是 ⑦ taskcard / ⑧ core 的事。

### 2.5 不做存储侧历史

折叠 / 迁移 / 备份 / 事件溯源 **不做，且不预留接口位**。理由见 1.10（用户原话：需要类似 git 的额外存储，合并设计不可行）。

## 三、我的判断与实现选择

### 3.1 用 `node:sqlite`，不用 `dsh-storage-sqlite`

【事实·已查实】
- `@deepseek-ai/dsh-storage-sqlite` **在本发行版未安装**：`app.asar/dsh/node_modules/@deepseek-ai/dsh-storage-sqlite/package.json` 不存在；全 asar 搜索 `storage-sqlite` 仅 3 处命中，**全是文档表格与延伸阅读链接，无一行实现代码**
- 对照：`dsh-storage`、`dsh-storage-json`、`dsh-storage-domain` 三个的 `package.json` 均可读
- **dsh 自己的 SQLite 先例是 `node:sqlite`**：`dsh-session-query-sqlite/lib/index.js:50` → `const { DatabaseSync } = await import("node:sqlite")`
- 运行时 **Node 24.21.0**（`dsh-primary-runtime/runtime.json:7`）
- `DatabaseSync` **同步阻塞 JS 线程、语句不可中断**（asar `:1889419` 原话：「DatabaseSync blocks the JavaScript thread during MATCH execution and cannot interrupt a statement already running」）

【实现判断】直接用 `node:sqlite` 的 `DatabaseSync`，并照抄 dsh 已有的建库习惯：
- `PRAGMA application_id`（防误开他库）
- `PRAGMA user_version`（schema 版本）
- `STRICT` 表
- 目录/文件权限 `0o700` / `0o600`

【实现判断】**不用 `dsh-storage-sqlite`**，即便它将来可用 —— 它是 `kv` facet（key→value 抽象），没有自定义 schema 与索引控制，与「按 JSON 内字段查询」的需求不匹配。

### 3.2 查询加速：表达式索引为主，视图作查询面

【事实·已查实】三者的真实能力完全不同：

| | 存储仍是纯 JSON | 能否真正加速 | 建表时是否需预知字段 | 是否「新增列」 |
|---|---|---|---|---|
| `VIEW` 视图 | 是 | **否**（纯虚拟表，不能建索引） | 不需要 | 否 |
| **表达式索引** `CREATE INDEX ... ON cards(json_extract(...))` | 是 | **是** | **不需要**（可随时追加） | 否 |
| 生成列 `GENERATED ALWAYS AS` | 是（VIRTUAL 不占存储） | 是 | **需要** | **是（`ADD COLUMN`）** |

【实现判断】**选表达式索引 + 便利视图**，弃用生成列：
- 只有「表达式索引 + 视图」同时满足「不做列」+「真加速」
- 生成列物理不占空间，但**字面上就是 `ADD COLUMN`**，且建表即需预知字段 —— 正是用户否决的
- 视图不加速，但 SQLite 会把简单视图扁平化进查询；**只要视图内表达式与索引表达式逐字一致，索引仍会命中**。视图的价值是**统一查询面**，让消费方不各写各的

【实现判断】**全库统一用 `json_extract(data, '$.<path>')` 一种写法**。`json_extract(...)` 与 `data->>'...'` 在不同版本下可能不命中同一索引。

【事实·已查实】**表达式索引会占用磁盘**（索引条目里存了提取出的值）。「不做列」不等于「不存那个值」，只是不声明成列、不参与表结构。

### 3.3 索引路径由谁声明 —— 现在不建，留口子

【实现判断】不预置任何索引，只提供「按需声明」的入口，由 ⑤ search 在实现时按真实查询决定。

理由：
- store 值无关 ⇒ 不知道卡里有哪些字段 ⇒ **自己无法决定索引什么**（这是「不做列」的直接后果，非疏漏）
- 字段形状未定 ⇒ 任何预置清单立刻过期
- 先不建最符合「有了原型实现才能改」；需要时追加即可，索引存于 `sqlite_master`，重启后仍在

【推断】这是**跨成员问题**（需要知道 ⑤ search 的查询形态）。按【用户指令，2026-11-01 01:29】「接口问题他们让成员之间互相汇报提问」，应由 search 侧提需求。

【事实·已查实】这件事权重很高，因为 `DatabaseSync` 同步阻塞：**没索引的全表扫描不是「这条查询慢」，而是「整个宿主进程卡住」**。建议把「卡量上千时的列表查询」列为冒烟必测。

### 3.4 文件名用 workspaceId 而非空间名

【实现判断】理由不是偏好，是安全性：
- 「空间改名」存在可能（用户提过）—— 用名则改名要连带改文件名
- 空间名是用户输入，Windows 文件名禁 `\ / : * ? " < > |`，且禁结尾空格/点，另有 `CON`/`NUL`/`COM1..9` 等保留名
- **dsh 同款做法**：`dsh-storage-json/lib/index.js:302` 的 `SAFE_KEY_RE = /^[a-zA-Z0-9_-]+$/`，写入前 `assertSafeKey` 拒绝不合规 key

【实现判断】代价是目录里不可读（`g-1.db` 而非 `我的项目.db`）。可读性放空间元信息里，不放路径。

### 3.5 空间元信息存哪

【实现判断】存**空间自己的 `.db` 内一张 `meta` 表**（键值对），不放库外。

理由：用户 1.6/1.8 的「拖文件就能迁移」要求**一个空间的全部信息跟着那一个文件走**。元信息若在库外，拖走单个文件会丢名字。

【推断】这不违反「不做列」——`meta` 不描述卡的结构。

### 3.6 值无关的精确表述（经三次修正后的终版）

> **store 知道「哪些东西是查询维度」，不知道「这些维度是什么意思」。**

具体：
- 知道 `id` 是主键 —— **不知道编号规则、不生成**
- 知道 `data` 是合法 JSON —— **不知道里面有什么键**
- 知道可以按 `json_extract` 的某个路径建索引 —— **不知道那个路径的语义**
- **不认 `history` 键，不做特殊处理**

### 3.7 同步接口

【实现判断】`DatabaseSync` 是同步 API，整条链路同步。

【事实·已查实】这会破坏下游四个包（`search` / `relation` / `workgroup` / `core` 都 `inject` 了 `taskboard2Store`）的现有调用方式。**这是接口破坏，要告知团队。**

【实现判断】事务回调内不允许 `await` —— 同步事务里让出事件循环会让事务跨请求，是 bug。

## 四、作废与被推翻的方案

每一条都写明「被哪句话推翻」，避免以后重蹈。

### 4.1 jsonl.zstd 格式 —— 作废

- **被推翻于**：【用户指令，2026-11-01 04:25】「那就走sqlite。 jsonl.zstd 也不是明文可读的。」
- **连带撤回**：我曾把「可读 / 可外部编辑」当作 jsonl 的优势论证（还查证过 dsh 的 pretty-print 设计）。**压缩后要解压才能看，这条优势不存在。**

### 4.2 追加 + 折叠 —— 作废

- **被推翻于**：同上（改走 SQLite，直接 UPDATE 即可，不需要折叠）
- **连带作废**：事件外壳（`op`/`id`/`record`/`fields`）、折叠规则（LWW、墓碑复活、对已删对象打 patch 的处理）、折叠内存缓存（增量消费字节偏移）

### 4.3 「一事务必在一帧」 —— 作废

- 原为 zstd 帧原子性推导出的约束。SQLite 有真事务，该推导失去前提。

### 4.4 固定列 + JSON blob 模型 —— 作废

- **被推翻于**：【用户指令，2026-11-01 04:25】「不做列。因为给储存成员的要求是支持任意的类型。」
- **我的错在哪**：为了索引而固定 `status`/`kind`/`template`/`created_at` 成列，等于让 store 预知业务字段 —— **我在拿值无关换查询性能，用户不接受这个交易。**

### 4.5 `history` 的机制保证（拒绝写入 / 保留旧值 / 专用追加接口 / 触发器）—— 作废

- **被推翻于**：【用户指令，2026-11-01 04:25】「只读是谁读，谁写？谁的历史？」
- **我的错在哪**：把「历史是只读字段」理解成**存储侧完整性要求**，于是设计了 `write()` 拒绝带 history 的卡、读旧值写回、`appendHistory()` 专用接口、SQL 触发器兜底，还得出「store 需要知道 `history` 键名」的结论。
- **正确读法**：「只读」= 不向消费者暴露写入口，**是接口权限，不是存储机制**。`history` 就是 `data` 里的普通键。
- **这条错误值得记下来**：它是同一类错误的第二次犯（第一次是 4.4 的固定列），共同点是**把上层语义下沉到 store 的机制层**。

### 4.6 用 `dsh-storage-json` / `dsh-storage-sqlite` —— 作废

- `dsh-storage-json`：曾是按 1.5 判据的正确选择（有 `root` 配置入口），但用户 04:25 裁定 SQLite，明文 JSON 后端不适用。
- `dsh-storage-sqlite`：本发行版未安装（4.1 已查实），且是 `kv` facet，抽象不匹配。

### 4.7 历史归类错误（记录在案）

- 我曾在「无人认领 9 项」清单里把**历史**与折叠、迁移、备份并列，报为「不做」。
- 【用户指令，2026-11-01 04:25】澄清后确认：那四项是**存储侧历史**，而用户说的历史是**卡上的字段**。
- **这不是用户改主意，是我把「字段」误归成「机制」。** 拆词固定下来：
  - **历史字段** = 卡上的普通键 → 归 ⑦/⑧
  - **历史机制** = 事件溯源 / 折叠 → 不做
  - **历史查询** = 按时间/操作者检索 → 不做

### 4.8 曾设计过的「per-workspace 写队列」 —— 作废

- SQLite 在进程内天然串行（`DatabaseSync` 同步执行），跨进程有文件锁 + `busy_timeout`。自建队列无必要。

### 6.1 `node:sqlite` 是否支持 JSON 函数（方案的硬门槛）

【待验证】**整个 JSON 存储方案依赖此前提，未实测。**

【事实·已查实】旁证：
- 运行时 Node 24.21.0（`runtime.json:7`）
- dsh 已在本运行时实跑 `node:sqlite` 的 `DatabaseSync`，且会发 **ExperimentalWarning**（asar `:1889342`：dsh 专门做「延迟到首次搜索才发警告」的设计）

- **JSON 函数自 SQLite 3.38（2022-02）起是核心功能，不再是可选的 JSON1 扩展**

【推断】几乎确定可用。但推断不能替代实测。

**开工后第一条命令即此门槛**：

```sql
SELECT sqlite_version(), json_extract('{"a":1}','$.a');
```

- 返回 `3.4x | 1` → 方案成立，可开工
- 报 `no such function: json_extract` → **整个 JSON 路线退回**，需重新讨论存储形态
