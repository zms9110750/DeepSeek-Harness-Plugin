## 二、已确定的语义

### 2.1 ⑤ = 宿主侧的纯函数（含输入 / 输出形状）

**core 按此调用**（⑦/⑨/⑩ 也可能引用）：

```ts
// ── 输入 ──
type SearchInput = {
  cards: readonly Card[];   // core 给：当前空间全量、非墓碑（含草稿）
  query: SearchCondition;   // 纯数据，可 JSON 序列化
};

// ── 输出 ──
search(input: SearchInput): Card[];   // 卡引用数组；顺序 = 卡的「采纳顺序」（1.6）
```

- **`cards` 由 core 给**（1.1「core 把所有任务的内存形式给他」），⑤ 不自己取数；
- **`query` 必须是纯数据**，可跨「浏览器 → 宿主」边界序列化（2.2）；
- **返回 `Card[]`（卡引用），不返回 id 列表、不做投影** —— 投影是消费者的事（3.2）；
- **返回顺序 = 卡的「采纳顺序」**（1.6，不是输入顺序，不是字典序）；
- **空 `query` = 返回全部输入卡**（仍按采纳顺序）。

**【实现判断】**：
- **随包 import**（**不是** core 的 service 方法）；
- **不取数据、不认空间、不建索引、无状态、无 IO、只读**；
- 条件必须是**纯数据**，可被 JSON 序列化。

### 2.2 为什么是「宿主侧」—— 这是决定条件必须可序列化的原因

**【实现判断，依据 1.1 + 1.5】**：
⑤ 是**宿主侧**的纯函数；⑩ ui 的搜索框把**条件序列化**发给宿主 → 宿主侧某个桥调用 ⑤ → 结果回传浏览器渲染。

**为什么不能在浏览器侧跑**：
- 浏览器拿不到 core 的内存卡集 ⇒ 要跑就得全量下发卡集，与「当前空间在宿主内存」冲突；
- 若两处各有一份实现 ⇒ **直接违反 ⑤ 存在的理由（口径统一）**。

**⇒ 条件必须可序列化的原始理由，就是它要跨「浏览器 → 宿主」这条边界。**
（若 ⑤ 在浏览器跑，条件只需是普通对象，不必承诺可序列化。）

**⚠ 由此的边界**：**⑤ 永远拿不到「条件以外的上下文」** —— 凡是需要"当前是谁在看"的过滤，都不能在 ⑤ 里。

### 2.3 只搜元数据

**可搜（元数据）**：**标题、编号**（1.6 点名的关键词字段）；
以及**状态 / 分组 / 领域**三项筛选所依据的字段。

**不可搜**：**正文（`sections`）与备注（`note`）** —— 依据 1.2。

**【事实·已查实，来自 ③/⑦ 对齐】**：
- **`status` 在卡上**（`card.status`）⇒ 状态筛选自足；
- **`group` 是状态组**，由调用方展开成状态列表（2.6）⇒ ⑤ 不内建组定义；
- **`domain` 是模板元数据，卡上不存**（用户 12:48 裁「domain 保持纯展示」，卡形状无 `domain`）⇒ 领域筛选需外部数据，见下。
- **`kind` 也在模板上**（`card.template.kind`），但**分类不是用户点名的筛选维度** ⇒ ⑤ 不提供分类筛选。

**⚠ 「领域」筛选的数据来源待确认**：卡上无 `domain`，要按领域筛就得先经 `template.ref` 反查模板元数据
—— 那需要 ③ 的注册表。**⑤ 是纯函数、不吃模板数据** ⇒ 【待确认】归 ⑧（由 ⑧ 把卡按领域预筛后再交给 ⑤，或由 ⑧ 传一份"模板 → 领域"的映射）。

### 2.4 不做的事

- **不做沿边展开**（1.3「不展开」）。
  **⚠ 注意区分**：`relations.parent` 的一次集合查询**是"取子任务"这个操作**，
  而用户 06:03 要的是「tool 看任务卡，要说，任务的子任务是什么」——
  **那是某张卡的详情操作，不是搜索能力**；**⑤ 不提供它**（3.1 末段）。
  「不展开」这条更根本：**⑤ 不做从一条边跳到另一条边的多跳遍历**。
- **不做分页**（1.4）。
- **不搜模板**（模板列表 = ③ 注册表的投影，由 ⑩ 渲染；⑤ 查卡不查模板）。
- **不读章节 / 不读 `accepts`**（章节与 action 的配对属 ②③）。
- **不做全文检索**（1.2 已排除正文）。
- **不做「取子任务」**（3.1 末段：那是卡的详情操作，不是筛选维度）。

### 2.5 `accepts` 三态（不是 ⑤ 的职责，仅登记以免混淆）

`accepts` 是**章节属性**（这一章接受哪些 action），属模板元数据：

| 值 | 含义 |
| --- | --- |
| `string[]` | 只接受列出的 action |
| `[]` | **禁止**任何 action |
| `'any'` | 未限制 |

**⚠ 无 `'unresolved'`** —— Lead 最终裁定按三态（`【Lead 指令，2026-11-01 13:25】` 第三节 D8）。

**但一条区分必须写进本文**（Lead 要求保留）：
> **「永不被产出的合法值」是 fail-closed 守卫**（防外部调用方给错时静默放行）
> **「留个位置以后填」是路径撒谎**
> **⇒ 两者不能并成一类。**

**⇒ ⑤ 与 `accepts` 零关系**：⑤ 查卡、不查章节。若文档里出现"⑤ 处理 `accepts`"，那是把 ② 的内容混进了 ⑤。

### 2.6 状态与状态组

**【事实·已查实，③ 提供】**：状态组（`ActiveStatus` / `ShelvedStatus` / `EndedStatus`）是**纯 TS 类型**，
**运行时被擦除** ⇒ **⑤ 想自己展开也做不到**。

**⇒ 定稿**：**⑤ 的条件里传「状态字符串列表」（`string[]`），⑤ 不展开组、不判断某状态属于哪组。**
调用方（⑧/⑨/⑩）负责把"组"解析成状态列表。

### 2.8 返回顺序 = 采纳顺序（依据 `history`）

**依据**：
> 【用户指令，2026-11-01 13:26】
> 卡的"历史"这个字段存了他的状态转变时间。

**⇒ 定稿**：

```ts
// 返回顺序 = 采纳顺序
// 采纳顺序 = 卡的 history 里「进入采纳态」那条记录的 at（时间）
// 同 at 时用 id 做确定性 tie-break（否则跨机器排序不稳定）
```

**三件必须写清的事**：

1. **`history` 是卡上的字段**，形如 `{ at: number; action: string; detail?: unknown }[]`；
2. **「采纳」= 草稿之后的那次状态转移**（用户 06:43「任务卡一旦采纳就冻结」）——
   具体是哪次转移、`action` 的字符串叫什么，**【待确认】归 ⑦（卡形状）**；
3. **`history` 是数组，但不保证有序** ⇒ **必须按 `at` 取极值，不能假设 `[0]` 就是最早**。

**⚠ 若某张卡没有采纳记录**（理论上不该有，因为建卡即入库）：
**不猜、不静默排到最前或最后**，**标【待确认】交 ⑦/⑧ 定**（可能的处置：报错 / 按 id 兜底 / 视为数据异常）。

**【实现判断】`history` 算元数据** —— 它不是"用户写的内容"，是**系统记的时序数据**，
与标题/编号/状态同类，因此**不违反"内容与备注不入搜索"**。
**⇒ 但 `history` 只用于排序，不参与关键词匹配、不参与任何筛选维度。**

### 2.9 入参里的空间

**【实现判断】**：**⑤ 不接收空间参数** —— 它拿到的卡集**本来就是单空间的**（由 core 保证）。
看全部空间 = 上层对每个空间各调一次搜索（用户 1.2「全部看一遍必须有多少空间调用多少次搜索」）。这循环不在 ⑤ 内。

## 三、我的判断与实现选择

### 3.1 条件的形状

```ts
type SearchCondition = {
  // ── 关键词（对应 UI 的搜索框）──
  keyword?: string;          // 匹配 title **和** id（1.6：搜索可搜标题、编号）

  // ── 筛选（对应 UI 的按钮）──
  status?:  string[];        // 状态（由调用方把"组"展开成状态列表，见 2.6）
  group?:   string[];        // 分组 = 状态组
  domain?:  string[];        // 领域
};
```

**【实现判断】**：
- **关键词 = 标题 + 编号**（1.6），**不含正文/备注**（1.2）；
- **关键词与筛选可同时生效**（1.6：AI 工具「一个方法，搜索的时候同时筛选」）；
- **筛选维度就是用户点名的三个**：`status` / `group` / `domain`，**零扩展位**；
- 条件里**只有字段过滤，没有图操作**（1.3「序列化只存字段」）；
- 空条件 = 返回全集；
- 多个字段之间是 **AND**；同一字段内的数组是 **OR**。

**⚠ 「取子任务」不在 `SearchCondition` 里**：用户 06:03 要的是「告诉我这张卡的子任务是什么」，
那是**某张卡的一个操作**，不是通用筛选维度。**⑤ 不提供这个能力**；
若将来需要，由 ⑧ 或 ⑦ 按 `relations.parent` 过滤即可。

### 3.2 结果只含卡引用

**【实现判断】**：⑤ 返回 `Card[]`（或**它的引用**），**不做投影、不裁剪字段** ——
投影（只留 id/标题/状态）是**消费者**的事。
理由：⑤ 若自带投影，就等于内置了一个"UI 要的形状"，而三个消费者的需要不同。

### 3.3 与 ④ 的边界：不重叠

- **④ 出「边」**（谁指向谁 + 类型 + 方向）；
- **⑤ 出「筛选后的卡集」**；
- **④ 不做候选集捞取，⑤ 不做图遍历** —— 两者**并列**，由 ⑧ 编排，**互不调用**。

## 六、需要与其它成员对齐的

### 6.1 与 ③ types —— 只吃数据，不调用
- **⑤ 不 import ③**；条件里的状态/分组/领域都是**字符串**。
- **状态组由调用方展开成 `string[]`**（2.6，技术上唯一解：组是 TS 类型、运行时被擦除）。
- **「分组」筛选（`group`）收的仍是字符串**，由调用方把"提交组/处理组/搁置组/完成组"展开成状态列表；
  **⑤ 不内建组的定义。**
- **⚠ 「领域」的数据来源在 ③/⑦ 侧**（卡上无 `domain`，见 2.3）⇒ **需 ⑧ 预筛或传模板→领域映射**。
- **⑤ 不读 `accepts`、不读章节**（2.5）。

### 6.1b 与 ⑦ —— ⑤ 需要读 `history` 字段（仅用于排序）
- **⑤ 读 `card.history`**：`{ at: number; action: string; detail?: unknown }[]`；
- **只用于排序**（2.8），**不参与关键词匹配、不参与筛选**；
- **【待确认】**：① 「采纳」对应的 `action` 字符串是什么；② 无采纳记录时如何处置。
  **两条都需 ⑦ 定（卡形状归 ⑦）**，⑤ 不做猜测。

### 6.2 与 ⑧ core —— 谁调 ⑤、卡从哪来
- **⑧ 提供卡集**：`{ 当前空间全量非墓碑卡 }`，**不分页**（用户 1.4「分页不考虑」；且全量才能保证结果完整）。

### 6.3 与 ⑨ ai-tool —— 新会话的默认入口
