# ⑦ taskcard —— 任务卡

> 任务对象本身。**状态只是它的一个字段。**

**状态：草稿。接口与规则待用户设计并同意。**

---

## 一、它是什么

一个任务卡的**形状、生命周期、编辑规则、fork**。

```
任务卡
 ├─ id            编号（③ 生成）
 ├─ template      用的哪个模板（③）
 ├─ kind          模板分类（③）
 ├─ body          章节正文（形状由 ③ 的章节 + ② 的行为决定）
 ├─ status        存储态（③ 定义，转换规则由 ③ 的分类注册）
 ├─ note          备注（永远可写）
 └─ relations     与其它卡的关系（④）
```

> 上表是**草稿**，字段的最终形状待用户设计。

---

## 二、边界

### 做

- 创建：照模板装配一章章正文
- 编辑：改正文（逐章判可变性）
- fork：派一张新卡 + 建「取代」关系
- 套模板：换模板、加章节
- 关系：这张卡连了谁（读写经 ④，不自己存）
- 备注：永远可写

### 不做

- 状态定义与判定 → ③ types
- 有哪些分类、每类的转换 → ③ types
- 模板长什么样 → ③ types
- 编号怎么生成 → ③ types
- 关系怎么存、怎么遍历 → ④ relation
- 事务、编排 → ⑧ core
- 怎么显示 → ⑩ ui

### 关键立场（用户已确认）

- **任务卡要解耦。** 有些东西依赖它、有些东西不依赖。
- **备注归任务卡自己。** 这是采纳冻结后唯一还能改的地方；**没有任何角色「需要」这个能力**，所以它不该做成服务 —— 只是卡上的一个字段 + 一个永远允许的写入口。
- **编辑与 fork 的分界**：采纳前可以原地改任何东西；采纳后不可原地改，要改只能 fork。

---

## 三、编辑与 fork（用户口述的规则，待细化）

### 采纳前是「编辑」

草稿可以原地改任何东西：正文、备注、关系、编号。

### 采纳后是「fork」

```
fork 出来的会有一个「取代」的关系。
未完成的子任务，和依赖，都会转移过来。
相关，参考，完成的子任务，不会转移。
```

| 什么 | 转移吗 |
| --- | --- |
| 未完成的子任务 | ✅ |
| 依赖（我依赖的、依赖我的） | ✅ |
| 相关 | ❌ |
| 参考 | ❌ |
| 已完成的子任务 | ❌ |

### 采纳后仍可写的

| 什么 | 为什么 |
| --- | --- |
| **备注** | 唯一无条件例外，任何时候都能写 |
| **行为声明了可变的章节** | 由 ② 说，不由状态算 |
| 关系、编号 | ❌ 采纳后冻结 |

---

## 四、上下游

- **上游**：③ types（状态 / 分类 / 模板 / 编号）· ④ relation
- **下游**：⑧ core
- **不依赖** ⑥ workgroup · ⑤ search · ⑨ ai-tool · ⑩ ui · ⑪ dsh-command

---

## 五、为什么它该是一个包

旧版没有这一层，结果一个任务对象散在几十个函数里，没人能说出「任务卡有哪些字段」。

**它把「一个任务是什么」收进一处**，让状态、模板、关系各自只管自己的事。

**为什么独立成包**：它是一个可替换的实现领域 —— 换任务对象的形状与编辑规则有意义。

---

## 六、待用户设计并同意

- 任务卡的字段究竟有哪几个
- 「取代」的方向（新卡指向旧卡，还是相反）
- fork 的 id：新卡拿新编号，旧卡编号是否保留
- 能不能同时 fork 出多张
- 模板能不能换（采纳后换模板算 fork 还是算禁止）
- 已完成的子任务为什么不留
- 子工作空间放在卡上还是组上
