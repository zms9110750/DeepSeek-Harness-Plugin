# ⑦ taskcard —— 任务卡

> 任务对象本身。**状态只是它的一个字段。**

**本文性质**：Lead 授权的成员文档，不是用户写的规格。用户原话逐条标注时间锚点；用户未说的部分一律标成【推断】/【实现判断】/【待验证】，三者不可混读。

**分类纪律**
- `【用户指令，…】` = Lead 转达的用户原话（本会话中，成员均未与用户直接对话，所有"原话"都是 Lead 转达文本）
- `【推断】` = 从原话推出、用户未直接说
- `【实现判断】` = 实现层选择，不占用户裁决
- `【事实·已查实】` = 有文件/行号证据
- `【待验证】` = 尚无实测结果
- `【待裁】` = 需用户决定

## 二、已确定的语义

### 2.1 卡形状（必须项 5 个）

```ts
interface Card {
  id: string;                     // 必须项。创建时分配、终身不变、空间内唯一
  title: string;                  // 必须项
  status: TaskState;              // 必须项。A2A 全名字面量（'TASK_STATE_*'）
  template: {                     // 必须项 = 模板实例引用（快照）
    ref: string;                  //   ③ 的模板稳定引用；**其值就是模板 name**
    kind: Kind;                   //   分类英文 id：'goal' | 'design' | 'record' | 'work'
    domain: string;               //   领域。**快照字段**（`【用户指令，2026-11-02 00:23】`「template 要有领域的」）
  };                              //   ⚠ domain 仍**纯展示、不校验语言、不建注册表**；卡上存它是为了**按领域筛选**
  relations: Relations;           // 必须项 =「关系」。类型从 ④ import，⑦ 不手写
  sections: Record<string, unknown>;  // 模板内容 + 答案；⑦ 零参与校验，整体透传
  note: string;                   // 追加项。永远可写，不随采纳清空
  history: { at: number; action: string; detail?: unknown }[];  // 追加项，只读
  deleted: boolean;               // 墓碑标记（独立字段，不是状态值）
  claimedBy: string;              // 当前占用者 = **agent 消息循环 id**（非会话 id）；'' = 无
  claimedAt: number;              // 占用起始时间；与 claimedBy 同生同灭
}
```

- **必须项恰好 5 个**：`id` / `title` / `relations` / `template` / `status`。其余为追加项。
- **无 `workspace` 字段**（用户 04:05 / 04:20：卡不知道空间、卡不能换空间）。
- **无裸 `kind` 字段**：分类在 `template.kind` 里，避免两处真值。
- `relations` 的具体形状由 ④ 定义（`{ parent: CardId | ''; links: RelationEntry[] }`），**⑦ 不重写、不手拼**。
- `sections` 是**单层映射** `{ [sectionId]: payload }`；payload 的结构归 ②，⑦ 不解释。

### 2.2 接口（全部纯函数：无 IO、不读 store、不认识容器）

```ts
isDraft(card): boolean                              // ⟺ status === DRAFT
changeIntent(card): 'edit' | 'fork'                 // 纯查询，供 UI 出按钮文案；封闭枚举
planCreate(input): Plan
planChange(card, all, { editable, patch? }): Plan   // 草稿期原地编辑（不产历史）
planFork(src, newTemplateSections): ForkPlan
planAdopt(card, all): Plan                          // 采纳（含取代执行）
planRelease(card, principal): Plan                  // principal = {type:'user'} | {type:'agentMessageLoop', id}
planClaim(card, actor, ctx): Plan                   // ctx.actorHasActiveWork 必填
planDelete(card): Plan
planForkTransfer(src, all): { transfer, skip }      // 只读，供 fork 面板预览
applyRelationPatches(card, patches): { ok:true; value: Relations } | { ok:false; issues: Issue[] }
planTransition(card, all, { to, actor, depsAllEnded, at? }): PlanResult   // 整组状态转移，见 2.8
```

- **所有 plan 只产出「意图」，不写盘**；落盘与事务归 ⑧。
- **意图里给"卡的最终完整字段"，不给 diff**（⑧ 不反推字段语义）。
- **`changeIntent` 的结果不得作为任何 plan 的输入**（TOCTOU：两次调用之间卡状态可能被别的 agent 消息循环改掉）⇒ ⑦ 内部重判。
- `planFork` 的返回额外含两个清单（见 2.5）。
- **`applyRelationPatches`（复数）**：**所有 relations 写入必须经 ⑦** 的落实点（Lead D1 裁定）；入参是 **`patches: RelationPatch[]`**，**按数组顺序应用**。

**历史动作名常量（⑦ 导出，供 ⑤⑧⑨⑩ 引用，禁止各包自写字面量）**

| 常量 | 值 | 含义 |
|---|---|---|
| `ADOPT_ACTION` | `'adopt'` | **「采纳」这个转移动作**（未指定 → 提交 / 需要授权）。⑤ 按它排序用。 |
| `SUPERSEDE_ACTION` | `'supersede'` | 采纳时执行取代（旧卡被处置）。 |
| `CREATE_ACTION` | `'create'` | 建卡。 |
| `FORK_ACTION` | `'fork'` | fork 建卡（历史写「分支」，不是「创建」）。 |
| ~~`EDIT_ACTION`~~ | `'edit'` | ~~草稿期编辑~~ ⇒ **编辑不产历史**（11-02 12:46）；常量保留以兼容 import，**⑦ 不再产出**。 |
| `CLAIM_ACTION` | `'claim'` | 领取（提交 → 处理中）。 |
| `RELEASE_ACTION` | `'release'` | 释放（处理中 → 提交）。 |
| `FORCE_RELEASE_ACTION` | `'force_release'` | 用户强制释放（非本人持有），`detail` 带原 `claimedBy`。 |
| `DELETE_ACTION` | `'delete'` | 删除（墓碑）。 |
| `TRANSITION_ACTION` | `'transition'` | **整组状态转移**（见 2.8）；`detail` 带 `{ from, to }`。 |

⚠ 动作名**永不变**（改名会让旧历史失去可判别性）；要加动作就**新增**，不复用旧名。

### 2.3 不变量

1. **冻结 ⟺ `status !== DRAFT`**。
   冻结范围：`id` / `title` / `template` / `relations` / `sections` 的**声明部分**。
   **不冻结**：`note`（永远可写）、`sections` 内的**答案值**。
2. **编辑权 ⟺ `DRAFT`；fork 权 ⟺ 非 `DRAFT`；两者互斥**。
   `【用户指令，2026-11-01 06:43】`「草稿不能 fork。**fork 和编辑，是一个按钮。**」
3. **身份 = (`id`, `template.ref`, `template.kind`)**，创建即固定、终身不变。
4. **删除仅草稿期**；墓碑（`deleted: true`）**默认读路径过滤**，**按 id 直查可见**。
   `【用户指令，2026-11-01 03:32】`「搜索、分类……都不显示墓碑。但直接使用 id，强行搜索，是可以搜索到的。」
5. **`claimedBy` 非空 ⟺ `status ∈ OCCUPYING_STATES`**；**清空原因只有三种**：`release` / 转终态 / 删除。
6. **取代**（`【用户指令，2026-11-01 13:18】` 已把旧限制全部推翻）：
   - **取代边可编辑、可由用户手写新建、可有多条**（旧的三条限制「不可编辑 / 只能由 fork 产生 / 只能一个」**全部作废**）；
   - **fork 时自动创建一条「取代」边**（新 → 旧）—— 但 **fork 只是快捷建卡**，不是取代的唯一来源；
   - **采纳时执行**（**先转移依赖、再判旧卡**）：旧卡在**「完成」组**（成功/失败/取消/拒绝）⇒ **不动**；否则 ⇒ **转「取消」**。
   - ⚠ **"可多条取代"对执行的影响**：一个卡可被多条取代边指向 ⇒ **采纳执行时按"被指向的每一张旧卡"分别处置**（各自看它是否在「完成」组），**不是"只判一张"**。
7. **草稿期不得删除已有 `sectionId` 键**（`planChange` 校验 `next.sections` 键集 ⊇ `current.sections` 键集；可改 payload、可新增键、**不可删键**）。
8. **新增 `sectionId` 是否属于模板** ⇒ **不在 ⑦**，归 ⑧ 的落库入口检查（见 3.3）。
9. **`relations` 的领域形状归 ④**；⑦ 只 import 类型，**不得手写**。
10. **`sections` 的内容归 ②**：⑦ 不校验、不解释、不补默认、不修正，**只整体透传**。
    唯一的结构性接触是 `isDeclarationOnlyChange(prev, next) → boolean`（**只收布尔，不收字段**），以及**键集比较**（键不是内容）。

### 2.4 `derive` 派生按钮的行为（**变量概念已整个消失**）

> `【用户指令，2026-11-02 11:26】`
> **派生按钮的行为一律携带：选择派生提供的模板，把关系里面设置对方为父任务，标题用父任务的标题，加上 -，然后加上父任务对这个派生按钮写的 label。如果没有 label，就加模板名字。这只是初始化的行为，如果中途改变了模板，标题不会附随自动更改。**

**⇒ 规则（写死在代码里，不再是模板里的变量替换）：**

| 项 | 值 |
|---|---|
| **模板** | `derive[].template` |
| **父任务** | **当前卡**（`relations.parent` = 当前卡） |
| **标题** | **`{父任务标题}-{derive[].label}`**；**`label` 缺失 ⇒ 用模板的 `displayName`** |
| **关系** | `parent` = 当前卡 |

**模板的 `derive` 只剩三个字段**：`label` / `description` / `template`。
**`title` 与 `relations` 已从模板语法中删除**（旧 YAML 若仍写它们，属过期写法）。

**⚠ 三条边界**
1. **只是"初始化"**：点按钮的那一刻算一次标题与关系；**中途改模板，标题不会自动跟着变**。
2. **derive 本身仍然"没有行为"**：它只是"新建面板的预填"，用户点提交时产生的仍是一次**普通建卡**，照常过校验。
3. **拼接归谁**：**归 ⑧（"按 derive 打开新建面板"那一刻）**，⑦ 的 `planCreate` **只接受最终的 `title` / `relations` 参数**，**不做任何拼接、不读 `label` / `displayName`**（`【实现判断】`，理由：⑦ 不认识"按钮"这个概念，兜底规则还依赖模板元数据）。

### 2.5 `planFork` 的两个清单

```ts
planFork(src, newTemplateSections) → {
  newCard, relations, events,
  droppedSections: Array<{ sectionId: string; payload: unknown }>,   // 源卡有、新模板无
  missingSections: Array<{ sectionId: string }>                      // 新模板有、源卡无
}
```

- **⑦ 能算**：两个清单的 `sectionId` 全集（纯键集运算：源卡 `sections` 键集 vs 新模板章节集）。
- **⑦ 不能算**：`hadContent`（"这章有没有填内容"是 payload 语义，⑦ 零参与）⇒ **⑦ 原样透传 `payload`，`hadContent` 由 ⑧ 判**。
- **`missingSections` 只带 `sectionId`**：`accepts` 已由 ③ 彻底移除；补空 payload 需要的 `default` 由 **⑧ 自己从 ③ 拿**（`【实现判断】`：⑦ 不需要 `default`，它只报"缺哪几章"）。
- **清单非空 ≠ 数据有问题**：只是键集差异的如实报告；"这一章本来该不该存在"归 ②/③。

### 2.8 `planTransition` —— 整组状态转移（新增）

> `【用户指令，2026-11-02 13:50】`
> **状态转移，是一个函数。参数是目标状态，调用者。**
> **调用者可能是用户，ai，系统（后端）**
> **用户和ai调用，就检查当前情况和权限。**
> **系统调用，就不读取那个目标状态的参数，自己按着转移规则数一下。切过去，或者不切**

#### 2.8.1 签名

```ts
planTransition(ports, card, all, input: {
  to: TaskState;               // 目标状态
  actor: Principal;            // user / agentMessageLoop
  depsAllEnded: boolean;       // ⑧ 算好的跨卡聚合（依赖是否全在完成组）
  at?: number;                 // ⑧ 在事务内盖
}): PlanResult
```

- **一次一张卡**（不是批量）。批量由 ⑧ 循环调。
- **纯转移**：产出 `{ op:'setStatus', cardId, to }` + 一条 `transition` 事件。
- **`TRANSITION_ACTION = 'transition'`**，`detail = { from, to }` ——
  依据 `【用户指令，2026-11-02 12:35】`「触发通知的是状态转移本身」⇒ 历史必须能读出"变了什么"。

#### 2.8.2 流程

| 序 | 步骤 | 说明 |
|---|---|---|
| 1 | `card.deleted` ⇒ 拒 `already-deleted` | 墓碑不参与任何转移 |
| 2 | 问 ③ `canTransition(kind, from, to, actor, {depsAllEnded})` | **不过就拒**（`transition-not-allowed`）；⑦ 不自己判状态机 |
| 3 | `agentMessageLoop` 且 `kind === 'work'` 且 `to === COMPLETED` | **三道闸**（2.8.3） |
| 4 | `agentMessageLoop` 且 `kind === 'work'` 且 `to === FAILED` | **一道闸**（2.8.4） |
| 5 | `to === card.status` ⇒ 拒 | **同值不产计划**（见 2.8.5） |

**⚠ 系统（后端）调用不在这条路上**：它不读 `to`，自己按规则数 —— 那是 ⑧ 的 `recompute`。

**⚠ 现有的 `planAdopt` / `planClaim` / `planRelease` / `planDelete` 全部保留不动** ——
它们有额外语义（采纳触发取代 / 领取设 `claimedBy` / 释放清占用 / 删除置墓碑），
**`planTransition` 只管纯状态转移**。

#### 2.8.3 `agentMessageLoop` 成功的三道闸（仅 `work`）

只对**直接子任务**生效。

> `【用户指令，2026-11-02 13:50】`
> **是的。就是判断模板是这个额而且状态是这个。**
> **所有子任务都要完成，不包括草稿。因为父任务统计子任务，遍历，遍历不出来草稿。**
> **是的。子任务全部失败，取消，拒绝。只要有一个成功的交付。就可以成功。所以这个成功，是需要点击和调用，不是自动行为。**


**⚠ 关键点**：
- **闸 2 只要求"在完成组"**（成功 / 失败 / 取消 / 拒绝 都算）⇒

**字面量 `'delivery'` / `'blocker'` 直接写在 ts 里**：

> `【用户指令，2026-11-02 13:30】`

## 三、我的判断与实现选择

> 以下均为 ⑦ 的实现判断，不占用户裁决。

### 3.1 卡形状相关

1. **`parent` 空值用空串 `''`，不用 `null` / 不用缺字段**。
   理由：JSON 里"缺字段"与 `''` 语义不同；`null` 会让"无父卡"有两种表示。
2. **`history.action` 是封闭的机器可读标识**（英文，不是中文文案）。
   `【用户指令，2026-11-01 03:32】`「任务板内部交互用的就是英文名。」 ⇒ ⑦ 不产中文、不消费中文。
   动作名**永不改名**（改名让旧历史失去可判别性），**新增就新增、不复用旧名**。
3. **`claimedBy` 存 agent 消息循环 id，不是会话 id**。
   依据：`【用户指令，2026-11-01 06:43】`「一个会话的子消息，也可以另外领取」—— 存会话 id 会实现成"整会话只能一张"。
   **`claimedBy` 的语义是"谁在占用"，不是"谁有权释放"**（权限差异由 `principal` 表达）。
   **值的字面前缀是 `agentMessageLoop:<id>`**（`{type:'user'}` 存 `'user'`）。

**⚠ 前缀变更（`loop:` → `agentMessageLoop:`）**
`【用户指令，2026-11-02 13:30】`「loop 确实是 ai。但我希望改名……agentMessageLoop」「前缀改就一起改」。
· **旧数据无法解析**（`principalOfClaim('loop:xxx')` ⇒ `undefined`）。
· **原型阶段无真实数据，不做迁移**；若将来改这段，需同时考虑 `claimedBy` 里已存在的旧前缀。

### 3.2 编辑 / fork

4. **`changeIntent` 必须返回封闭枚举、不是 boolean**（二元命名会把语义焊死）。
5. **单入口、入口内分派**：⑦ 对外是一个"变更"入口（用户看到的是一个按钮），**内部两条路**；`op` 字段告诉 ⑧ 该落哪一种。
6. **`planChange` 入参分两段**：
   - `editable`：用户/AI 可提交部分（`title` / `note` / `sections` / `relations` 的可编辑视图）；
   - `patch?`：计划项式操作（供 ④ 的级联计划消费）。
   `editable.relations` 用 ④ 的 `EditableRelations`，**⑦ 不手拼**。
   - ⚠ **`editable` 不再类型层排除「取代」**（`【用户指令，2026-11-01 13:18】`：取代可编辑、可新建、可多个）⇒ 原「三重保护」（类型层排除 / 后置断言 / 来源限制）与 `normalizeRelations` 的作者三档（`user`/`fork`/`system-transfer`）**整块作废**。
   - **取而代之的只有一件事**：写入仍必须经 `validateRelations` 收口（形状 + 词汇），**这条与"能不能改"无关**。

### 3.3 `sections` 的守卫边界（重要）

7. **⑦ 只守"键集不缩小"**（不删键），**不守"新增键是否属于模板"**。
   - 后者需要模板知识（`sectionsOf`），⑦ 不持有。
   - **归属**：**⑧ 的落库入口检查**（Lead 转达的 (丙) 方案：⑧ 在 `updateBody` 落库前校验"新增 `sectionId` ∈ 模板章节集"）。
   - 为什么不由 ⑦ 做：⑦ 是"变更计划层"，**计划可以不被执行，落库一定会执行**；护栏应放在能被执行的地方。
8. **⑦ 不校验 `sections` 唯一性/重复键**。
   上游（③ 的注册解析）已保证解析后唯一；**若发现重复，行为未定义**（不是"静默接受"，也**不是 ⑦ 保证唯一**）。
9. **⑦ 不校验 payload 合法性、不碰 `$type` 字面量**。
   判定在 ②：`payloadHasContent(payload)`。⑦ 侧**承诺不出现任何 action 类型字面量**（否则 ② 新增第四个 action 时会静默出错）。
   · ⚠ **`emptyPayloadFor(accepts)` 已作废**（11-02 12:10，`accepts` 从 ③ 彻底移除）⇒ 补空 payload 改用**该章的 `default`**，由 ⑧ 从 ③ 拿。

### 3.4 占用 / 释放

10. **`QUOTA_STATES` = `{ status: 处理中 }` 且 `kind === 'work'`**。
    `【用户指令，2026-11-01 06:55】`「占位算的是『工作』且为『处理中』。**目标的处理中是不算的。**」
    ⇒ 配额判定是**判定式**（分类是硬条件），不是单纯状态集合。
11. **搁置 = 自动让出配额，但保留 `claimedBy`**。
    依据：清空白名单只有三种（`release` / 转终态 / 删除），**搁置不属于任何一种**；且搁置是**自动计算**出来的状态，让计算产生"清字段"副作用会破"计算只改状态"。
12. **`planRelease` 准入 = 持有者本人 或 用户**；**目标 = 「提交」**。
    `【用户指令，2026-11-01 06:55】`「（释放后）回到『提交』。」；`【用户指令，2026-11-01 07:00】`「用户可以释放。用户权限和 ai 权限是不同的。」
13. **`WORK_SINGLE_CLAIM`（一个 actor 只能有一张处理中的工作卡）**：
    - **规则表述归 ③**（可引用的具名规则声明，非可执行分支）；
    - **计算与拦截归 ⑧**（`actorHasActiveWork` 由 ⑧ 算、由 ⑧ 拦）；
    - **⑦ 只做非空校验**：`ctx.actorHasActiveWork` 为 `undefined` ⇒ **报错，不许默认 `false`**（默认 `false` = 静默允许重复领取）。

### 3.5 取代 / 旧卡

> `【用户指令，2026-11-01 13:18】`「取代是可以编辑的。甚至新建的时候可以取代多个卡。fork 只是快速的创建一个卡，帮你填写字段。」

14. **取代边在 fork 时自动建立（新 → 旧），但 fork 不是唯一来源**：**用户可手写、可编辑、可建多条**。
    旧卡在**采纳时**才终止；"建立"与"终止"是**独立事件**。
15. **旧卡处置看「完成」组**：在组内（成功/失败/取消/拒绝）⇒ **不动**；否则 ⇒ **转「取消」**。
    ⇒ 失败/拒绝**不会**被抹成取消，复盘类规则不受影响。
16. **旧卡已终态时**：取代**不产生状态变更项**，只做依赖转移（`reason: superseded-noop`）。
17. **多条取代 ⇒ 逐张处置**：采纳执行时，对**每一条被指向的旧卡**分别判「是否在完成组」，**不是只判一张**。
18. **「依赖阻断领取」的归属 —— 判断：归 ③ 的 `canTransition`，⑦ 不判**
    `【用户指令，2026-11-01 13:18】`「有行为的只有『依赖』。效果是所有依赖对象都进入了完成态，这个卡才能被领取（从提交转为处理中的那个状态转换的按钮）」
    - **理由**：这是**「提交 → 处理中」这个状态转移的合法性条件**，而转移判决的归属一直是 ③ 的 `canTransition(kind, from, to, actor)`。
    - **⑦ 的 `planClaim` 只做单卡准入**（卡是否可领、`actorHasActiveWork` 非空校验），**不做依赖完成度判定**。
    - ⚠ **依赖完成度需要"整张关系图 + 各目标卡状态"**（跨卡聚合）⇒ 与 `actorHasActiveWork` 同性质 ⇒ **由 ⑧ 算好传入 ③**，不是 ⑦ 自己扫全量卡。
    - ⇒ **数据流**：⑧ 取依赖目标状态 → 算「是否全部在完成组」→ 传 ③ 的 `canTransition` → ③ 判决。

### 3.6 错误与失败

19. **模板解析的两种失败必须分开**：
    - **注册表未初始化 ⇒ `resolve` 抛错** ⇒ 按"系统未就绪"处理（**中止**）；
    - **已初始化但无此模板 ⇒ 返回 `undefined`** ⇒ **fail-closed 拒绝建卡**。
    两者一个"状态不对"、一个"数据不对"，**不合并成一个错误**。
20. **`planClaim` / `planRelease` 等准入拒绝返回 `{op:'reject', reason}`**，**不抛异常**（⑦ 是纯函数，不把异常当控制流）。
    `reason` 为**封闭枚举**（数据，非文案）—— core 查表转文案，**不写 `if reason.kind`**。
21. **`reason` 的结构**（取代/级联相关）：
    ```ts
    type Reason =
      | { kind: 'supersede';             edge: { from: CardId; to: CardId } }  // 新→旧
      | { kind: 'superseded-incomplete' }        // 旧卡不在「完成」组 ⇒ 转取消
      | { kind: 'superseded-noop' }              // 旧卡已在「完成」组 ⇒ 不动
      | { kind: 'force-release';         previousHolder: string }
      | { kind: 'path-hit';              via: 'parent' | { label: LinkLabel; from: CardId } }
    ```
    去重键 = **(kind, 依据)**：同 kind 同依据才去重；**同 kind 不同依据保留两条**（同一父卡可同时命中"子任务"与"依赖方"两条路径）。

### 3.7 可变性与不可变性

22. **`Kind` 会随注册表扩宽**（新增分类时联合类型加宽）⇒ ⑦ **不写穷举 `switch(kind)`**，一律经 ③ 的 `initialStatus` / `canTransition`。
23. **状态字面量只有一个来源**（③ 的 `TaskState`）。⑦ **不得书写状态字符串字面量**。
    - lint 需**两条**：① `src/` 内不得出现 `'TASK_STATE_*'`；② 不得出现 `status === "<字面量>"`（后者抓"短名写错"，前者抓不到）。
24. **分支上限（本轮教训）**：任何"看起来最干净"的结论，都要先验伪再写进文档。

### 3.8 fork 的章节差异（两个方向都要留痕）

25. **fork 时「丢弃已填内容」= 允许，不阻断，但必须留痕**（`【Lead 指令，2026-11-01 13:30】`）。
    - 理由：**阻断与用户已裁的「fork 可用」冲突**；**风险已收窄为边角**（仅"该章有用户内容且新模板删了该章"）；**留痕可追溯**。
    - ⑦ 的职责：**产出 `fork-discarded` 事件（`sectionId` 全集）**；**不判"这章有没有内容"**（payload 语义，⑦ 零参与）。
26. **反向（缺章）同样留痕**：⑦ 产出 `fork-filled` 事件（补了最小空 payload 的 `sectionId`）。
    - 理由：**只记"少了"不记"多了"，用户看到多出的章节同样困惑**；补的一侧必然是空内容，**不需要 `hadContent`**。
27. **事件名与是否升格归 ⑧ 的实现选择，⑦ 不预设**（`【实现判断】`，非用户裁决）。
    - ⑦ 只给**纯数据**（id 全集）；**⑧ 判出 `hadContent` 后决定**用哪个事件名（如 `fork-discarded` / `fork-discarded-content`）以及是否升格为告警级。
    - 理由：**用户不关心事件叫什么**；而"⑦ 直接产带 `hadContent` 的事件"需要 ⑧ 先把判定回传，**多一次往返、不划算**。
28. **清单语义是"如实报告"，不是"数据有问题"**：`droppedSections` / `missingSections` 的计算基准 = 源卡 `sections` 键集 vs 新模板章节集；源卡若含非法键，它会如实出现在 `droppedSections` 里 —— **"这一章本来该不该存在"归 ②/③，不在清单语义里**。

### 3.9 取代的编辑性（`13:18` 新裁）

29. **取代边与其它 link 同等对待**：**可新建、可编辑、可删除、可多条**。
    - 因此 ⑦ **没有**"取代特殊通道"：不设只读约束、不设唯一性约束、不设"只能由 fork 产生"的来源约束。
    - `fork` 只是**快捷建卡**（自动填一条取代边），**不承担"取代必须来自 fork"的语义**。
30. **但"可编辑"不等于"绕过校验"**：任何 relations 写入仍**必须经 `validateRelations`**（形状 + 词汇），这条与"能不能改"无关。
31. **取舍记录**：原设计中"取代不可手写/唯一/不可编辑"三条限制**全部来自 `05:52`**，已被 `13:18` 显式推翻（用户自述「我之前可能说过取代只能有一个，现在改掉这个要求」）⇒ **07 文档一律按 `13:18` 执行**。

#### 6.6.1 `hasBehavior` 的判据（`【Lead 指令，2026-11-01 13:40】`）

> **`hasBehavior` = 「这个关系会作为状态转移的准入条件」。**
> **不是「这个关系会产生状态变化」。**

| 关系 | `hasBehavior` | 为什么 |
|---|---|---|
| **依赖（`dependsOn`）** | ✅ **`true`** | **它阻断「提交 → 处理中」的转移** |
| **取代（`supersedes`）** | ❌ `false` | **它在采纳时处置旧卡，不阻断任何转移** |
| 约束 / 相关 / 参考 | ❌ `false` | 无任何状态影响 |

**关键区分**
- **依赖 = 准入条件**（你能不能进这个状态）；
- **取代 = 后果处置**（你进了这个状态之后，别人怎么了）。

⇒ **两者都"产生状态变化"，但只有前者是"行为"。判据是"是否阻断别人"，不是"是否改变别人"。**

**为什么取代的 `hasBehavior` 是 `false` 而不是 `true`**（这条要写清，否则会被反复质疑）：
**取代确实有"执行效应" —— 采纳时处置被取代的旧卡（不动或转取消）—— 但那是采纳流程本身的一部分，不是任何状态转移的准入条件。**
⇒ **"有效应" ≠ "有行为"。** 若把"会产生状态变化"也算作行为，那么 `取代`、以及将来任何"某某时点顺带改别人"的关系都会被算进来，`hasBehavior` 就失去了区分力。
