## 二、已确定的语义

以下每一条都**来自用户原话**（见第一节）或**来自已查实的机制事实**，不是我的偏好。

### 2.1 行为清单（只有两个）

| 行为名 | 说明 | 值 |
|---|---|---|
| `text` | 文本框。HTML `textarea` 式，可带 placeholder 虚色字 | `string[]` |
| `select` | 选择框。单选/多选**同一个行为**，靠参数区分；恒有「未选择」、恒有自填输入框 | `string[]` |

- **纯展示**：用户明确说「这是实现问题不是设计问题」「用文本框加禁止输入框，也能达到纯展示」。
  → 【实现判断】不设第三个行为，用 `text` + `readonly: true` 实现。见 §3.1。
- **复合型（选项卡等）**：用户明确「只是预告，现在没有做的必要性。不是冒烟测试里面的要求」。
  → 现在**不做**，但它是形状体系里预期存在的类别（包装型，`items` 里装子 payload、递归行为）。

### 2.2 最外层形状：object + `$type` + `items`

```js
{
  $type: "text",        // 必填，元数据
  items: [ ... ]        // 入口数组，与 $type 并列
}
```

三条硬规则：

1. **最外层必须是 object**。不能是裸数组。
2. **`$type` 必填，永远不可省。** 理由来自用户原话：一个模板里的章节可能支持多个行为，工具不知道到底是哪一个，**不能用 union 根据字段去判断**，所以参数里必须有明确指示。
3. **`items` 永远是数组**，单成员也包成数组；`items` 内部不搞 union。**最外层也不搞 union。**

### 2.3 数量动态

数量 = `items` 数组的长度。**不设 `min_count` / `max_count` 之类的数量参数**，因为「数量是动态的…因为 json 自己就是数组。所以数量是不固定的」。

### 2.4 MD 渲染的位置（硬语义）

- **控件内部的值不渲染 MD**：用户输入 / AI 写入的 `value` 永远是纯文本。
- **只有控件外部的标题/说明才渲染 MD**：用户原话「文本框内的是不渲染的。只有文本框外面的标题才有md渲染」。
- 【实现判断】因此 ② **只产出 md 文本，不渲染它**；渲染由 ⑩ ui 负责。也正因如此，**② 里不存在 `markdown` 行为**（展示 MD 发生在章节层，不在行为层）。

### 2.5 渲染器是冻结的（防注入）

- 「渲染器不是变量。不会因为用户侧的参数而改变行为」。
- 数据只当数据：JSON 里的任何内容都不能被当成"渲染指令"。
- 要改渲染行为，必须去**开发侧**改代码。

【实现判断】推论：**不搞通用 schema→表单生成器**。因为那会让 UI 的形态由数据（schema）决定，等于让数据改变渲染逻辑，与冻结冲突。每个行为的 `edit` 手工写死。

### 2.6 保存策略

用户说「没有设计」「不干涉」，但给了四条硬约束：

1. 望文生义地像 HTML 表单行为
2. 逐字 / 失焦 / 防抖 / 保存按钮，都允许，不干涉
3. **不能丢数据**
4. **不能一次保存就刷新界面、把位置变了**

【实现判断】默认策略（详见 §3.3）：**防抖 500ms + 失焦立即 flush + 卸载/页面隐藏前 flush**；IME 组合过程中不触发保存、不重渲染；`readonly` 不参与 onChange 与草稿逻辑。

### 2.7 用户也必须能「制造合法 JSON」（本轮补充的语义）

用户原话（§1.7）：**所有参数都要有用户可以写的地方并渲染为 UI；制造这个合法 JSON 的过程也要图形化操作。**

⇒ 渲染器有两个作用面，缺一不可：
- **显示**：把 AI 已提交的合法 JSON 渲染成 UI
- **生产**：让用户通过 UI 造出合法 JSON

## 三、我的判断与实现选择

**本节全部是我的判断**，标 `【实现判断】`；与用户原话无关，可被原型推翻。

### 3.1 槽位：两个（`view` / `edit`），不设第三个

- `view`：只读渲染一份已完整的 payload
- `edit`：可交互，任何改动都产生**整份 payload 的下一个候选**

【实现判断】用户说的"工具拼接（为 AI 提供文本结果）"**不是渲染器槽位** —— 那是 ⑨ ai-tool 把工具返回值渲染成文本的职责，输入也不是章节值。放进 ② 会让 ② 依赖工具层语义。

【实现判断】**纯展示 = `text` + `readonly: true`**，不新增第三个行为：
理由：既然控件内部不渲染 MD，"展示"和"文本框"在渲染上没有差别，唯一差别是能不能输入；一个参数就够，不值得一个新行为 + 一本模板作者要记的名字。渲染器对外表现为**展示块**（纯文本、可换行、保留空白），而不是画一个灰掉的输入框 —— 尊重用户「那不叫作只读」的表述。

### 3.2 `edit` 的契约：产物是「下一份 payload」，不是「值变了」

```
edit(payload, onChange) → 节点
  入参：当前 payload（可能是骨架，字段可缺 —— 见 §3.4）
  交互：任何改动都调 onChange(nextPayload)
  nextPayload：整份候选 payload
```

【实现判断】这是"制造合法 JSON"的统一入口：用户改 `placeholder`、加一个 `options`、切 `multi_select`、填一个值 —— 全部都是"产生了一份新 payload"，而不是两条不同的路径。

**两个编辑面（本轮补充）：**

| 编辑面 | 编什么 | 产出 |
|---|---|---|
| **声明编辑** | `$type`、`items` 的数量、每个实例的 `placeholder` / `md` / `readonly` / `question` / `multi_select` / `options` | 结构完整的 payload 骨架 |
| **值编辑** | 用户在控件里填的答案 | 值 |

两者**共用同一个渲染器**，只是作用对象不同。

### 3.3 保存策略的默认实现

- 控件内部维护**本地草稿**，输入即写本地；对外保存一律从草稿取快照
- **防抖 500ms + 失焦 flush + 卸载/页面隐藏 flush**（三者叠加，不互斥）
- **IME 组合过程中绝不触发保存或重渲染**（否则中文候选词被打断）——这是"望文生义像 HTML 表单"的必然要求
- **保存不做整体重渲染**：只回写状态；列表 key 必须稳定（用**我方生成的稳定 id**，不用数组索引），否则删中间一条会让后面输入框错位、丢焦点
- 外部值变化时**只在"与本地草稿不同"时采用**，避免回声覆盖光标
- 保存失败：保留草稿 + 标记未保存，不清空、不弹窗打断
- `readonly: true` 无 onChange 路径，也不参与"未保存草稿"逻辑

### 3.4 三层校验（本轮补充的最重要判断）

原来的"写入严格 / 渲染宽容"二分法**不够用**：用户是一步步填的，中间态必然不合法。实际分三层：

| 层 | 判什么 | 何时必须成立 | 不成立时 |
|---|---|---|---|
| **L1 结构** | 是 object、有 `$type`、`$type` 已注册、`items` 是数组 | **任何时刻，含草稿** | 拒绝（坏数据，不是未完成） |
| **L2 形状** | 各字段类型对不对 | **任何时刻** | 拒绝 |
| **L3 完整** | 必填齐、语义约束成立（`options` 非空、单选答案长度 ≤1 等） | **只在提交/采纳这一刻** | 阻止提交，但不毁数据 |

- **AI 路径（工具调用）**：一次给完整 → L1+L2+L3 全查，不过就拒（用户语义不变）
- **用户路径（UI 编辑）**：每次保存只查 L1+L2，L3 只做**标记不阻止**

**中间态必须能持久化，且不能因为保存而被"修正"**：空 `items`、元素只有 `$type` + `placeholder`、`options` 为空数组，都是合法中间态，必须原样存、原样取回、原样渲染。渲染器遇缺字段按"空默认"画，**不报错、不灰卡**（灰卡只用于 `$type` 未注册这类 L1 例外）。

**校验器要返回分级问题**，区分 L2 错误（阻断保存）与 L3 缺失（只标记）——UI 才能显示"还差 2 项必填"而不是报错。

### 3.5 校验入口：`$type` 是唯一判别入口

```
1. 读 payload.$type
2. 缺失 → 拒绝（报"缺少行为标识"）
3. 未在注册表 → 拒绝（报"未注册的行为（模板与行为版本不匹配）"）
   绝不回落到"猜一个"或用章节默认行为
4. 取该行为 schema，校验 items
5. items 缺失 → 拒绝
```

理由：数据不能通过"缺字段"来改变渲染选择（对应 §2.5 的防注入语义）。

### 3.6 两个行为的 `edit` 契约细节

**`text`**
- 骨架 `{ $type:'text', items:[] }` → 空态显示"+ 添加一条文本框"
- 点击 → `items: [ {} ]`，出现第一条空输入框 + 可展开的说明/placeholder 编辑
- 每条可编：`placeholder` / `md` / `readonly` / 值
- 删条 → 按 id 移除该元素
- 【实现判断】`allow_grow`（默认 false）控制"用户可增删元素"这个能力开关，**它不是数量参数**。代价约 40–60 行 UI + "删到 0 条"的边界。

**`select`**
- 骨架 → "+ 添加一组选择"
- 每组可编：`question` / `md` / `multi_select` / `options` 列表 / 值
- `options` 是二级数组编辑：加一项 / 删一项 / 每项编 `label` 与 `description`
- **删除一个 option 时，若它正在 `value` 里被选中，同时从 `value` 移除**（避免悬空引用）
- 单选 = `multi_select:false` + `value.length ≤ 1`（由我方校验器保证，不写 schema 关键词）

### 3.7 schema 子集

【实现判断，已修正】用 dsh 工具面的强制子集：`type` / `properties` / `required` / `additionalProperties` / `items` / `enum` / `const` / `oneOf`。

之前担心"`minItems`/`maximum` 不在子集里"，**这个担心已消失**：
- 数量动态 → 不需要 `minItems` / `maxItems`
- 单选/多选 → 由 `multi_select` 布尔参数表达，不需要 `maxItems`
- 但前提是 ⑨ ai-tool 把 body 以**结构化 schema** 暴露（不是 `type:'json'` 不透明）；若是后者则不受 dsh 子集限制，可用更多关键词。

### 3.8 注册形态

- 所有行为在 `apply(ctx)` 内注册，返回清理函数；**不做模块加载期自注册**
- 外部扩展走同一个 `register(def)`，且**注册 API 不暴露给 AI 工具参数**（渲染器是开发侧的、不是参数）
- 行为**自带渲染器**，不做"名字 → 去别处查"

### 3.9 行为注册表

需要 `name → { schema, renderers }` 的注册表。表的内容**只能由代码填充**，不能由工具参数填充。这是"数据与渲染逻辑物理分离"的硬边界，也是冻结语义的落地。

## 六、需要与其它成员对齐的

以下都是**实现/接口层**，按用户指示由成员之间互相问，不上报用户。

### 6.1 → `mod-types`（③ types）

1. **章节 `accepts` 是数组**（多个候选），payload 里只有一个 `$type`；`$type` 必须 ∈ 该章节 `accepts` —— 这条校验归 ③（它知道 accepts），② 只负责"`$type` 有没有注册、`items` 合不合该行为的 schema"。
2. **章节 label（③）与行为 `md`（②，每实例元数据）的分工**：label = 这一章叫什么；`md` = 这个控件上面那句说明。两者不同层级，不是重复真源。
3. **`required` / `aiWritable` 归 ③**（章节属性）。② 只描述"这个控件的值合法吗"。
4. **声明编辑的初始值从哪来**：用户从零造时 `items` 是空数组，还是模板章节给初值？

### 6.2 → `mod-ai-tool`（⑨ ai-tool）

1. **body 以结构化 schema 暴露**，不能用 `type:'json'` 不透明 —— 模型必须看到 `$type` 必填、且知道其可选值。
2. **`$type` 的可选值集合随模板章节变化**，应由 ⑨ 在运行时按模板生成，不写死（写死必然漂）。
3. 上述两条决定 §3.7 的 schema 子集可用范围。

### 6.3 → `mod-ui`（⑩ ui）

1. 渲染器接收 `{ $type, items }`，返回**节点描述 + md 文本**；**md 文本由 ⑩ 渲染**，② 不渲染。
2. **AI 写的长篇汇报内容的 MD 渲染归 ⑩**，不经过 ②（汇报没有 schema、没有章节、没有值，不是"章节 payload"）。
3. 节点描述的接口形状需对一次（实现问题）。

### 6.4 → ⑦ taskcard / ⑧ core

1. **答案（用户填的值）存哪、谁写**：② 只做"声明 → 控件"和"控件 → 新 payload"的转换，**不负责存储**。
2. **声明在什么阶段可改**：创建时？采纳后还能改吗？我倾向"只要能拿到编辑入口就能改"，权限由 ⑦/⑧ 判，② 不设限。
3. **`$type` 用户能否切换**（把这一章从 `text` 改成 `select`）：我倾向能（accepts 是 union，选哪个是用户自由），但切换后旧 `items` 不适用，**需要清空或转换**；清空简单但会丢用户已填内容 —— 待与 ⑦ 对齐后定。
